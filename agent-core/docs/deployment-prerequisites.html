Before anything

00

Toolchain and account

None of this is stage-specific. All of it blocks the first apply.

Local toolchain

terraform
Resolves hashicorp/aws ≥ 6.58 and hashicorp/time. terraform init per directory, or once in 00_all_at_once.
aws cli
Not used by terraform, but every verification step below is a CLI call. Credentials must resolve — aws sts get-caller-identity should print your ARN.
uv
Installs Python 3.13 for you. The deployment zips target PYTHON_3_13; building on the same minor version the container runs avoids a class of wheel mismatch.
node + npm
The chat proxy is Node because Lambda response streaming exists on Node.js managed runtimes only. The UI is a Vite build.

Behind a TLS-inspecting proxy uv needs UV_SYSTEM_CERTS=1 (or uv sync --system-certs), otherwise every install fails with invalid peer certificate: UnknownIssuer.

Build artifacts — before plan, not before apply

Four stages read files with filemd5() or filebase64sha256(), and those are evaluated at plan time. A missing zip is not a slow apply — it is a plan that refuses to produce a diff. 

make artifacts   # package + seed + ui-build — everything below at once

# or individually
uv run scripts/package.py   # dist/*.zip  → stages 02, 05, 07
uv run scripts/seed_s3.py   # terraform/01_s3_data/seed/*.json → stage 01
make ui-build               # ui/dist/ → stage 08

Account and region

Region
One region for the whole stack. AgentCore Runtime, Gateway and Memory must all be in it, and the Cognito discovery URL is built from it.
Model access
bedrock_model_id has no safe default — model ids are account- and region-specific. This stack ships us.amazon.nova-lite-v1:0.
Password
One human input besides the model id: password for the Cognito machine user, minimum 8 characters, marked sensitive. Keep it out of any *.tfvars you commit.

Anthropic models need a form Anthropic models on Bedrock require a use-case submission approved per account. Until it is, every call fails with ResourceNotFoundException: Model use case details have not been submitted for this account — which names neither the model nor the agent that asked for it. Amazon's own models have no such gate, which is why the default here is Nova.

Dependency order

The number is the order. Two stages are roots and could run first or in parallel; everything else consumes an earlier stage's terraform output.

Roots 01 s3_data — nothing 04 memory — nothing
Then 02 lambda ← 01 03 gateway ← 02
Then 05 runtimes ← 01, 03, 04 06 observability ← 03, 04
Last 07 api ← 03, 05 08 ui ← 07

Worth knowing 06 does not depend on 05. Its number reads as "after the runtimes", but it needs only the gateway and memory ARNs. There is an argument for applying it earlier — the X-Ray trace destination is account-level, so setting it after the runtimes exist loses the first container's start-up traces.

Stage 03

03

gateway

Identity and the AgentCore Gateway with one target. The widest output surface in the stack — three later stages need something from it.

Needs

From 02
lambda_arn, lambda_name
You supply
password — the Cognito machine user's, minimum 8 characters, sensitive.
Decisions
gateway_authorizer_type — AWS_IAM (default) or CUSTOM_JWT. Decide before the first apply.

Immutable authorizer_type cannot be changed in place. Switching it replaces the gateway and every target under it, and the replacement has a new gateway_url — which then propagates into stage 05.

Creates — roles

RoleTrusted byPermissions
<gateway_name>-role bedrock-agentcore.amazonaws.com
optional aws:SourceAccount / aws:SourceArn 		lambda:InvokeFunction the one target function

Also creates, and they are not roles A Cognito user pool, an app client (ALLOW_USER_PASSWORD_AUTH, ALLOW_REFRESH_TOKEN_AUTH, no secret) and one user with a permanent password. Without the user the stack deploys and nothing is callable.

Confused-deputy conditions are a second apply restrict_trust_to_gateway = true adds aws:SourceArn to the trust policy — but that ARN does not exist until the gateway does. Apply once with false, then flip it.

Deployer must be able to

  • bedrock-agentcore:CreateGateway
  • bedrock-agentcore:CreateGatewayTarget
  • bedrock-agentcore:Get/Update/DeleteGateway
  • cognito-idp:CreateUserPool
  • cognito-idp:CreateUserPoolClient
  • cognito-idp:AdminCreateUser
  • cognito-idp:AdminSetUserPassword
  • iam:PassRole
  • iam:CreateRole
  • iam:PutRolePolicy

Expect one retry A time_sleep sits between the role and the gateway because IAM is eventually consistent. If you still see ValidationException: Gateway service is not authorized to perform AssumeRole, the policy is correct and has not propagated — raise iam_propagation_delay.

Three separate actions, one conversation InvokeAgentRuntime sends the message. GetAgentCard fetches the card, and runs first — grant only the former and every delegation dies at discovery with a 403 that reads like the remote agent is down. InvokeGateway is a third action again, and does not follow from either.

IAM is the entire check between services Only the supervisor has an authorizer (CUSTOM_JWT, because a person is on the other side). The other four take SigV4 with their execution role, so there is no second lock behind the policy above.

Deployer must be able to

  • bedrock-agentcore:CreateAgentRuntime
  • bedrock-agentcore:Get/Update/DeleteAgentRuntime
  • bedrock-agentcore:ListAgentRuntimes
  • iam:PassRole
  • iam:CreateRole × 5
  • iam:PutRolePolicy
  • s3:PutObject
  • s3:GetObject

Two things this stage deliberately does not create No endpoint resources — CreateAgentRuntime makes DEFAULT itself, so declaring one is a ConflictException on every apply. No log groups — their names contain a service-generated runtime id, so they cannot exist before the runtime does, and the container creates its own.

One CloudWatch role per account, per region aws_api_gateway_account is an account-level setting shared by every REST API in the region. If something else already manages it, set manage_apigw_account_logging = false — otherwise this stack takes it over. Leave it unset when nothing manages it and the stage fails with BadRequestException: CloudWatch Logs role ARN must be set in account settings, pointing at a resource nothing in your API refers to.

The one people miss

iam:PassRole. Creating a role is not the same as being allowed to hand it to a service. Five stages create a role and immediately give it to Lambda, API Gateway or AgentCore, and without PassRole each fails at the second step with a message about the service rather than about you.

Scope The action lists on this page are derived from the resource types each module declares. Treat them as the shape of the policy, not a copy-paste artefact — confirm against your own identity with the simulator below before assuming a gap is a bug in the stack.

Verifying, before and after

→

Four checks that answer without an apply

Each one turns a guess into a fact.

Does this principal have the action?

The fastest way to settle any permission question, and it modifies nothing. It distinguishes allowed from implicitDeny, which is what a missing action looks like. 

aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::<account>:role/agentcore-hiring_supervisor-role \
  --action-names bedrock-agentcore:InvokeAgentRuntime bedrock-agentcore:GetAgentCard \
  --resource-arns <the callee's runtime arn> \
  --query 'EvaluationResults[].{action:EvalActionName,decision:EvalDecision}' --output table

Does the chain hold?

terraform validate checks one directory in isolation, so a stack where 06 needs gateway_arn and 03 never exports it validates cleanly and then cannot apply. This is that audit, plus the IAM and documentation invariants on this page. 

uv run scripts/check_terraform_chain.py

Is the Gateway reachable, without an agent in the way?

Signs with your own credentials and lists what the Gateway publishes. Needs bedrock-agentcore:InvokeGateway on your identity — the grant in stage 05 is for the screening runtime, which is a different principal. 

make gateway                                        # list the tools
make gateway CALL=hrdata___get_requisition ARGS='{"job_id":"J2001"}'

MCP Inspector will not work here It sends a bearer token and cannot sign SigV4. It is usable only if you set gateway_authorizer_type = "CUSTOM_JWT".

Did the code actually ship?

Artifact keys are content-addressed, so new bytes mean a new S3 key, a new object and a new runtime version. A version that never moves is the one symptom of a deploy that silently changed nothing. 

aws bedrock-agentcore-control get-agent-runtime \
  --agent-runtime-id <id> \
  --query '{version:agentRuntimeVersion,prefix:agentRuntimeArtifact.codeConfiguration.code.s3.prefix}'

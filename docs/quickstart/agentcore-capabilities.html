Why any of this exists

Everything that makes an agent work on a laptop is what breaks in production

On your laptop

  • State is a Python dict that dies with the process
  • Auth is your ~/.aws/credentials
  • Tools are functions you imported
  • Debugging is a print() and a scrollback buffer
  • Quality assurance is running it three times and it "seeming fine"
  • One user — you — and one conversation at a time

The moment someone else can call it

  • State must outlive the request and not leak between users
  • Auth must distinguish a person from a service
  • Tools live in other teams' accounts, behind other teams' APIs
  • A wrong answer at 2am needs a trace, not a hunch
  • A prompt change that "seems harmless" can drop accuracy 20% silently
  • Turns run for hours; Lambda gives you fifteen minutes
The honest framing

None of this is agent-specific. It is the same list you would write for any service. AgentCore's bet is that you would rather not build it a sixth time.

Ask the room: who has already built session isolation or a token vault by hand? Usually a third of hands. Those are the people who will get the value fastest — and the people most alert to lock-in.
The mental model

A framework decides how your agent thinks.
A platform decides what happens when other people can call it.

Framework — you keep choosing

Strands, LangGraph, CrewAI, LlamaIndex, or a bare while loop around the Messages API. AgentCore does not care and does not replace it.

Platform — AgentCore's job

Hosting, session isolation, tool plumbing, memory, identity, traces, authorization, evaluation. Nine services you adopt one at a time, not a bundle you swallow whole.

Model-agnostic too. Bedrock models are the smooth path, but Anthropic's API directly, OpenAI, Gemini, Mistral, Cohere, HuggingFace or a self-hosted model all work — a runtime is a container that happens to make outbound HTTPS calls. Choose on cost, capability, regional availability or compliance; nothing in Runtime inspects which model you picked.

This is the slide that defuses the most common objection — "we already standardised on LangGraph". The answer is that the two are not competing; AgentCore is where LangGraph runs.

A naming note

AWS material often counts seven components by folding Code Interpreter and Browser together as "Tools" and leaving out the two newest. Same services, different arithmetic — do not let the count confuse you.

The rule that matters more than the count

Take only what you need. Runtime alone is a perfectly good adoption. Nothing forces the other eight, and nothing charges you for them.

Emphasise the second callout. The most successful adoptions in the room will be "Runtime + Observability" for six months before anything else is touched. Presenting all nine as a package is how you lose people.

Capability 01

Runtime — a serverless container host built for agents

What it is

You hand it a zip or an image. It hands you an ARN and an endpoint. Each session gets its own microVM with dedicated CPU, memory and filesystem.

What it replaces

An ECS service, an ALB, an autoscaling policy, and the session-affinity logic you were about to write.

The surprise

Turns can run for hours — but the container has 30 seconds to become healthy at cold start, and a heavy dependency tree spends it.

The whole contract, in five lines
from bedrock_agentcore.runtime import BedrockAgentCoreApp

app = BedrockAgentCoreApp()

@app.entrypoint
def handler(payload, context):          # context carries session id + headers
    return {"result": agent(payload["prompt"]).message}

if __name__ == "__main__":
    app.run(port=8080)                  # HTTP protocol -> 8080

Same signature for every framework. payload is your own JSON schema; the return dict is serialised to JSON.

Against the thing you would otherwise use
LambdaAgentCore Runtime
Max duration15 minutes8 hours
Max payload6 MB100 MB
IsolationShared execution envmicroVM per session
Idle behaviourCold start15-min idle timeout
BillingPer ms of invocationPer second, while processing

The container itself is unremarkable: Linux, ARM64 (Graviton), a POST /invocations endpoint and a GET /ping health check. BedrockAgentCoreApp wires all of that for you.

The 30-second health check is the single most common launch failure. strands-agents[a2a] pulls in a PostgreSQL driver and gRPC; the OTel distro walks ~45 instrumentations before your server binds. Prune the first, disable the auto-instrumentor if you must. The symptom is HTTP 424, which reads like a client error. Note the tension with AWS's "sub-second cold start" claim — that is the microVM starting, not your dependency tree importing.

The protocol decides the port. Get it wrong and nothing tells you.

The failure that wastes an afternoon

Bind 8080 in an A2A container and the deploy succeeds. The container starts, fails its health check, and the error you eventually see is a timeout. Nothing anywhere says "wrong port." This table is the first thing to check when a deploy works but never answers.

If you only leave one table on screen during questions, make it this one. Every team hits it exactly once.
Capability 01 · the parts people discover late

Three Runtime behaviours worth designing for on purpose

Streaming vs blocking

A plain def entrypoint blocks until the whole answer exists, then returns it in one piece. Make it an async def that yields and the caller gets tokens as they are generated.

Rule of thumb: anything a human waits on should stream. Anything a service consumes should not.

Long-running work

Past ~15 minutes of silence a session is considered idle. For genuinely long jobs the agent reports status HEALTHY_BUSY from its ping handler, which keeps the session alive to the 8-hour ceiling.

Design consequence: "still working" is a state you must actively assert, not a default.

Multi-modal payloads

100 MB covers text and documents, images (PNG/JPEG/WebP), audio, video and large datasets — which is what makes document-extraction and transcription agents practical here rather than in Lambda.

Watch: big payloads are billed compute time too.

The context object

Alongside the payload you get session id, user id and — if you allow-list them — custom headers. That is the supported channel for OAuth tokens, tenant identifiers, tracking ids and feature flags. Use it instead of smuggling metadata into the prompt.

The HEALTHY_BUSY detail is the one that saves a project. Teams building long research or migration agents assume the 8 hours is automatic; it is available, but only if the ping handler claims it.
Capability 02

Gateway — a protocol adapter, not a router

What it is

A managed MCP server fronting things that are not MCP servers. One endpoint, many targets, one tools/list.

What it replaces

The MCP wrapper server you were going to write for each internal API, plus its deployment, plus its auth, plus its token refresh.

The surprise

Tools arrive namespaced: hrdata___find_by_skill. Split on the wrong delimiter and your Lambda dispatch silently mismatches.

The design rule, in one sentence

Put a thing behind the Gateway only when it cannot speak MCP on its own. A server that already speaks MCP should be a Runtime with the MCP protocol, called directly — routing it through Gateway adds a hop and buys nothing.

The 1-click SaaS integrations (Slack, Salesforce, Jira, Asana, Zendesk) are the fastest demo you can give a business audience: provide OAuth credentials, get working tools, no integration code.
Capability 02 · the operational detail

Three target types, one URL, and a naming rule that bites

Lambda targets

Your own logic: database queries, business process automation, proprietary rules. You define each tool's JSON schema — and the description is what the model reads to choose it.

OpenAPI targets

Hand it a Swagger/OpenAPI spec and every endpoint becomes a tool. Auth via API key, OAuth 2.0 or IAM, with credentials held in a credential provider rather than your code.

Smithy targets

Built-in models for hundreds of AWS services — DynamoDB, S3, Lambda, EC2, RDS, SQS, SNS. Gateway translates MCP calls into SDK calls and handles IAM via the execution role.

One gateway, one URL, every framework
https://{gatewayId}.gateway.{region}.amazonaws.com/mcp
Semantic tool search

Agents start mis-picking somewhere around 100 tools; turn semantic search on past ~50 so the agent searches rather than being handed the whole list. It is set at gateway creation and cannot be changed later — like the gateway id and region.

Reading the namespaced tool name in a Lambda
def lambda_handler(event, context):
    raw = context.client_context.custom["bedrockAgentCoreToolName"]
    tool = raw.split("___", 1)[-1]        # hrdata___find_by_skill
    return DISPATCH[tool](**event)       # event is flat — no API GW envelope
Check this against your own gateway

Working code in agent-core/ uses a three-underscore delimiter, and its tests assert it. Some AWS course material writes the pattern as target__tool with two. Print the raw name once on your own gateway and split on what you actually receive.

The "description is what the LLM reads" point deserves ten seconds. Teams write tool descriptions like internal API docs — tech stack, owning team — when the only reader that matters is choosing between them.
Capability 03

Memory — events are written now, records appear later

Short-term — the conversation

Raw user messages, agent responses, tool invocations and system events, written synchronously and read back in order. Retention is configurable from 7 to 365 days.

CreateEvent · ListEvents · GetEvent · ListSessions

Long-term — the extracted records

Strategies run asynchronously over those events and write durable records you query by relevance within a namespace.

RetrieveMemoryRecords(namespace=…)

The surprise that generates the most bug reports

Long-term extraction is eventually consistent. You write an event, immediately query long-term memory, get nothing, and conclude Memory is broken. It is not — the strategy has not run yet. Test long-term retrieval on the next session, not the current turn.

The key decision: what are your two ids?

actorId is the memory owner and the security boundary — a person, or an agent. sessionId is the unit of conversation. Get this pair wrong and memory either leaks between users or forgets between turns.

Namespaces are how you scope a query

/strategy/{strategyId}/actor/{actorId}/session/{sessionId} — read left to right, that is global → per strategy → per actor → per session. Retrieve at the granularity you actually mean.

If someone asks "why not just DynamoDB?" — the honest answer is that short-term memory is a table you could write in an afternoon. The part you cannot write in an afternoon is the extraction pipeline behind long-term strategies. Also worth noting: one memory can be shared across several agents.
Capability 03 · what actually gets extracted

Four built-in strategies, and a custom one when none of them is your domain

Strategy 1

Semantic

Facts and knowledge from a session, retrievable by meaning.

Support agent recalls that order #ABC-123 belongs to a specific ticket, so the user need not repeat it.

Strategy 2

Summary

A condensed account of roughly one conversation.

After a 30-minute troubleshooting call: "reported issue with v2.1, tried a restart, sent the KB article."

Strategy 3

User preference

Stable preferences accumulated across many sessions.

An e-commerce agent remembers favourite brands and size, and tailors recommendations later.

Strategy 4

Episodic

Structured records of completed interactions — situation → intent → action → outcome — plus reflections across many episodes.

A deployment agent learns that memory-error Docker builds were fixed five times by multi-stage builds, and applies it.

Why episodic is the interesting one

The first three remember facts. Episodic remembers which strategies worked — outcome is part of the record, so the agent can prefer the approach that succeeded rather than re-deriving it. That is the difference between an agent with a history and an agent that improves.

Custom strategies

An extraction prompt (what to pull out, your domain rules) plus a consolidation prompt (merge, deduplicate, update vs add vs skip) plus the model of your choice.

When to reach for one

When the generic summary is prose and you needed structure: ranked preferences, confidence scores, fields a downstream API can consume. Prose is a bad interface for the next system.

Good demo if you have time: the travel-booking transcript. A generic summary produces a readable paragraph; a custom strategy produces ranked loyalty programmes with confidence scores. Same conversation, one is queryable.
Capability 04

Identity — two directions, and they work differently

Inbound — who may call this agent

Humans arrive with a JWT from Cognito, Entra ID, Okta or any OIDC provider — configured as a JWT authorizer on the runtime or gateway.

Machines arrive with SigV4 signed by an IAM role: credentials valid and permission in scope, or the call is blocked.

Outbound — what the agent may do as you

A token vault holds OAuth 2.0 credentials and API keys, KMS-encrypted, scoped per agent-and-user, refreshed automatically and logged on every access.

Built-in providers: Google (Drive, Calendar, Gmail), GitHub, Slack, Salesforce, Auth0, Microsoft, Cognito — plus any OAuth 2.0 service you configure yourself.

The thing that catches everyone

An inbound human token is not a credential you can forward inward. A supervisor authenticated by Cognito calling a specialist runtime makes that inner hop machine-to-machine, signed with its own execution role. Any user context the inner agent needs must travel in the payload or an allow-listed header — never as a re-used bearer token.

This is an architecture constraint, not a bug: it forces you to decide explicitly what the inner agent is allowed to know about the user. Teams that assume token pass-through design themselves into a corner around week three.
Capability 04 · the distinction that decides your design

Ask one question: does a human have to consent?

2LO — two-legged, machine to machine

The agent authenticates as itself with client credentials. No user, no consent screen, no interaction.

  • Pull logs from internal APIs
  • Process company analytics
  • Generate scheduled reports
  • Write to a shared data warehouse

Choose when the data is the company's, or the job runs at 3am with nobody to ask.

3LO — three-legged, on behalf of a user

The agent hands the user an authorization URL; the user logs in and consents; the returned code is exchanged for tokens the vault then keeps and refreshes.

  • Read this user's Gmail
  • Access this user's calendar
  • Save a file to this user's Drive

Choose when the resource is personal and the user is present to approve it.

The workload access token

AWS-signed, issued to the runtime, carrying agent identity plus user identity — "an agent visa and a user passport." It is what the vault checks before releasing a credential, which is how the same agent gets your Google token and not someone else's.

The 2LO/3LO split is the cleanest vocabulary in the whole platform. If a team cannot say which one a given integration is, they have not finished designing it.
Capability 05

Observability — the only reason you will ever find out what happened

What it is

Built-in metrics — session counts, latency, duration, token usage, error rates — across Runtime, Memory, Gateway, Tools and Identity, in CloudWatch's GenAI observability dashboard.

What it replaces

Logging every prompt to stdout and grepping five log groups at 2am trying to reconstruct one request.

The surprise

Transport spans come free. Model and tool spans do not — they need aws-opentelemetry-distro and the process started under opentelemetry-instrument.

The hierarchy every dashboard is built on
SESSION  (a one-hour conversation)
├── TRACE 1  "What's the weather?"
│   ├── Span: LLM reasoning        200ms
│   ├── Span: Weather tool call    500ms
│   └── Span: Format response       50ms
├── TRACE 2  "Any tips?"
│   ├── Span: LLM reasoning        180ms
│   ├── Span: Memory retrieval     100ms
│   └── Span: Generate response    150ms

Session = the conversation · Trace = one user prompt · Span = one step inside it

What to watch in production

  • Performance — latency p50/p90/p99, duration, tokens per request
  • Reliability — 4xx vs 5xx, throttles, success rate
  • Cost — invocations, token consumption, memory resource usage
  • Usage — active sessions, requests per minute, peak times

It is OpenTelemetry underneath, so third-party platforms work too — enable Transaction Search in CloudWatch, and know that OpenLLMetry/Traceloop-style tooling plugs into the same stream.

One requisition, one trace — but only if you propagate the session id on every hop. Drop it once and you get five unrelated traces that share nothing, which is worse than no tracing because it looks like it is working.

Three quiet failures worth naming: a trace that splits into five (dropped header), spans with no model detail (missing distro), and a session that looks healthy while every tool call inside it failed and the agent apologised its way to an answer.
Capabilities 06 & 07 · together, AWS calls these "Tools"

The two you will either love or never touch

Code Interpreter

A sandboxed session where model-written code actually runs — Python, JavaScript, TypeScript, with pandas and numpy available.

executeCode · executeCommand · writeFiles · readFiles · removeFiles · listFiles

Reach for it when the answer requires arithmetic over data the model should not eyeball — a 40,000-row CSV, a statistical test, a format conversion, a chart.

Browser

A managed, serverless headless Chrome the agent drives: clicking, typing, submitting, executing page JavaScript, reading the page as a human sees it.

Live view lets a human watch and take control. Session replay records every interaction — a real audit trail, not a log line.

Reach for it when the system of record has no API and never will.

Both have two network modes

Public for the open internet — public APIs, web scraping. VPC for anything internal — databases, private APIs, internal web apps. Pick deliberately; the default is the weaker guarantee.

The CAPTCHA rule

Do not use Browser for general web search, and do not try to solve CAPTCHAs programmatically. Use a search tool for search, use Browser for specific page actions, and route the CAPTCHA to a human through live view.

Say this part out loud: the HR example uses neither. Scoring is deterministic Python behind an MCP server, and every data source has an API. Both of these are answers to a question you should be able to state first.

Browser is genuinely the escape hatch for legacy integration — worth flagging to anyone in insurance, logistics or public sector, where "there is no API" is a fact of life rather than a temporary state.
Capability 08

Policy — because "the agent decided to" is not a control

The problem it exists for

  • Agents choose which tools to call, and with what arguments
  • LLMs can be talked out of your system prompt by prompt injection
  • A single breach is not one bad answer — it is one bad action

Concretely: the agent pays a $50,000 claim it was told to cap at $10,000. It approves an ineligible customer. It reads a PII table because a user asked nicely in three paragraphs.

What Policy is

A deterministic, fine-grained authorization layer that intercepts every tool call flowing through the Gateway and evaluates it against Cedar rules — outside the agent, outside the LLM.

What it is not: a prompt guardrail (those live inside the model and can be argued with), rate limiting, or API traffic management. And it does not care which model or framework you used.

The sentence that sells it to a risk officer

The system prompt is a request. Cedar is a rule. No amount of clever prompting changes what a forbid policy does.

This is the newest capability and the one most likely to be unfamiliar. For regulated audiences it is often the single feature that makes the platform viable at all.
Capability 08 · how it actually decides

Default deny, forbid wins, and one mode you must run first

The evaluation rules

  • Default deny — no matching policy means blocked. Tools are closed out of the box.
  • At least one permit must match for access.
  • Forbid wins — a matching forbid denies even if a permit also matched.

FORBID > PERMIT

A Cedar policy has three parts

Effect — permit or forbid.
Scope — the principal, action and resource it applies to.
Condition — a when or unless clause that must hold.

Cedar is not a programming language: no loops, no state. That is why the decision is deterministic.

Where the principal comes from

The caller's JWT claims, mapped into the policy entity store. Your identity provider controls the claims; Cedar controls what they mean at the tool level.

That is how role-based access, OAuth scope checks and department rules all become one mechanism.

Two enforcement modes — run them in this order

LOG_ONLY evaluates every policy and writes ALLOW/DENY traces, but blocks nothing. This is dev mode, and where you discover your false denials.

ENFORCE actually blocks, returning an error to the agent.

Best practice: stay in LOG_ONLY for at least one full business cycle — month-end and quarter-end do things your test data does not.

The patterns you will actually write

Block all · disable one tool · block one user · numeric ceilings (refunds ≤ $500) · string match · set membership · required fields · unless guards · RBAC · OAuth scope · multi-condition.

Real examples: no scheduling outside 08:00–17:00; only doctors may cancel appointments; a senior analyst may approve up to $1M.

NL2Cedar drafts policies from plain English — treat the output as a draft to review, not as the policy.

Three operational rules

1. Keep Cedar policies in git, with PR review and CI validation — they are code. 2. Separate the gateway execution role (minimum permissions, runtime evaluation) from the policy management role (CRUD) and never merge them. 3. Use permit for business logic and reserve forbid for hard safety boundaries.

The LOG_ONLY-for-a-full-business-cycle advice is the one to repeat. Policies that look complete in testing fail on the day the finance team does something they only do once a quarter.
Capability 09

Evaluations — because "we ran it a few times and it seemed fine" is not a test

The trap

  • Run the agent a few times in dev; if it seems good, ship it
  • Trust a gut feeling over any number
  • Never re-evaluate after a prompt change

What it costs: a model that "seems fine" carries 15% toxicity on edge cases. A harmless-looking prompt tweak drops accuracy 20%. You find out when a customer complains.

What Evaluations does

It reads the traces you are already emitting via OpenTelemetry, scores them, and writes results back to CloudWatch.

It measures goal attainment (did the task complete end to end), response correctness, tool accuracy (right tool, right parameters), safety, and whatever custom metric you define.

Note the dependency: no Observability, no Evaluations. Traces are the input.

The framing that lands with engineering leadership: this is the regression test suite for a non-deterministic system. You cannot assert equality on the output, so you score it — and then you can compare model A to model B with a number.

Across the whole multi-turn conversation — the metric the business actually cares about.

On-demand — you choose what to score

Name specific span, trace or session ids. A point-in-time assessment returning a label, a value, an explanation and token usage.

Best for: dev and testing, debugging a specific failure, validating a fix, analysing historical data.

Online — it scores production as it flows

Configure a sample rate (say 10%) and optional filters; evaluators run continuously and simultaneously, aggregating into CloudWatch dashboards.

Best for: catching quality regressions, trend analysis, knowing before the customer does.

Custom evaluators, two flavours

LLM-as-a-judge — your model, your instructions, your scoring schema, applied at span, trace or session level. Best for subjective or domain-specific quality. Code-based (Lambda) — regex, external lookups, business rules; deterministic, with no model uncertainty. Best for format validation and exact matching. Start with built-ins; add custom only when a built-in cannot express what you mean.

Cost note if asked: built-in evaluators are token-priced, custom evaluators are per request, and an LLM-as-a-judge adds its own inference cost on top. Sampling at 10% rather than 100% is the main lever.

Part 2 · the case for

The pros are mostly things you stop writing

Infrastructure you no longer own

  • Session isolation — a microVM per session with its own CPU, memory and filesystem
  • Long turns — 8 hours, where Lambda caps at 15 minutes
  • Large payloads — 100 MB against Lambda's 6 MB, which is what makes multi-modal practical
  • Per-second billing — you pay while processing, not while idle
  • No cluster — no ECS service, ALB, target group or scaling policy

Plumbing you no longer maintain

  • Tool adapters — Lambda, OpenAPI and Smithy targets become MCP tools
  • SaaS integrations — Slack, Salesforce, Jira, Asana, Zendesk in one click
  • Memory extraction — the async summarise-and-store pipeline is managed
  • OAuth token vault — third-party refresh tokens are not your problem
  • Trace wiring — OTel to CloudWatch without building a collector
  • An eval harness — thirteen evaluators you did not have to design
The one that is easy to undersell

Framework and model indifference. Runtime hosts a container that listens on a port. Strands today, LangGraph next quarter, a bare loop after that — the deployment story does not change. That is unusual for a managed agent product, and it is the main reason the lock-in is smaller than it looks.

The composability point matters commercially: you can adopt Runtime and keep every other piece of your stack, which makes the first proof-of-value cheap to attempt and cheap to abandon.
Part 2 · the case for

And a few that only show up at team scale

One security review, not five

IAM, VPC, CloudTrail, KMS and CloudWatch are already approved in most AWS shops. An AgentCore service inherits that review instead of starting a new one.

An answer for the risk officer

Cedar policies are deterministic, reviewable, version-controlled and outside the model. "The LLM was instructed not to" becomes "the call is structurally impossible."

Quality you can put a number on

Goal success rate and tool accuracy as trends, not anecdotes — which is what turns "the agent feels better" into a release decision.

Interop by protocol

MCP for tools, A2A for agent-to-agent. Both open specs, so another team on another stack can call your agent without importing your library.

Independent deploys

Each agent is its own runtime with its own ARN. The screening team ships without asking the scheduling team — the actual promise of "multi-agent".

A real IaC path

Terraform and CloudFormation resources exist, so runtimes, gateways, memories and policies are reviewable code rather than console clicks.

"One security review, not five" is usually the argument that actually moves an enterprise. Engineers pick on capability; platform teams pick on approval friction; risk teams pick on Policy.
Part 2 · the case against

The cons are mostly opacity — and one of them is expensive

Failures arrive as silence

  • Wrong protocol port → deploy succeeds, requests time out, nothing says why
  • Slow cold start → HTTP 424, which reads like your fault, not the container's
  • Dropped session id → five traces instead of one, and nothing looks broken
  • Async memory extraction → an empty long-term query that looks like data loss
  • Default-deny Policy → a correct agent that can do nothing, and a trace that just says DENY

Constraints you must design around

  • runtimeSessionId has a 33-character minimum — your natural business key probably fails validation
  • No inbound token pass-through — user context must travel in the payload
  • 30-second health check at cold start, spent by your dependency tree
  • ARM64 only — wheels built for your laptop will not do
  • Immutable at creation — gateway id, region and semantic search cannot be changed later
  • Regional availability is narrower than core AWS services — check before you promise a region
The honest summary

The platform is solid; the feedback loop is the weak part. Most of a team's first two weeks goes into failures whose error messages do not name the cause. Budget for that explicitly rather than discovering it in a sprint review.

Do not soften this slide. Teams that hear it up front treat the first week as expected cost; teams that do not, escalate it as a platform defect.
Part 2 · the case against

Three more, in decreasing order of how often they kill a project

Cost is hard to forecast

Consumption-based across many dimensions at once — runtime seconds, memory events stored and retrieved, gateway invocations, browser and interpreter session time, evaluator tokens — on top of model tokens.

Mitigation: bound the agent loop before anything else, sample evaluations rather than scoring everything, destroy sessions instead of letting them idle out, and put cost-per-session on a dashboard in week one. A runaway loop is a billing incident, not just a bug.

The surface is young and still moving

Policy and Evaluations are the newest members and were not in the original launch set. APIs, SDK names and IaC coverage have all moved recently; expect resources to lag the console and an occasional SDK upgrade to be a real migration.

Mitigation: pin versions, read release notes before upgrading, and keep the local-run path working so you can bisect against something that does not involve AWS.

Lock-in is real but bounded

Your agent logic is portable — a container listening on a port. What is not: Gateway target definitions, Memory strategies and stored records, Identity configuration, Cedar policies, and the IAM around all of it.

Mitigation: keep tool implementations behind your own interface, and treat Memory as a cache of facts you could re-derive, not as your only copy.

If asked for hard pricing numbers, do not quote from memory — point at the AgentCore pricing page. The defensible statement is the shape of the bill, which is what this slide gives. One order-of-magnitude anchor from AWS course material (Oct 2025): a Gateway serving ~10,000 requests a day was on the order of a couple of dollars a month, before the model and runtime costs that dominate.

Part 2 · the verdict slide

Use it when three of these are true. Do not when two of the right ones are.

Adopt

  • You are already on AWS and Bedrock is an approved service
  • Turns are conversational and long, not batch and short
  • More than one team will call the agent
  • Tools live behind existing Lambdas or internal REST APIs
  • Tool calls have consequences, and someone will ask who authorised them
  • You need per-user isolation and cannot justify building it
  • You want the agent in production this month, not this quarter

Do not adopt

  • Multi-cloud portability is a hard requirement, not a preference
  • The workload is a scheduled batch job with no session at all
  • Latency budget is tens of milliseconds — this is not that platform
  • Your required region does not have it yet
  • You have a platform team already running agents well on Kubernetes
  • The whole thing is one prompt and one API call — just call the model

The cheapest possible evaluation: deploy one existing agent as a Runtime with Observability on. Nothing else. If that week feels good, the other eight capabilities are additive decisions you can make later — and if it does not, you have lost a week and no architecture.

This is the slide to leave on screen during Q&A if the meeting is a go/no-go. The last callout is the recommendation: a one-week, one-capability trial with a defined exit.
Part 3

Empty folder
to deployed agent

Eleven steps. The first four need no AWS account beyond credentials, and the first two need no AgentCore at all.

Tell people not to type along — the code is in the tutorial. This section is about the order, which is the part that is hard to recover if you get it wrong.
Step 0

Prerequisites — fifteen minutes, once

  • An AWS account with Bedrock model access enabled for the model you intend to use — a separate opt-in, and the most common first-hour blocker
  • A region where AgentCore is available — confirm before you design around it
  • Python 3.11+ and uv or pip
  • Docker only if you plan to ship a container image rather than a zip
  • An IAM execution role with permissions for Bedrock, CloudWatch Logs and whatever your tools touch
Install
pip install bedrock-agentcore \
            bedrock-agentcore-starter-toolkit

# whichever agent framework you already use
pip install strands-agents

aws sts get-caller-identity        # prove credentials work
aws bedrock list-foundation-models \
    --region us-east-1 | head       # prove model access works

Do not skip the second command. "Access denied" on a model you never enabled is the failure that looks like a code bug for an hour.

If you are running this as a workshop, have people do step 0 before the session. Model access approval is occasionally not instant.
Steps 1 & 2

Write the agent, then run it on your laptop — no AWS involved yet

Step 1 · main.py — the entire runtime contract
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from strands import Agent

app = BedrockAgentCoreApp()
agent = Agent(system_prompt="You screen candidates against a requisition.")

@app.entrypoint
def invoke(payload, context):
    """payload is your JSON body; context.session_id is the conversation."""
    result = agent(payload["prompt"])
    return {"result": result.message}

if __name__ == "__main__":
    app.run(port=8080)          # HTTP protocol -> port 8080

Swap Agent for a LangGraph graph, a CrewAI crew or your own loop — the four lines around it do not change.

Step 2 · prove it before you deploy it
python main.py &

curl -s localhost:8080/invocations \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Screen E1002 against J2001"}'
Why this step is not optional

Everything above if __name__ == "__main__": is identical locally and deployed. Nothing in your agent knows which world it is in. So every bug you can reproduce locally is a bug you should never debug through a deployed runtime — where the same failure costs a two-minute deploy cycle and arrives as a timeout.

The local-first discipline is the single biggest productivity difference between teams. Keep the local path working forever, not just during week one.
Steps 3 & 4

Configure, launch, invoke — the three commands

Step 3 · deploy
# writes .bedrock_agentcore.yaml — read it, it is short
agentcore configure --entrypoint main.py

# builds the ARM64 image, pushes to ECR, creates the runtime
agentcore launch

agentcore status        # ARN, endpoint, readiness

If launch succeeds but invoke times out, go straight to the protocol/port table. It is that, roughly nine times in ten.

Step 4 · call it, with a session id that validates
import re

SESSION_RE = re.compile(r"^[a-zA-Z0-9][a-zA-Z0-9_-]{32,255}$")

def safe_session_id(candidate: str) -> str:
    """A session id AgentCore accepts, derived from the one you meant."""
    candidate = (candidate or "").strip()
    if SESSION_RE.match(candidate):
        return candidate
    base = re.sub(r"[^a-zA-Z0-9_-]", "-", candidate) or "session"
    if not base[0].isalnum():
        base = f"s{base}"
    return f"{base}-{'0' * 33}"[:64]     # J2001 -> J2001-00…0

Do not reach for uuid4(). The session id is what stitches multiple runtimes into one trace. A random value per hop gives you N traces that share nothing. Derive it from a business key — a requisition, a ticket, a chat thread — and pad it deterministically.

The 33-character minimum applies to InvokeAgentRuntime and to GetAgentCard. People discover it twice.
Steps 5 & 6

Now add the two capabilities that change the product, not the plumbing

Step 5

Memory — make it remember

Create a memory resource, choose your long-term strategies and retention, then swap your framework's session manager for AgentCore's. The agent code does not change.

from bedrock_agentcore.memory.integrations.strands.session_manager \
    import AgentCoreMemorySessionManager

with AgentCoreMemorySessionManager(config) as sessions:
    agent = Agent(session_manager=sessions, ...)
    result = agent(payload["prompt"])

Decide three things first: actorId (the recruiter), sessionId (the requisition), and which of the four strategies you actually want running.

Step 6

Gateway — give it tools it does not own

Create a gateway, add one target per backing system, and point the agent at the gateway's single MCP URL. Your Lambda now answers tools/call.

def lambda_handler(event, context):
    # tools arrive namespaced: target___toolname
    raw = context.client_context.custom["bedrockAgentCoreToolName"]
    return DISPATCH[raw.split("___", 1)[-1]](**event)

Write the tool descriptions for the model, not for a code reviewer — they are the selection criteria. Turn on semantic search before you pass ~50 tools.

Steps 5 and 6 are where the demo stops being a demo. Everything before this is a hosted chatbot; memory and real tools are what make it a system.
Steps 7 & 8

Then close the two things you cannot retrofit cheaply

Step 7

Identity — decide who may call, and as whom it acts

  • Humans in → a JWT authorizer pointing at your OIDC discovery URL (Cognito, Entra, Okta)
  • Machines in → SigV4 with the calling role; no authorizer needed
  • Out, as the company → 2LO client credentials for system data
  • Out, as the user → 3LO consent flow; the vault stores and refreshes the tokens
  • User context crosses inward in the payload or an allow-listed header, never as a forwarded token
Step 8

Observability — day one, not day ninety

  • Add aws-opentelemetry-distro>=0.18.0
  • Start the process under opentelemetry-instrument for model and tool spans, not just transport
  • Enable Transaction Search in CloudWatch
  • Propagate the session id on every outbound hop
  • Dashboard latency p50/p90/p99, error rate, token spend and active sessions before your first real user

Why these two are grouped: both are invisible while you are the only user, and both are painful to add once you are not. They are the "before the pilot, not after" pair — and step 10 cannot happen without step 8.

The OTel distro is heavy and contributes to the 30-second cold-start problem. That tension is real: instrument first, then prune instrumentations you do not need, rather than skipping instrumentation to make the deploy fast.
Step 9

Put a rule in front of every consequential tool call

  • Inventory the damage first. List every tool that moves money, changes a record, or reads regulated data. Those are the ones that need policies; the rest can wait.
  • Write permits for business logic, forbids for safety. A forbid is a hard boundary no model output can argue with — spend them on the things that must never happen.
  • Start in LOG_ONLY. Evaluate everything, block nothing, and read the ALLOW/DENY traces for at least one full business cycle.
  • Then switch to ENFORCE — and expect the first week to surface a legitimate workflow you forgot.
  • Commit the policies to git. PR review and CI validation, same as code.
The shape of a Cedar rule
permit (
    principal,
    action == Action::"invoke_tool",
    resource == Tool::"refund"
)
when { context.amount <= 500 };

forbid (
    principal,
    action == Action::"invoke_tool",
    resource == Tool::"cancel_appointment"
)
unless { principal.role == "doctor" };
Two roles, never merged

The gateway execution role gets minimum permissions to evaluate policies at runtime. A separate management role gets policy CRUD. If one principal can both write the rules and be judged by them, you do not have a control.

NL2Cedar can draft these from plain English — useful for a first pass, but review the generated policy the way you would review generated SQL. The Cedar syntax above is illustrative shape, not copy-paste; check the current schema for your entity names.
Step 10

Replace "it seemed fine" with a number you can trend

10a

Start on-demand, in dev

Pick sessions you already understand — one clean success, one known failure — and score them. If the evaluator disagrees with you about the failure, fix the evaluator before you trust it on anything else.

10b

Match the metric to the level

Tool accuracy at the span. Correctness, faithfulness and safety at the trace. Goal success rate at the session — that last one is what you report to the business.

10c

Then sample production online

10% with conditional filters is a sane start. Aggregate into a dashboard and watch the trend across prompt changes and model swaps — that is the whole point.

The workflow this unlocks

Change a prompt → run the same evaluators over the same sessions → compare. That is a regression test for a system you cannot assert equality on, and it is the only honest way to answer "is the new model better for us?"

Built-ins first

Thirteen evaluators cover most of what teams write by hand. Add an LLM-as-a-judge only for genuinely domain-specific quality, and a Lambda evaluator when the check is deterministic — format, exact match, a business rule.

10a is the step teams skip and regret. An evaluator you have not sanity-checked against a known-bad session is a number that makes you confident rather than correct.
Step 11

Then delete the CLI from your deployment path

The agentcore CLI is the right tool for the first week and the wrong tool for the first production incident. Once the shape is settled, the runtime, the gateway, the memory, the policies and every IAM role become reviewable code.

resource "aws_bedrockagentcore_agent_runtime" "screening" {
  agent_runtime_name = "talent_screening"
  role_arn           = aws_iam_role.screening.arn

  protocol_configuration { server_protocol = "HTTP" }   # HTTP | MCP | A2A

  agent_runtime_artifact {
    code_configuration {                                # no Docker involved
      entry_point = ["main.py"]
      runtime     = "PYTHON_3_13"
      code { s3 { bucket = var.artifacts, prefix = "talent_screening-${local.hash}.zip" } }
    }
    # or, when you need system packages or a non-Python runtime:
    # container_configuration { container_uri = "${var.account}.dkr.ecr...:v1" }
  }
}
Start with the zip

Move to ECR only when you genuinely need system packages. But build wheels for the container's CPU — it is ARM64 Graviton, not your laptop: --python-platform aarch64-manylinux2014 --only-binary=:all:. Without the second flag a package with no arm64 wheel compiles from source for the wrong architecture, quietly.

Keep the hash in the artifact name

Content-addressed zip names are what make "did my code actually deploy?" answerable. Without them you will spend an afternoon debugging a runtime that is still serving last Tuesday.

If the audience is a platform team, this is their slide. Note that IaC coverage has lagged the console at times — check the provider version supports the resource you need before promising a delivery date.

Part 3 · field notes

The ones that cost a day each

Deploy succeeds, nothing answers

Wrong port for the protocol. A2A is 9000, MCP is 8000, HTTP and AGUI are 8080. The symptom is a timeout, never a message.

HTTP 424 at launch

The container missed its 30-second health check. Usually a heavy dependency tree or the OTel auto-instrumentor walking ~45 instrumentations before your server binds.

ValidationException on a good id

runtimeSessionId needs 33+ characters. J2001 is rejected — pad it deterministically rather than randomising it.

Tool dispatch silently misses

Gateway namespaces tool names with a multi-underscore prefix. Print the raw value once and split on what you actually receive.

Five traces instead of one

The session id was not propagated on an outbound hop. Everything looks healthy; only the trace view shows the damage.

Long-term memory "loses" data

Extraction is asynchronous. Querying immediately after writing an event returns nothing, and that is the design, not a fault.

Wheels built for your Mac

The runtime is ARM64 Graviton. Zips need --python-platform aarch64-manylinux2014 --only-binary=:all:, or a package compiles for the wrong architecture without complaining.

Policy blocks everything

Default deny is the design. A new gateway with no matching permit refuses every tool — which looks exactly like a broken agent until you read the trace.

A served agent with no bound loop

A script has a call site where you can cap turns. A served agent does not — bound it with a before-tool-call hook or a runaway loop becomes a bill.

Patterns first, then three worked examples — and the shapes where it is the wrong answer.

Shift from technical to applied. If executives joined late, this is the section they need.
Part 4 · patterns

Almost everything that fits is one of four shapes

Shape 1

Long-running assistant

A conversation with a person that spans hours or days and must remember. Support, advisory, onboarding, case management.

Needs: Runtime, Memory, Identity

Shape 2

Supervisor + specialists

One front door delegating to focused agents owned by different teams, each deployed independently.

Needs: Runtime (A2A), Observability

Shape 3

Tool-heavy operator

The intelligence is small; the integration surface is large. Dozens of internal APIs the agent must reach safely.

Needs: Gateway, Identity, Policy

Shape 4

Legacy bridge

The system of record has no API and never will. The agent drives the UI a human would drive.

Needs: Browser, Observability

Diagnostic question: if you cannot say which of these four your project is, the project is not scoped yet — and adopting a platform will not fix that.

Ask the room to classify their own project out loud. It takes two minutes and it usually surfaces one project that is really shape 3 wearing shape 1's clothes.
Part 4 · the catalogue

Where these shapes show up

Customer support triage

Reads the ticket, pulls order and account history, drafts a resolution, escalates with a written rationale. Shape 1 + 3.

HR candidate screening

Scores candidates against a requisition, explains every rejection, schedules the survivors. Shape 2.

Financial ops reconciliation

Matches statements to ledgers, computes variances in a sandbox, writes an exception report a human signs. Shape 3 + Code Interpreter.

Insurance claim handling

Reads documents, checks policy terms, requests missing evidence — with a Cedar ceiling on what it may approve unaided. Shape 1 + Policy.

Healthcare scheduling

Books and reschedules within business hours only, and only clinicians may cancel — enforced outside the model. Shape 3 + Policy.

Developer productivity

Triages failing builds, reads the diff and the logs, proposes a fix and opens the PR. Episodic memory learns which fixes actually worked. Shape 3.

Supply-chain exceptions

Watches shipments, calls carrier APIs, and drives the supplier portal that has no API. Shape 4.

Sales revenue desk

Assembles account context from CRM, ERP and email, then acts on the rep's behalf via 3LO into SaaS. Shape 3 + Identity.

IT service desk

Resets access, provisions accounts, files the change record — every action attributable to the requesting human. Shape 3 + Identity + Policy.

Pick the two closest to the audience's business and skip the rest. Reading all nine aloud is how you lose the room in the final third.

Why A2A, not one big agent

Three teams own three agents and ship independently. One ARN each, one card each, no shared deploy.

Why the scorer is MCP, not Gateway

It already speaks MCP. Gateway is for things that cannot — putting it there would add a hop and buy nothing.

Part 4 · worked example

Support triage — the one most companies should build first

What happens in one session

  • A ticket arrives; the session id is the ticket id, so every later message joins the same conversation
  • Gateway exposes order lookup, entitlement check and refund initiation — three existing Lambdas, zero new services
  • Memory recalls that this customer has contacted you twice this month, without re-reading both transcripts
  • Policy caps the refund tool at $500, so the worst case is bounded by a rule rather than a prompt
  • The agent drafts a resolution and either sends it or escalates with its reasoning attached
  • Online evaluation samples 10% of sessions for goal success rate and safety, so a regression shows up as a trend

Why it is a good first project

The tools already exist as APIs, the value is measurable in handle time, and a wrong answer is recoverable — a human is in the loop by design.

Where teams get it wrong

Letting the agent take irreversible actions — issuing the refund rather than proposing it — in the first release. Earn that with a month of traces showing what it would have done.

Capabilities used: Runtime, Gateway, Memory, Identity, Observability, Policy, Evaluations. Seven of nine, and no Browser or Code Interpreter anywhere.

"Propose, do not perform" is the single best piece of rollout advice for any agent that touches money or customer records. Traces from the shadow period become the business case for the next release — and Policy is what makes "perform" survivable when you get there.
Part 4 · worked example

The legacy bridge — when the answer really is a browser

The situation

A supplier portal holds delivery commitments. There is no API, there will not be one this year, and the integration currently runs on a person with a spreadsheet and a login.

The build

  • Browser drives the portal, in VPC mode if the portal is internal, with live view for when it stalls
  • Identity holds the portal credentials, so no secret lives in the agent
  • Code Interpreter reconciles the scraped table against the ERP extract
  • Session replay keeps the recording — which is what makes it auditable rather than merely automated
The trade you are making

Browser automation is the most brittle integration you can build. The portal will redesign its login page and your agent will fail on a Tuesday. Accept that cost knowingly — and re-open the API conversation every six months.

The test that decides it

Ask: "If this vendor shipped an API tomorrow, would we throw this away?" If yes, build it anyway — and write it so throwing it away is one module, not the whole system.

Why AgentCore rather than your own Playwright fleet

You get the session lifecycle, the isolation, the live view and the replay without running headless Chrome on infrastructure someone has to patch.

This is the use case that most often makes a skeptical operations audience lean forward, because they have a person doing it today and they know exactly what it costs. Mention the CAPTCHA rule here: use a search tool for search, Browser for specific actions, and a human for the CAPTCHA.
Part 4 · the other list

Four projects that should not be AgentCore

The nightly batch

No session, no user, no conversation. That is a container on a schedule, and it will cost less and fail more legibly.

The single prompt

One model call with no tools and no memory does not need a platform. Call the model from whatever already serves your traffic.

The latency-critical path

If the budget is tens of milliseconds and the caller is a page render, this is the wrong layer entirely.

The portability mandate

If a contract requires the same system to run on another cloud, adopt Runtime at most and keep every other capability behind your own interface.

The pattern in all four: AgentCore earns its keep when there is a session — something with an identity, a lifetime and a memory. Take the session away and most of the value goes with it.

Saying "do not use it for X" from an AWS-adjacent deck buys credibility for everything else you claimed. Do not cut this slide for time.

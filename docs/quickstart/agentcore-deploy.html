AgentCore: Deployment Prerequisites

Reference 8 stages 9 IAM roles terraform

Deploying the AgentCore stack means eight terraform apply runs, in order, each consuming an earlier one's outputs. This page answers the three questions that block them: what must already exist, what each stage creates for AWS services to assume, and what the identity running the apply needs to be allowed to do.

Every module below opens with the same five lines — what it depends on, what it consumes, what must be built first, what you must decide, and what it unblocks — followed by the standalone apply that wires those outputs in, the roles it creates, and every deployer permission with the reason it is needed.

🔑 The distinction this page is built around

The roles the stack creates are not the permissions you need to run it. A Lambda execution role and the engineer typing terraform apply are different principals, and conflating them is why “but the runtime has admin” never helps. Every stage below lists both, separately.

Before anything

Local toolchain

ToolWhy
terraformResolves hashicorp/aws >= 6.58 and hashicorp/time. Run terraform init per directory, or once in 00_all_at_once.
aws cliTerraform does not need it; every verification step on this page is a CLI call. aws sts get-caller-identity should print your ARN.
uvInstalls Python 3.13. The zips target PYTHON_3_13 on arm64 — building on the same minor version the container runs avoids a class of wheel mismatch.
node + npmThe chat proxy is Node because Lambda response streaming exists on Node.js managed runtimes only. The UI is a Vite build.
⚠️ Behind a TLS-inspecting proxy

uv needs UV_SYSTEM_CERTS=1 (or uv sync --system-certs), otherwise installs fail with invalid peer certificate: UnknownIssuer.

Build the artifacts first — before plan, not before apply

Four stages read files with filemd5() or filebase64sha256(), and those are evaluated at plan time. A missing zip is not a slow apply; it is a plan that refuses to produce a diff at all.

terminal
make artifacts              # package + seed + ui-build, all at once

# or individually
uv run scripts/package.py   # dist/*.zip   -> stages 02, 05, 07
uv run scripts/seed_s3.py   # seed/*.json  -> stage 01
make ui-build               # ui/dist/     -> stage 08

Account and region

One region for the whole stack — Runtime, Gateway and Memory must share it, and the Cognito discovery URL is built from it. Two values have no safe default and must be supplied: bedrock_model_id (model ids are account- and region-specific; this stack ships us.amazon.nova-lite-v1:0) and password for the Cognito machine user, minimum 8 characters and marked sensitive.

⚠️ Anthropic models need a form first

Anthropic models on Bedrock require a use-case submission approved per account. Until then every call fails with ResourceNotFoundException: Model use case details have not been submitted for this account — which names neither the model nor the agent that asked for it. Amazon's own models have no such gate, which is why the default here is Nova.

Dependency order

The number is the order. Two stages are roots and could run first, or in parallel; every other stage consumes an earlier one's terraform output.

Roots 01 s3_data — nothing 04 memory — nothing
Then 02 lambda ← 01 03 gateway ← 02
Then 05 runtimes ← 01, 03, 04 06 observability ← 03, 04
Last 07 api ← 03, 05 08 ui ← 07
📘 06 does not depend on 05

Its number reads as “after the runtimes”, but it needs only the gateway and memory ARNs. There is an argument for applying it earlier: the X-Ray trace destination is account-level, so setting it after the runtimes exist loses the first container's start-up traces.

📘 Applying standalone, or all at once

The numbered directories are also modules of terraform/00_all_at_once, where the wiring is done for you and make deploy is the whole thing in one apply. The per-stage commands below are the standalone path — the same modules, with the outputs passed by hand. They declare no provider block of their own, so set the region in the environment: export AWS_REGION=us-west-2.

03 · gateway

Identity and the AgentCore Gateway with one target — the widest output surface in the stack.

Depends on
02, applied.
Consumes
lambda_arn — the single target the gateway role is allowed to invoke.
Providers
hashicorp/aws >= 6.58 and hashicorp/time >= 0.9. A fresh terraform init here downloads two, not one.
You supply
password for the Cognito machine user — minimum 8 characters, in a *.tfvars named anything except example.tfvars, which the root .gitignore deliberately un-ignores.
You decide
gateway_authorizer_type, before the first apply and permanently. Then restrict_trust_to_gateway (false on the first pass) and iam_propagation_delay.
Unblocks
05, 06 and 07 — the widest output surface in the stack.
terminal
cd terraform/03_gateway && terraform init && terraform apply \
  -var lambda_arn=$(terraform -chdir=../02_lambda output -raw lambda_arn) \
  -var-file=dev.tfvars                        # holds `password` — never example.tfvars

# then, once the gateway exists, harden the trust policy:
terraform apply -var lambda_arn=... -var-file=dev.tfvars -var restrict_trust_to_gateway=true
🛑 authorizer_type is immutable

It cannot be changed in place. Switching it replaces the gateway and every target under it, and the replacement has a new gateway_url — which then propagates into stage 05.

Role createdTrusted byPermissions
<gateway_name>-rolebedrock-agentcore.amazonaws.com, optionally conditioned on aws:SourceAccount / aws:SourceArnlambda:InvokeFunction — the one target

Also created, and not roles: a Cognito user pool, an app client (ALLOW_USER_PASSWORD_AUTH, ALLOW_REFRESH_TOKEN_AUTH, no secret) and one user with a permanent password. Without the user, the stack deploys and nothing is callable.

⚠️ Two things that need a second apply, or patience

restrict_trust_to_gateway = true adds aws:SourceArn to the trust policy — but that ARN does not exist until the gateway does, so apply once with false and then flip it. Separately, a time_sleep sits between the role and the gateway because IAM is eventually consistent; ValidationException: Gateway service is not authorized to perform AssumeRole means the policy is correct and has not propagated. Raise iam_propagation_delay.

No required variables. Both region and env default.
Build first
Nothing.
You decide
Nothing.
Unblocks
05 with memory_id, which the supervisor reads as an environment variable, and 06 with memory_arn.
terminal
cd terraform/04_memory && terraform init && terraform apply
Role createdTrusted byPermissions
hr-memory-rolebedrock-agentcore.amazonaws.commanaged: AmazonBedrockAgentCoreMemory​BedrockModelInferenceExecutionRolePolicy

Extraction runs a model over your conversation to derive facts, so the service needs inference permissions of its own — they are not borrowed from the runtime that wrote the event.

⚠️ Strategy names take no hyphens

Attribute name value must match '^[a-zA-Z][a-zA-Z0-9_]{0,47}$' — so candidate_facts, never candidate-facts.

⚠️ An account prerequisite this stage does not name

None of the three strategies names a model, so AgentCore uses its own default — an Anthropic one. In an account without that access the memory is created, events land, and extraction fails asynchronously with ResourceNotFoundException: Model use case details have not been submitted, from a component nobody is watching, long after the agent answered. Pinning a different model is not one line: configuration.extraction requires both model_id and append_to_prompt, so overriding it means replacing AWS's tuned extraction prompt with your own.

Permissions the deployer needs, and what each one is for

ActionWhat it does in this stage
iam:CreateRolehr-memory-role, trusted by bedrock-agentcore.amazonaws.com.
iam:AttachRolePolicyThe managed inference policy. Extraction is a model call the service makes on its own schedule, not one your runtime makes, so the permission has to live on this role — without it the memory exists, events land, and no memory record is ever produced.
iam:PassRoleCreateMemory takes the role as memory_execution_role_arn.
bedrock-agentcore:CreateMemoryhr_hiring_desk, with a 90-day event expiry.

🛑 Three separate actions, one conversation

InvokeAgentRuntime sends the message. GetAgentCard fetches the card, and runs first — grant only the former and every delegation dies at discovery with a 403 that reads like the remote agent is down. InvokeGateway is a third action again, and follows from neither.

📘 IAM is the entire check between services

Only the supervisor has an authorizer (CUSTOM_JWT, because a person is on the other side of its door). The other four take SigV4 with their execution role, so there is no second lock behind the policy above.

Permissions the deployer needs, and what each one is for

ActionWhat it does in this stage

iam:CreateRole ×5agentcore-<name>-role, one per runtime. One shared role would erase the call graph in the table above — the separation is the security model here.

iam:PassRoleCreateAgentRuntime hands each of the five roles to the service.
bedrock-agentcore:CreateAgentRuntimeThe five runtimes, in three dependency tiers terraform resolves within one apply.

bedrock-agentcore:GetAgentRuntime

📘 What the deployer does not need

bedrock:InvokeModel is all over this stage and appears nowhere on your own identity. It is granted to the five execution roles, and the model is called by the containers, never by terraform. Adding it to the principal running the apply does nothing for a runtime that lacks it — and removing it from yours breaks nothing at deploy time. The same holds for bedrock-agentcore:InvokeAgentRuntime: creating the runtimes and talking to them are different permissions on different principals.

📘 Two things this stage deliberately does not create

No endpoint resources — CreateAgentRuntime makes DEFAULT itself, so declaring one is a ConflictException on every apply. No log groups — their names contain a service-generated runtime id, so they cannot exist before the runtime does; the container creates its own.

🛑 Account-wide, and destroy turns it off

enable_transaction_search is not scoped to this stack. Enabling it affects every trace in the account and region, and terraform destroy disables it again — including for anything else relying on it.

08 · ui

The React build on CloudFront, with stage 07 as its /api/* origin — which is what removes CORS entirely.

Depends on
07, applied. The last stage.
Consumes
api_domain — the bare execute-api host, no scheme and no path — and api_stage, which becomes CloudFront's origin_path so the browser never sees it.
Build first
make ui-build → ui/dist/. fileset() and filemd5() run at plan time, and a missing directory fails with call to function fileset failed — which does not sound like “you forgot to build the UI”.
You decide
price_class, and origin_read_timeout — 60 is the maximum without a quota increase, and the supervisor regularly goes quiet for longer than the 30-second default.
Unblocks
Nothing. The chat_url output is the thing you open.
terminal

cd terraform/08_ui && terraform init && terraform apply \
  -var api_domain=$(terraform -chdir=../07_api output -raw api_domain) \
  -var api_stage=$(terraform -chdir=../07_api output -raw api_stage)

terraform output -raw chat_url

Creates: no IAM roles — but a bucket policy that does the same job, granting s3:GetObject to cloudfront.amazonaws.com, conditioned on this distribution alone.

📘 Only S3 gets an origin access control

CloudFront OAC has no apigateway origin type, so execute-api stays publicly resolvable and the Cognito authorizer is the gate — not network placement. That is also why the stage carries a throttle.

⚠️ The one people miss: iam:PassRole

Creating a role is not the same as being allowed to hand it to a service. Five stages create a role and immediately give it to Lambda, API Gateway or AgentCore, and without PassRole each fails at the second step with a message about the service rather than about you.

📘 How precise are these lists?

Everything about the roles the stack creates is exact — read straight from the policy documents in the terraform. The deployer tables, actions and purposes alike, are derived from the resource types and arguments each module declares: right in shape, and complete for the resources listed, but confirm against your own identity with the simulator below before assuming a gap is a bug in the stack. Tagging is the usual quiet extra — every resource here carries tags, so a permission boundary that allows Create* but not TagResource fails on resources you have already been allowed to make.

Verifying, before and after

Does this principal have the action?

The fastest way to settle any permission question, and it modifies nothing. It distinguishes allowed from implicitDeny, which is what a missing action looks like.

terminal
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::<account>:role/agentcore-hiring_supervisor-role \
  --action-names bedrock-agentcore:InvokeAgentRuntime bedrock-agentcore:GetAgentCard \
  --resource-arns <the callee's runtime arn> \
  --query 'EvaluationResults[].{action:EvalActionName,decision:EvalDecision}' --output table

Does the chain hold?

terraform validate checks one directory in isolation, so a stack where 06 needs gateway_arn and 03 never exports it validates cleanly and then cannot apply. This is that audit, plus the IAM and documentation invariants on this page.

terminal
uv run scripts/check_terraform_chain.py

Is the Gateway reachable, with no agent in the way?

Signs with your own credentials and lists what the Gateway publishes. Needs bedrock-agentcore:InvokeGateway on your identity — the grant in stage 05 belongs to the screening runtime, a different principal.

terminal
make gateway                                        # list the tools
make gateway CALL=hrdata___get_requisition ARGS='{"job_id":"J2001"}'
⚠️ MCP Inspector will not work here

It sends a bearer token and cannot sign SigV4, so it is usable only if you set gateway_authorizer_type = "CUSTOM_JWT".

Did the code actually ship?

Artifact keys are content-addressed, so new bytes mean a new S3 key, a new object and a new runtime version. A version that never moves is the one symptom of a deploy that silently changed nothing.

terminal
aws bedrock-agentcore-control get-agent-runtime \
  --agent-runtime-id <id> \
  --query '{version:agentRuntimeVersion,prefix:agentRuntimeArtifact.codeConfiguration.code.s3.prefix}'

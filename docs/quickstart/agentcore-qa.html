AgentCore, Question by Question

Q&A tutorial decision-level no code required ~35 min

The AgentCore Tutorial answers how. This one answers the questions that come before anyone writes a line of it: how is this different from Bedrock Agents, what would I have to build myself without it, what does adopting it actually cost me, and how do I explain the decision to the person who signs off on it.

It is written as a dialogue between a developer with prototypes that work and a production deadline that does not, and an architect who has done this before.

📎 Where this comes from

This tutorial follows the shape and question list of “Mastering Amazon Bedrock AgentCore: An Expert-to-Developer Dialogue” by DataTechBridge on Medium. The questions are theirs. The answers here are rewritten in this course's voice, illustrated with the HR recruiting system the rest of the course uses, and cross-checked against the working implementation in agent-core/. Where the original makes a claim that is directional rather than measurable — timelines, cost savings, roadmap — it is labelled as the source's claim rather than repeated as fact.

The example behind every answer

Whenever an answer needs something concrete, it uses the course's HR recruiting desk: employees have skills rated 1–5, requisitions require skills at a minimum level, and some of those are mandatory. A candidate below a mandatory bar is blocked — no score saves them. Four agents fill requisition J2001: a supervisor, a screener, an outreach writer and a compliance reviewer. It runs on a laptop and it runs on AgentCore; the tutorial is the deployed version.

1. What is it, and why does it exist?

DeveloperWhat is Amazon Bedrock AgentCore, in one sentence?
Architect

A suite of services for running AI agents in production — not for building them. It gives an agent you already wrote a place to run, a way to reach tools, memory, an identity story and traces.

The single most important word is agnostic: it does not care which framework you used or which model you call. Strands, LangChain, LangGraph, CrewAI, plain Python — and a model from Bedrock, or one that is not on Bedrock at all.

DeveloperBedrock already lets me build agents. Why would I need this as well?
Architect

Because they answer different questions. Bedrock Agents is a managed way to define an agent inside the Bedrock ecosystem — you describe it and AWS runs the loop. AgentCore assumes the agent already exists, written however you like, and takes over everything around it.

The test is simple: if the framework and the model are decisions you want to keep making yourself, you want AgentCore.

The line between them

Bedrock Agents: AWS defines how the agent thinks. AgentCore: you do, and AWS runs it.

DeveloperI have a LangChain agent calling a non-Bedrock model. Can I deploy that?
Architect

Not as a Bedrock Agent — that path expects you to work inside its ecosystem. Yes with AgentCore Runtime, which takes your code as a container image in Amazon ECR (or, for a plain Python service, a zip in S3) and runs it as-is.

Runtime's contract is not "use our framework". It is much smaller than that: listen on the right port at the right path. What happens inside the process is entirely yours.

2. What are the components?

DeveloperBreak it down for me. What am I actually buying?
Architect

Six services, and you adopt them one at a time rather than all at once:

ComponentWhat it doesThe question it answers
RuntimeServerless host for your agent, whatever it is written in“Where does this run when it is not my laptop?”
GatewayTurns APIs and Lambda functions into MCP-compatible tools“How does my agent reach the systems we already have?”
MemoryManaged short-term and long-term conversation context“Why does it forget everything between sessions?”
IdentityAuth in both directions, with Okta / Entra / Cognito“Who is allowed to ask, and what may it reach?”
ToolsCode Interpreter and Browser, both sandboxed“How does it run code or use a website safely?”
ObservabilityDashboards and traces, OpenTelemetry-compatible“What did it actually do at 2am?”
Six or seven? Both counts are right

The source article counts six, grouping Code Interpreter and Browser together as “Tools”. Our tutorial counts seven by listing them separately, because they have very different risk profiles — one runs your code, the other drives someone else's website. Same platform, different bracketing. Do not let a count in a slide deck confuse you.

3. Runtime

DeveloperHow does Runtime actually work? What do I hand it?
Architect

You package the agent as a container, push it to ECR, and point a runtime at it. AWS handles scaling, networking and the security boundary. You get an ARN and an endpoint back.

Two details people miss on day one:

  • You do not need Docker for a plain Python agent. A zip in S3 with an entry point works too, and it removes a registry, an image-scanning story and a build step from the project. Move to a container image when you need a system package.
  • The protocol decides the port. An HTTP agent listens on 8080 at /invocations, an MCP tool server on 8000 at /mcp, an A2A agent on 9000 at /. Bind the wrong one and the deploy succeeds, the health check fails, and what you see is a timeout.
DeveloperMy prototype serves a handful of users. How hard is it to get to thousands?
Architect

From Runtime's side, nothing: it scales out on demand and back down when the demand goes away, with no code change.

What actually breaks at a thousand users is rarely the compute. It is model throughput quotas, the downstream systems your tools call, and cost per conversation. Runtime removes one of those four problems, and it is the easiest one.

Worth saying out loud

“Serverless scaling” is not the same as “this will work at scale”. Load-test the tools, not the agent.

One thing per session, and it is not free

Runtime isolates each session — its own microVM, its own memory and file system, so two conversations cannot leak into each other. The cost of that isolation is a cold start per new session id, so key the session to a business object (a requisition, a ticket, a chat thread) rather than minting a new one per request. In our HR system the session id is the requisition id, which is also what makes five runtimes produce one trace.

4. Memory

DeveloperMy agent forgets everything. Does Memory just fix that?
Architect

It fixes two different problems that are usually confused with each other:

  • Short-term is the event log for the conversation in progress — what makes a chat survive a restart.
  • Long-term is what gets extracted from those events afterwards and retrieved later by relevance: facts, preferences, summaries.

The part that saves you real work is the retrieval: it pulls back what is relevant rather than everything, so you are not hand-rolling a context-window budget and a truncation strategy for the fourth time.

DeveloperHow much work is it to put into an agent that already has its own memory?
Architect

Small — a session manager and a config object, and your existing memory code comes out. The hard part is not the API.

The hard part is choosing the two keys, and getting them wrong looks like a model problem for weeks:

the decision, not the code
actor_id   = "recruiter-nk"   # WHO is working
session_id = "J2001"          # WHAT they are working on

Use a fresh UUID per conversation and the system forgets J2001 between Tuesday and Thursday. Use actor_id="agent" and the whole recruiting team shares one preference profile. The session id is a business key, not plumbing.

DeveloperOur security team will ask about the data. What do I tell them?
Architect

Encrypted at rest and in transit, you keep control of where it lives, access is governed by the same identity layer as everything else, and the access events are logged — which is the part a GDPR or HIPAA conversation actually turns on.

Then tell them the thing the platform cannot help with: a conversation log is now a data retention decision. Someone has to own the expiry period, and it should not be the person who wrote the agent.

Extraction is asynchronous — which is why a demo that writes a memory and immediately reads it back looks broken.
The failure mode nobody warns you about

A summarisation strategy will happily turn “blocked on Apache Spark” into “some gaps”. Next week that sentence is what your agent reads, and a warm note goes to a candidate who cannot do the job. Read memory for context; re-derive verdicts from the source of truth. Never the other way round.

5. Gateway and MCP

DeveloperWhat is MCP and why does everyone keep mentioning it?
Architect

An open standard for how models, agents and tools talk to each other. Its value is boring and enormous: one interface instead of one integration per pair. A tool that speaks MCP can be consumed by any client that speaks MCP, including ones you did not write.

New to it? The FastMCP Quick Start builds a four-tool server for this exact HR domain in about twenty minutes.

DeveloperSo what does Gateway do that I cannot do myself?
Architect

It makes things that are not MCP servers behave like one: a Lambda function, an OpenAPI service, a Smithy model, an API Gateway stage. You register a target and its operations show up as tools, namespaced so two targets can export the same name without colliding.

Could you write that adapter yourself? Yes, and you would then own it forever.

The rule that keeps this clean

Put a thing behind the Gateway when it cannot speak MCP on its own. Anything that already speaks MCP should be called directly — otherwise you are paying an extra network hop on every call and maintaining its tool schema in two places.

DeveloperDo I have to rewrite my LangChain agent for MCP?
Architect

Mostly no. Frameworks are adding native MCP support, and where they have it the change is at the tool discovery and tool calling layer — an MCP client instead of a hand-written tool list. Your prompts, your routing logic and your business tools are untouched.

One thing does change, and it is worth planning for: tool names. Gateway-provided tools arrive prefixed by their target. If your system prompt names tools as strings, it will need editing — so name capabilities in prompts, not tool identifiers, and the prompt survives moving a tool from one side of the boundary to the other.

6. Code Interpreter and Browser

DeveloperWhat is Code Interpreter for, and what should I not use it for?
Architect

A sandbox where the agent runs code it wrote: isolated, resource-limited, state kept between executions, a file system it can read and write, and a large set of libraries already installed — pandas, matplotlib, requests and friends.

It earns its place on open-ended work: analysis, charts, format conversion, awkward calculations, throwaway scripts. “Plot the skill gap across all six open requisitions” is a good use — there is no fixed function to call, and writing one for every such question is how you end up with two hundred tools.

What it must never own

The arithmetic your business has to defend. In our system match() is forty lines of weighted scoring, and it stays a plain function in a tool server. A score you cannot reproduce by hand is a score nobody will defend in a hiring review.

DeveloperAnd the Browser tool — is that just scraping with extra steps?
Architect

It is a managed browser session the agent drives like a person would: navigate, click, fill a form, scroll, keep cookies and session state, take a screenshot, and reason about what is on screen rather than about raw HTML.

It exists because a large amount of enterprise software has a UI and no API you are allowed to use — half of HR tooling, most benefits portals, plenty of applicant tracking systems.

Reach for it last

It is the slowest, most brittle and most expensive way to read a fact, and it is the integration that breaks because someone else shipped a redesign. If an API exists, put it behind the Gateway and get typed tools instead.

What you needWhere it belongs
Arithmetic your business must defenda plain function in a tool server
An existing Lambda, API or OpenAPI servicea Gateway target
Open-ended analysis over data you just fetchedCode Interpreter
A system with a UI and no APIBrowser — and a note in the risk register

7. Identity

DeveloperWe already use Okta. Do we have to build a second login for the agent?
Architect

No — and if you find yourself doing that, stop. Identity handles both directions:

  • Inbound — who is talking to the agent, verified against the provider you already run: Okta, Microsoft Entra, Amazon Cognito.
  • Outbound — how the agent authenticates to everything it calls: OAuth, API keys, service accounts.
DeveloperDifferent people should be able to do different things. Is that modelled anywhere?
Architect

Yes — fine-grained policy on identity and role, and it applies to the agent and to every tool it can reach, which is the part that matters. A recruiter can screen candidates; a hiring manager can approve a shortlist; only HR ops sees compensation bands. The agent inherits those distinctions instead of re-inventing them.

The design rule underneath

Humans authenticate with your identity provider. Machines authenticate with IAM. An agent cannot carry a user's token inward forever — the platform consumes the inbound credential at its edge — so plan for service-to-service calls to be signed by execution roles, not by borrowed tokens.

DeveloperAudit says “show me who did what”. What do I have?
Architect

Identity and access events are logged with the detail an auditor asks for — identity, resource, action, timestamp, method — and they can be fed into the SIEM you already have. That is what makes SOC 2 / HIPAA / GDPR conversations tractable rather than theoretical.

Add one thing yourself: log the decision, not just the access. “Read employee record E1003” is an access event; “shortlisted E1003 for J2001 at 61%, blocked on Apache Spark” is what the review board will ask about.

8. Observability

DeveloperWhat do I actually get to see?
Architect
  • Dashboards: volume, latency, error rate, satisfaction signals.
  • Trace visualisation — the whole flow of one request: every tool call, every memory read, every step of the agent's reasoning.
  • Model metrics: token usage and cost, per interaction.
  • Error analysis grouped into categories rather than a wall of stack traces.

It is OpenTelemetry-compatible, so it lands in the tooling you already own rather than becoming a second place to look.

DeveloperHow does that make the agent better, rather than just monitored?
Architect

Because the traces tell you which of your assumptions were wrong. Concretely, from a real run of our hiring pipeline: the supervisor called the screening agent four times for one requisition. Nothing failed and no user complained — the answer was fine. The trace showed it, the token count priced it, and one prompt change removed three of the four calls.

You cannot make that fix from logs, because nothing in that story was an error.

9. What would I build without it?

DeveloperSuppose we do not adopt it. Where would I deploy an MCP server on AWS today?
Architect

EC2, ECS or EKS — and then the list nobody puts in the estimate: auto-scaling, load balancers, TLS, health checks, patching, multi-AZ, and a monitoring story. None of it is hard. All of it is yours forever.

DeveloperAnd for the LangChain agents themselves?
Architect

Three usual options, each with a catch that shows up late:

OptionFine forWhere it hurts
Lambda + API Gatewayshort, stateless callsexecution-time ceiling, memory limits, cold starts — and an agent turn is neither short nor stateless
ECS / EKSteams who already run containersorchestration expertise and operational overhead you now need on the AI team
EC2full controlyou own patching, scaling and availability for a workload whose traffic you cannot predict

And whichever you pick, the same five things still have to be built on top: memory, authentication, observability, scaling policy, and the security controls that let it near production data.

10. What does it cost, and what does it save?

DeveloperGive me the number I can put in a slide.
Architect

Here is the source article's estimate, and I want to be explicit that it is an estimate rather than a measurement:

Piece of workBuild it yourselfOn AgentCore
Deployment pipeline1–2 weekspackage + deploy: ~2 days
Vector store / memory2–3 weeks~1 day
Authentication3–4 weeks1–2 days
Monitoring and tracing2–3 weeksconfiguration
Each system integration2–4 weeks each1–2 days per system
Total3–4 months1–2 weeks
Read that table with your own project in mind

These are the source's figures and they are directional, not benchmarked — and they measure the part of the work that AgentCore replaces. In practice the schedule of an agent project is usually set by the things no platform removes: getting access to the data, agreeing what a correct answer is, evaluation, and the review that has to happen before it touches customers. Use the table to argue “do not build a log shipper”, not to promise a date.

DeveloperIs it cost-effective for something small?
Architect

It is pay-for-use, so a handful of requests a day costs very little and there is no upfront commitment — which is the honest advantage for a small team: you are not buying a cluster to find out whether the idea works.

The comparison that matters at any size is not "AgentCore versus nothing" — it is AgentCore versus the fully loaded cost of the equivalent you would run yourself, including the engineer who gets paged for it.

Do not budget from a blog post

Including this one. Pricing changes; check the current AWS pricing page for the components you intend to use, and model your own token spend separately — the model bill is usually the bigger line.

DeveloperWe already built some of this. Is it all-or-nothing?
Architect

No, and this is the most useful property of the whole platform: it is modular. Keep your own memory layer and adopt Gateway. Keep your own hosting and adopt Identity. Nothing requires you to move everything.

The usual first step for a team with existing infrastructure is Gateway, because it deletes the most hand-written glue for the least disruption.

11. What do people build with it?

Four shapes, and note that each one is a different combination — the components are rarely adopted alone:

Customer support

Memory for history across contacts · Gateway for the CRM · Browser to walk a customer through a page. The model can be whatever answers best.

Healthcare scheduling

Identity carries the access rules for patient data · Gateway reaches the scheduling system · Memory holds preferences. Identity is load-bearing, not decoration.

SRE assistant

Code Interpreter over logs and metrics · Gateway into monitoring tools · Observability to watch the watcher.

Self-service analytics

Code Interpreter for ad-hoc analysis · Memory for what was already asked · Identity so people only query what they may see.

And the one this course builds end to end

Hiring. Four agents fill requisition J2001: a supervisor takes the request, a screener ranks candidates against the record, an outreach agent drafts the note, a compliance reviewer checks it before it goes out. Runtime hosts all four · Gateway fronts the Lambda over the employee data · a direct MCP connection carries the scoring engine · Memory keys on the requisition · Identity puts Cognito at the door and IAM everywhere inside · one trace covers the lot. The tutorial builds it; the code is in agent-core/.

12. How do I start?

DeveloperMonday morning. What do I do first?
Architect

Not "read all the docs". Pick one thing that already half-works and put it somewhere real:

1

Pick a use case you already have

An existing prototype beats a new idea — you want to learn the platform, not the domain, this week.

2

Start with Runtime alone

Get the thing you have running behind an endpoint. Change nothing else. This is the step that proves the "agnostic" claim to your own satisfaction.

3

Add Gateway next

One target, one real internal system. This is where the value shows up fastest for teams with an existing estate.

4

Then Memory

And spend the thinking time on actor_id and session_id, not on the API.

5

Turn on Observability before you need it

Traces you did not enable are not available retroactively for the incident you are currently having.

6

Only then Identity, tools and the rest

Adopt in the order your risk requires, not the order the docs list them.

The cheaper version of every one of those steps

Every failure you will hit in AWS has a version on 127.0.0.1 that costs nothing to reproduce. This course's agent-core/ project runs the whole four-agent system locally on a local model, with the same code that deploys — so debug the pipeline in five terminals first, then move it. Steps 1–6 of the tutorial's verification ladder do not need an agent at all: prove the tools with a client that has no model in it.

13. Where is it going?

DeveloperAm I betting on something that will still be here in two years?
Architect

The direction the source article expects — more built-in tools, better multi-agent collaboration, deeper integration with the rest of AWS, richer observability, broader framework support, and enterprise governance features for running a lot of agents at once.

Treat all of that as expectation rather than commitment. The stronger argument for adopting it is structural, not roadmap-based: because it is framework- and model-agnostic, the parts you would be most upset to rewrite — your prompts, your tools, your agent logic — are exactly the parts it does not touch.

15. Check yourself

Your team has a working CrewAI agent calling a non-Bedrock model. Which is true?
Framework- and model-agnostic is the defining property. Runtime's contract is that your process listens on the right port at the right path; what happens inside is yours. That is also the strongest structural argument for adopting it: the parts you would hate to rewrite are the parts it does not touch.
You already run an MCP server for your internal tools. Should it go behind Gateway?
Gateway is a protocol adapter, not a router: put a thing behind it when it cannot speak MCP on its own. Routing an existing MCP server through it adds a permanent network hop to every call and a second copy of its tool schema to maintain — in exchange for merging two tool lists that your client merges for free.
The article estimates 3–4 months of build-your-own work becoming 1–2 weeks. How should you use that?
The figures are directional and they measure only the part a platform can replace. What actually sets an agent project's schedule is getting access to the data, agreeing what a correct answer looks like, evaluating it, and passing review. Use the table to stop someone building a log shipper — not to promise a date.

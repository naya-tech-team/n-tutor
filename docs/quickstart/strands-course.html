Strands Agents — Full Course Guide

Full Course 17 lessons runnable code ~3.5 hours

The Strands Quick Start gets you an agent in fifteen minutes. This guide is the whole course — seventeen lessons that take that agent from a toy to something you would put in front of users: tools it can't misuse, memory that survives a restart, budgets it can't blow through, and a human in the loop when it matters.

⬇️ Every lesson is runnable

The companion project lives in strands-ai/. Each lesson is a folder with a README.md (the write-up) and a main.py (the demo). Every output shown on this page came from an actual run against a local model — including the ones that go wrong.

One domain, seventeen lessons

Every example runs on the same small world: employees have rated skills, requisitions require skills, and something has to decide who fits. Twelve people, six open roles, a skill catalogue with aliases ("pyspark" → "Apache Spark") — all in app/_shared/hr_data.py, in memory, no database.

match(employee, job) returns a score, the skills that matched, the gaps, and any blockers — a missing mandatory skill. It is arithmetic, never a model call. The model's job is to find the right people to score, call the tool and explain the result — not to invent a percentage. A score nobody can reproduce by hand is a score nobody will defend in a hiring review.

Two employees worth memorising, because they show up on every page below: E1002 Priya Raman (Senior Data Engineer, Bengaluru, on the bench, Spark 5 / Python 4 / SQL 5) scores 100% on requisition J2001. 3. Choosing a model — read this first

⚠️ This one decision breaks more tutorials than any bug

Strands hands the model a list of tools and lets it decide. Everything depends on how well your model calls tools — and weak models fail in a specific, recognisable way: they print the tool call as text instead of making it.

One prompt — "We're filling J2001. Open it." — through lesson 17's desk agent, two local models, verbatim traces. The work is finished on the first tool call in both cases.

llama3.2 (3B) — done at cycle 1, then eight cycles of nothing
[1] open_requisition({"job_id": "J2001"})                          -> Now working J2001 …  ✅
[2] find_candidates({"job_id": "J2001", "location": "Bengaluru"})  -> ValidationError: skill required
[3] find_candidates({"job_title": "Senior Data Engineer", …})      -> ValidationError: skill required
[4] find_candidates({"job_title": "Senior Data Engineer"})         -> ValidationError: skill required
[5] find_candidates({"job_title": "Senior Data Engineer"})         -> ValidationError: skill required   <-- identical to [4]
[6] find_candidates({"location": "Bengaluru"})                     -> ValidationError: skill required
stop_reason: limit_turns   answer: ''
qwen2.5:7b — one call, one answer, stops
[1] open_requisition({"job_id": "J2001"})   -> Now working J2001 — Senior Data Engineer in Bengaluru, 6+ years.
stop_reason: end_turn   cycles: 2
answer: Job ID: J2001, Senior Data Engineer, Bengaluru

Look at cycle 5: it is byte-identical to cycle 4. That is the signature of a model that has run out of ideas — it has no new information after a bare validation error, so it reshuffles the same wrong guess until something stops it. Lesson 17 shows the two fixes (a tool that answers the call it actually received, and a turn cap that guarantees termination).

Override per run without editing a file — real environment variables beat .env:

terminal
OLLAMA_MODEL=qwen2.5:7b uv run app/00_tutorial/tutorial.py

If your agent starts describing tool calls instead of making them, that is a model problem, not a prompt problem. Reach for a bigger model before you rewrite anything.

4. The one diagram to memorize

Every feature in the rest of this course plugs into exactly one place in this loop. Learn it now and the other sixteen lessons become "where does this attach?"

flowchart TD
    S["agent(prompt)"] --> A["append user message"]
    A --> CM["conversation manager
trims / summarizes"]
    CM --> M["MODEL CALL
messages + tool specs + system prompt"]
    M --> SR{"stop_reason"}
    SR -->|"tool_use"| T["run the requested tools"]
    T --> AR["append toolResult messages"]
    AR --> CM
    SR -->|"end_turn / limit_* / max_tokens"| R["AgentResult"]
    SR -->|"interrupt"| P["pause and return"]
One cycle = one model call + the tools it asked for. Repeat until the model stops asking.

Which means, in four words: Model ⇄ Tools, wrapped in Memory, watched by Hooks.

LessonAttaches at
14 · Conversation managementbefore every model call — decides what messages survive
13 · Hooks & 16 · Pluginsbefore/after model, before/after each tool, on message added
15 · Interruptsinside a tool or before-tool hook — pauses the whole loop
11 · Sessionsafter invocation / after message — persists what happened
17 · Memorybefore each model call — injects recall into the model input
17 · Context offloaderafter a tool returns — swaps an oversized result for a preview
04 · Limitschecked at the top of each cycle
"Repeat" means recursion, not a while-loop

Each cycle calls recurse_event_loop — one Python stack frame deeper. A model that keeps calling tools does not churn harmlessly; it walks off the stack and you get EventLoopException: maximum recursion depth exceeded several hundred paid model calls later. This is why limits= is not optional in unattended code. Lesson 17 has the full mechanism.

5. Part 1 — Build it (lessons 01–04)

Your first agent

python
from strands import Agent, tool
from _shared import employees_with_skill, make_model, skill_level

@tool
def find_candidates(skill: str, min_level: int = 3) -> str:
    """Find bench employees who have a skill at or above a proficiency level.

    Args:
        skill: Skill name or alias, e.g. "pyspark" or "Apache Spark"
        min_level: Minimum proficiency, 1 (aware) to 5 (expert). Default 3.
    """
    people = employees_with_skill(skill, min_level=min_level, available_only=True)
    if not people:
        return f"Nobody on the bench is at level {min_level}+ in {skill!r}."
    return "\n".join(f"{e['employee_id']} {e['name']} — level {skill_level(e, skill)}" for e in people)

agent = Agent(tools=[find_candidates], model=make_model())
result = agent("Who on the bench knows pyspark at level 4 or better?")

No routing, no if intent ==. The model reads the tool's name, docstring and type hints and decides to call it — including translating the user's "pyspark" into the skill argument. That is what "model-driven" means: you add capability by adding functions.

You did not get a string back

agent(...) returns an AgentResult. str(result) gives the text, but the field you will actually grep for in every incident is result.stop_reason. Branch on that, never on the text of the answer.

stop_reasonMeaningWhat to do
end_turnfinished normallyuse the answer
max_tokensthe model's own output capanswer is truncated — retry or raise the cap
limit_turns / limit_total_tokens / limit_output_tokensyour budget cap firedinspect and decide; agent.messages is still valid
interruptwaiting for a humancollect responses, re-invoke (lesson 15)
cancelledagent.cancel() was calledclean up
guardrail_intervened / content_filteredpolicy stopped itsurface a safe message

Tools that need the agent

python
from strands import tool, ToolContext

@tool(context=True)
def open_requisition(job_id: str, tool_context: ToolContext) -> str:
    """Set the requisition this conversation is working on.

    Args:
        job_id: e.g. "J2001"
    """
    job = get_job(job_id)
    if job is None:
        return f"No such requisition {job_id!r}."
    tool_context.agent.state.set("job_id", job["job_id"])   # get() returns a COPY — set it back
    return f"Now working {job['job_id']} — {job['title']} in {job['location']}."

The model extracts, the tool stores. A model is good at pulling "we're filling J2001" out of a sentence and bad at still knowing it twenty turns later — especially once the conversation manager has thrown those turns away. Play to both strengths.

The tool_context parameter is invisible to the model. It carries three things:

  • tool_context.agent — the calling agent: its state, messages, model.
  • tool_context.tool_use — this call's toolUseId and raw input.
  • tool_context.invocation_state — kwargs passed into agent(...) for this run.

It is also the handle you use to pause for a human (lesson 15).

Borrowing tools over MCP

python
from mcp import stdio_client, StdioServerParameters
from strands import Agent
from strands.tools.mcp import MCPClient

# The HR team owns employee data. They publish one MCP server; we speak the
# protocol to it. Nothing here imports their code.
hr = MCPClient(lambda: stdio_client(
    StdioServerParameters(command=sys.executable, args=["hr_mcp_server.py"])
))

with hr:                          # the block is load-bearing: leaving it kills the server
    agent = Agent(tools=[*hr.list_tools_sync(), shortlist_candidate], model=make_model())
    print(agent.tool_names)
    # ['find_by_skill', 'score_match', 'rank_for_job', 'rank_jobs_for_person', 'shortlist_candidate']

You pass the client, not a list of tools — MCPClient is a ToolProvider, so the agent asks the server "what can you do?" on connect. Those four HR tool names were never typed in your codebase; they came off the wire, and they mix freely with your own local tools in one registry.

A server publishes three kinds of thing, and only the first is famous:

KindWhat it isWho drives it
toolsactions with argumentsthe model chooses
resourcesdata read by URI — hr://bench, hr://employees/E1002you: no model call, no tokens
promptsthe question itself, authored by the team that owns the datayou render, the model answers

Resources are the underused one: hr.read_resource_sync("hr://employees/E1002") fetches a profile with the model entirely uninvolved. And a prompt lets HR — not you — own the definition of a good screening note.

Leaving the with block kills the tools

Outside it the subprocess is gone and those tool names are unusable. A dead MCP server looks like an agent that quietly starts improvising — it still has the tool names in its history, so it makes plausible answers up.

Debugging an MCP client that will not start

The stdio transport swallows the subprocess's real error into unhandled errors in a TaskGroup, which tells you nothing. Always run the server command by hand — uvx strands-agents-mcp-server — to see what actually failed. (For us it was a TLS-interception cert blocking PyPI; --system-certs fixed it.)

Let the model recover

python
@tool(context=True)
def screen_candidate(employee_id: str, tool_context: ToolContext) -> str:
    """Score a candidate against the open requisition and add them to the shortlist."""
    employee = get_employee(employee_id)
    if employee is None:
        # Directive, not just descriptive. A bare "not found" invites a model to
        # try E1148, E1149, E1150… A tool's error message is a prompt too.
        return (f"No employee {employee_id!r} exists. Do not guess employee ids — "
                "call find_candidates and screen only the ids it returned.")
    ...

An error result goes back to the model as text, and the model reads it and corrects itself. Write error messages for the model, not for a log. A raised exception is caught too, but a deliberate message tells the model how to fix itself.

Measured: the difference between "not found" and an instruction

The first version of that tool returned a bare "No employee E1148." — and llama3.2 answered it by trying E1149, then E1150, then E1151, until the turn cap fired. Adding "do not guess employee ids — call find_candidates first" ends the loop, because it gives the model somewhere to go. Every tool result is the next thing the model reads, so it steers behaviour exactly as much as your system prompt does.

Budget caps — the runaway safety valve

python
result = agent("Screen E1002, then summarise the shortlist.", limits={"turns": 1})
result.stop_reason        # 'limit_turns'
len(agent.messages)       # 3 — still re-invokable

# all three dimensions; omit any for no cap on it
agent(prompt, limits={"turns": 8, "total_tokens": 50_000, "output_tokens": 4_000})
A limit that fires is not an error

No exception is raised. If you do not check stop_reason, a truncated run looks exactly like a successful one. Token caps are soft — one oversized response can overshoot by a turn, since checks happen at turn boundaries. On a simultaneous trip the priority is turns → total_tokens → output_tokens.

Caps are checked at the top of each cycle, which is what makes them safe to combine with everything in lesson 17: tools the previous cycle requested have already finished and their results are appended, so agent.messages ends on a complete exchange, the session persists a coherent conversation, and the next turn resumes normally.

6. Part 2 — Shape the output (lessons 05–07)

Structured responses

Problem

A hiring manager sends a paragraph of wishful thinking; somebody has to turn it into a requisition row with a real skills list. Prose cannot go into a database column. So teams write a second prompt asking for JSON, then a regex to find it, then a try/except because the model wrapped it in a code fence, then a validator because it invented a field. That whole pipeline is a bug farm.

python — the real schema from lesson 05
from pydantic import BaseModel, Field
from typing import Literal

class SkillRequirement(BaseModel):
    """One skill a role needs."""
    skill: str = Field(description="Canonical skill name, e.g. 'Apache Spark' not 'pyspark'")
    min_level: int = Field(ge=1, le=5, description="1 aware, 3 working independently, 5 expert")
    mandatory: bool = Field(description="True only if a candidate without it cannot do the job")

class Requisition(BaseModel):
    """An open role, extracted from a hiring manager's message."""
    title: str = Field(description="Job title, under 6 words")
    department: str
    location: str = Field(description="City, or 'Remote' if none is stated")
    min_experience_years: int = Field(ge=0, le=25)
    seniority: Literal["junior", "mid", "senior", "lead"]
    required_skills: list[SkillRequirement] = Field(description="3 to 6 skills, mandatory ones first")

req = agent(hiring_manager_message, structured_output_model=Requisition).structured_output
req.seniority             # 'senior' — a real enum value, already validated

The input is deliberately messy, the way real ones are:

the message being parsed
We're drowning in the retail lakehouse work. I need someone senior in Bengaluru who can
own our pyspark pipelines end to end — strong python, strong SQL, and they must be able to
run Airflow without hand-holding. Databricks experience would be a bonus. Six-plus years ideally.

Note what the schema is quietly doing: "Canonical skill name, e.g. 'Apache Spark' not 'pyspark'" makes the model normalise vocabulary, and mandatory's description — "True only if a candidate without it cannot do the job" — is the entire difference between a blocker and a nice-to-have. Field descriptions are where the business rules go.

flowchart LR
    P["Pydantic model"] -->|"converted to a tool spec"| M["Model"]
    U["User message"] --> M
    M -->|"calls the output tool
with typed args"| V["Pydantic validation"]
    V --> R["result.structured_output"]
    V -.->|"invalid"| M
Strands turns your schema into a tool the model must call — which is why it works on any tool-capable model.

A paragraph of system prompt does less work than one good description=. Literal[...] makes an invalid value structurally impossible.

Verified limit: nesting is expensive

Requisition nests — a list[SkillRequirement] inside it — and that is exactly where small local models start to fail. Strands raises StructuredOutputException rather than handing you a half-filled object. Lesson 05 wraps all three demos in try/except for that reason, and prints "this is a model limit, not a code bug" rather than hiding it. On a small model, prefer two flat calls over one nested schema — and catch that exception rather than letting it 500.

Structured output validates types, not truth

Nothing stops a model returning score=87 for a candidate the matcher scored 61. That is why GapReport's fields say "the score returned by score_match, unchanged" and "use exactly the verdict returned by the tool", and why the lesson-05 prompt says "do not recompute them". Compute what you can in tools; let the model fill in only what needs judgement.

python — tools first, then forced into the schema
class GapReport(BaseModel):
    """Why one candidate does or does not clear the bar."""
    employee_id: str
    verdict: Literal["strong", "possible", "weak", "blocked"] = Field(
        description="Use exactly the verdict returned by the score_match tool")
    score: int = Field(ge=0, le=100, description="The score returned by score_match, unchanged")
    blocking_skill: str | None = Field(description="The one mandatory skill they miss, or null")
    development_action: str = Field(description="One concrete step to close the gap, under 15 words")

report = agent("Can E1010 take the Analytics Engineer role J2003?",
               structured_output_model=GapReport).structured_output

E1010 (Divya Pillai) is the interesting case the course is built around: 52% on J2003, blocked by exactly one mandatory skill she has never used. That is the shape of decision a recruiter actually has to make — and development_action is where the model earns its keep.

agent.structured_output(Model, prompt) is deprecated — it bypasses the tool loop. Use structured_output_model= on the agent or the invocation.

Streaming responses

Two traps, both common

1. Leaving the default callback_handler on and iterating stream_async prints everything twice. 2. current_tool_use fires repeatedly as the model streams the tool's JSON arguments — deduplicate on toolUseId if you only want one notification per call.

Hiring is exactly the case for a Graph: the fairness review must run, and must run last. "The model usually remembers to review" is not a compliance story.

Verified: swarms need a strong model

On llama3.2, the swarm above ping-pongs screener → recruiter → screener → recruiter, and one agent emits the raw handoff JSON as text instead of calling the tool. The identical task through the Graph completes cleanly every time. Check your model before designing around a swarm.

name and description are load-bearing in every pattern — one agent reads another's identity to decide what it is for. A vague description is the number-one cause of multi-agent systems that route badly.

7. Part 3 — Understand the engine (lessons 08–12)

Cycles and cost

Instrument the loop with a hook and it stops being mysterious:

output
── invocation start ──
  cycle 1: → model
  cycle 1: ← model (stop_reason=tool_use)
  cycle 1:   ⚙ open_requisition({'job_id': 'J2001'})
  cycle 1:   ✓ open_requisition -> success
  cycle 2: → model
  cycle 2: ← model (stop_reason=end_turn)

The last cycle produces no tool call — it is the model writing the answer. Budget for roughly n_tools + 1 model calls, and remember context grows every cycle, so cost is superlinear.

Two state gotchas that cost real debugging time

state.get() returns a deep copy — agent.state.get("shortlist").append(x) silently does nothing at all. Read, mutate, set() back. And state is invisible to the model by design: setting it does not "tell" the model anything; a tool must return the value.

State validates JSON on write — deliberately

agent.state.set("seen", {"E1002", "E1003"}) raises ValueError, because a set is not JSON. State exists to be persisted (lesson 11) and snapshotted (lesson 12), so anything that cannot round-trip is rejected at the point of the bug — not three days later when a session tries to serialize it.

State also enforces ordering that a system prompt can only request. screen_candidate refuses to run at all until a requisition is open:

job_id = agent.state.get("job_id")
if not job_id:
    return "No requisition is open. Call open_requisition first."

A workflow rule enforced in code, not hoped for in a prompt.

Storage — four methods over bytes

python
class Storage(Protocol):
    async def write(self, key: str, data: bytes) -> None: ...
    async def read(self, key: str) -> bytes | None: ...      # None when missing, not an error
    async def delete(self, key: str) -> None: ...
    async def list(self, query: str) -> list[str]: ...

No transactions, no schemas, no query language — that is the design. Anything can implement it in twenty lines, and every persistence feature consumes it.

pin_first counts messages, not turns — and getting it wrong looks like it working

One turn is a user message plus an assistant message, and more once tools are involved. Pinning the two opening turns is pin_first=4, not 2. Pinning caps how much you can reclaim

Pin 4 messages of a 6-message window and the trimmer logs "all messages in trim range are pinned, unable to reduce" — note the history above grew to 10, past window_size. That is the trade, not a bug. Pin a small fraction of a large window.

The shortlist does not belong in the transcript

Nothing in that table can lose a fact that lives in agent.state. Conversation management is a decision about dialogue; durable facts should never have been in the dialogue in the first place.

The default is already trimming

If you never configured this, you are running SlidingWindowConversationManager(window_size=40) and silently dropping history. There is no warning and no event — the model just stops knowing things.

python — asking from a hook (the tool stays unaware)
RISKY_TOOLS = {"reject_candidate"}      # tools that change a person's record

class ApprovalGate(HookProvider):
    def register_hooks(self, registry: HookRegistry, **_) -> None:
        registry.add_callback(BeforeToolCallEvent, self.approve)

    def approve(self, event: BeforeToolCallEvent) -> None:
        if event.tool_use["name"] not in RISKY_TOOLS:
            return
        answer = event.interrupt("approve_rejection", reason=event.tool_use)
        if answer != "yes":
            event.cancel_tool = "The recruiter declined this rejection."

The rule in hiring: an agent may screen, rank and draft all day, but a human approves anything that touches a person's record. Note the tool itself is untouched — it does not know it is gated.

python — handling the pause
result = agent("Reject E1003 — their Spark level is too low for J2001.")

while result.stop_reason == "interrupt":
    for i in result.interrupts:
        print(i.name, i.reason)          # render this to your UI
    payload = [{"interruptResponse": {"interruptId": i.id, "response": "yes"}}
               for i in result.interrupts]
    result = agent(payload)              # resume

Interrupt state is part of the session and of preset="session" snapshots — so a different process, hours later, can resume the same paused agent. Durable human-in-the-loop with no queue of your own.

The hook re-runs on resume

Everything before the interrupt() call executes twice. Keep that code free of side effects. Also: always loop on stop_reason == "interrupt" — a resumed pass can raise new interrupts.

A hook is a function. A plugin is a feature — the unit you publish, version and reuse.
python
from strands import tool
from strands.plugins import Plugin, hook

class ProfileAccessGuard(Plugin):
    """How many candidate profiles may one request read? A data-minimisation rule."""
    name = "profile-access-guard"           # stable id — required

    def __init__(self, max_profiles: int = 3) -> None:
        self.max_profiles = max_profiles
        self.reserved = 0
        super().__init__()                  # discovers @hook and @tool methods — call this LAST

    @hook
    def _reset(self, event: BeforeInvocationEvent) -> None:
        self.reserved = 0

    @hook
    def _enforce(self, event: BeforeToolCallEvent) -> None:
        if event.tool_use["name"] != "read_profile":
            return
        if self.reserved >= self.max_profiles:
            event.cancel_tool = (
                f"Profile access limit of {self.max_profiles} reached for this request."
            )
            return
        self.reserved += 1                  # reserve BEFORE — see below

    @tool
    def remaining_profile_quota(self) -> str:
        """Report how many more candidate profiles may be read in this request."""
        return f"{max(0, self.max_profiles - self.reserved)} profile reads remaining"

    def init_agent(self, agent) -> None:
        agent.state.set("profile_quota", self.max_profiles)

agent = Agent(tools=[read_profile], plugins=[ProfileAccessGuard(max_profiles=3)])
agent.tool_names        # ['read_profile', 'remaining_profile_quota'] — the plugin's tool is there
The bug this course actually hit — reserve in Before, not After

Tools in one turn run concurrently, so every BeforeToolCallEvent fires before the first AfterToolCallEvent. A counter that only increments in After reads zero at every check and enforces nothing — five profiles sail through a limit of three. Reserve up front, reconcile in After. This bites every quota, rate-limit and budget plugin you will ever write.

MultiAgentPlugin is the orchestrator-level counterpart (hooks only — orchestrators have no tool registry); lesson 16 uses one to time every node in a Graph. Ships with the SDK under strands.vended_plugins: ContextOffloader, ContextInjector, AgentSkills, Goal, Steering.

Two traps in one line of config

1. The offloader "auto" builds for you is in-memory. Pair it with a session and restart, and the restored messages hold references to blobs that no longer exist. Pass your own ContextOffloader(storage=LocalFileStorage(...)) in plugins= — "auto" detects one and skips adding its own.
2. …and supplying it resets its thresholds. A bare ContextOffloader(storage=...) defaults to max_result_tokens=2500, not the 1500 "auto" would have used — so results between the two sail through un-offloaded and nothing warns you. We shipped that bug and caught it only because the blob count printed zero.

The seams — six facts that need two layers to see

  1. A snapshot is what a session writes. SnapshotSessionManager has no separate format — it captures the same Snapshot as take_snapshot(preset="session"). One is the storage policy for the other.
  2. Trimming is not destructive on disk. A message-log session keeps every message, and restores from offset=conversation_manager.removed_message_count. The audit record stays complete; the agent comes back holding only the untrimmed tail.
  3. Memory injection never enters the transcript — see above.
  4. State is JSON-validated because state is what gets persisted. The rejection happens at the point of the bug, not at save time three days later.
  5. restore_snapshot does not move snapshot_latest. Follow it with save_snapshot(is_latest=True) or the next restart returns the mistake.
  6. A rewind under a message-log session is not durable. load_snapshot shortens agent.messages in memory; it does not delete the files FileSessionManager already wrote, so the abandoned branch comes back on the next boot. If undo must survive a restart, the session has to be snapshot-based.

An early draft loaded only find_candidates but left shortlist_candidate named in the system prompt. The model promptly hallucinated a call to the tool that did not exist. If a prompt references a tool the agent lacks, the model will invent one. Keep the prompt and tools= in sync — and note the mirror image from lesson 17: a prompt that lists four tools reads to a small model as four steps it is expected to perform.

13. Check yourself

An agent answers a two-tool question. How many model calls did that take?
One cycle = one model call + the tools it asked for. The final cycle produces no tool call — it is the model writing the answer. Budget for n_tools + 1, and remember context grows every cycle, so cost is superlinear.
You set agent.state["recruiter_id"]. Why does the model still not know the recruiter?
agent.state is deliberately invisible to the model — that is what makes it safe for recruiter ids, tenant ids and auth. Only agent.messages is sent. (Also note state.get() returns a deep copy, so mutating the result does nothing; set() it back.)
Your unattended agent dies with EventLoopException: maximum recursion depth exceeded. What happened?
The agent loop is recursion, not iteration — each cycle calls recurse_event_loop. The only natural exit is the model returning end_turn, so a looping model walks off the stack. limits={"turns": n} is checked at the top of each cycle and returns cleanly instead. Then fix the cause: usually a required tool parameter the model would never think to supply, answered with a bare validation error.
A rule the manager stated on requisition J2001 must still apply when they open J2004 next week. Where does it go?
State and sessions are both scoped to one conversation. Open a new session_id for J2004 and everything from J2001 is unreachable — that is the point of a session key. Memory is the layer keyed by the desk rather than the conversation, and injection surfaces it without anyone asking.
Your cost-guard plugin counts spend in AfterToolCallEvent and never blocks anything. Why?
The counter reads zero at every check. Reserve the cost in BeforeToolCallEvent and reconcile in After. This is a real bug we hit building this course — $0.05 went through a $0.03 budget.

Flip these until they are automatic:

What ends the agent loop?
A stop_reason other than tool_use.
What does the model read to pick a tool?
Name + docstring + type hints. Docstrings are prompt.
Where do you put a recruiter or tenant id?
invocation_state — the model never sees it.
Session vs. memory?
A session is one conversation. Memory is every conversation this desk ever had.
Why does an unbounded tool loop crash rather than spin?
The loop recurses — one stack frame per cycle. Cap it with limits.
How do you block a tool without editing it?
event.cancel_tool = "reason" on BeforeToolCallEvent.
Known order of work → which multi-agent pattern?
Graph. Coordinator in charge → agent-as-tool. Let them figure it out → Swarm.
Interrupt: what happens on the second call?
It returns the human's answer instead of raising.

The four things worth remembering

1. One cycle = one model call + its tools — and it recurses, so cap it. 2. Docstrings, field descriptions and tool error messages are all prompt, not documentation. 3. stop_reason is the only branch you need. 4. Policy belongs in hooks, never in the system prompt — a prompt is a suggestion, a hook is a rule. 5. Pick the layer by how long the fact must survive: a call, a conversation, a requisition, or the desk.

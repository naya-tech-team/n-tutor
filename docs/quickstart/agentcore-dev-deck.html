Why this talk

Your agent works. Now ship it.

The demo took a week. Production asks six questions that have nothing to do with prompt engineering:

Where does it run?

Lambda caps at 15 minutes. ECS means paying for idle and building isolation yourself.

How does it remember?

Extract facts, embed, dedupe, merge — per user, forever. The merging is the hard part.

How does it reach tools?

M agents × N tools. Write an MCP server per tool, or don't scale.

Whose credentials?

The agent's token is more powerful than the user it serves — and it's non-deterministic.

Why did it do that?

A 200 OK with a confidently wrong answer is invisible to every metric you have.

What actually stops it?

"Never refund over $1,000" in a system prompt is a suggestion, not a control.

The thread running through all of it

Agents are long-running, stateful and non-deterministic. Nearly every design decision in AgentCore — and every gotcha in part two — falls out of one of those three properties.

Agenda
The shape of it

Six services, not one framework

Runtime

Serverless hosting. One microVM per session, 8-hour sessions, no CPU charge while waiting on the model.

Memory

Raw event log + asynchronously extracted long-term records, with managed consolidation.

Gateway

APIs, Lambdas, MCP servers and model providers as governed tools behind one endpoint.

Identity

Agent identity + credential vault. Every credential bound to which agent × whose behalf.

Observability

OTel sessions/traces/spans in CloudWatch, plus LLM-as-judge Evaluations.

Policy

Cedar authorization at the Gateway boundary. Rules the model can't argue with.

Adopt à la carte

Every one is a plain AWS API — Memory works from a Lambda, Observability ingests from on-prem or another cloud. The only hard coupling: Policy requires Gateway.

Runtime · 1 of 3

Agents aren't web services

8 h
session lifetime
1 : 1
session : microVM
100 MB
payload

Four facts about agents that no general-purpose compute service is designed around:

They run for minutes or hours

Not milliseconds. Lambda's 15-minute ceiling isn't a tuning problem, it's a wall.

They mostly wait

Blocked on model tokens and tool I/O. Paying for reserved CPU during that is pure waste.

They accumulate mutable state

Scratch files, installed packages, cached embeddings — which must never leak between users.

They're non-deterministic

So security can't depend on the agent behaving well. It has to be structural.

Runtime · 2 of 3

Isolation is a platform property

  ┌── session A ──┐ ┌── session B ──┐
  │   microVM     │ │   microVM     │
  │  own CPU      │ │  own CPU      │
  │  own memory   │ │  own memory   │
  │  own filesystem││  own filesystem│
  └───────────────┘ └───────────────┘
        ▲                  ▲
        └── nothing shared ─┘

  session ends → microVM destroyed,
                 memory sanitised
Why it matters

Agent frameworks cache aggressively — embeddings, tool results, retrieved documents. In a shared-container model a caching bug becomes a cross-tenant disclosure. Here it's a one-session incident.

Your half of the deal

AgentCore does not enforce a session-to-user mapping. Generate session IDs server-side and bind them to your authenticated user — never accept one from the client.

Session lifecycle in one line

Active (CPU + memory billed) → Idle (memory only, 15 min default) → Stopped. Reuse the session ID across turns or you pay a cold start every time.

Runtime · 3 of 3

The contract is three HTTP endpoints

POST /invocations   your agent turn
GET  /ping          health + "still working"
GET  /ws            optional WebSocket
                    (MCP servers: :8000 /mcp)

# /ping returns:
{ "status": "Healthy" }
{ "status": "HealthyBusy" }   ← keeps the
                                session alive
The two production bugs

Never block in the entrypoint — a blocked event loop starves /ping, and your long job dies at ~15 minutes.

Never refresh time_of_last_update on every ping — sessions then look permanently active, never get reaped, and you hit the quota.

Memory · 1 of 3

Two stores wearing one name

Short-term eventsLong-term records
NatureWrite-ahead log — raw, immutable, dumbLLM-derived materialised view — distilled
ConsistencySynchronous, instantly readableAsynchronous — seconds to minutes
Cost$0.25 / 1K events$0.50 / 1K retrievals
Answers“What just happened in this conversation?”“Who is this person and what do we know?”
The rule that falls out

Read events for recency, records for identity. Never write a fact and try to retrieve it as a record in the same turn — extraction is asynchronous and there's no wait-for-consistency API.

What you're actually buying

Extraction is a prompt. Embeddings are a library call. Vector search is a managed index. Consolidation — deciding whether a new fact is novel, refines an existing record, or is redundant, forever, per user — is the part that's genuinely hard to build.

Memory · 2 of 3

Strategies do the distilling

  CreateEvent ──► short-term store          synchronous, always fast
       │
       │ triggers, per strategy                    ASYNCHRONOUS
       ▼
   EXTRACTION      LLM proposes candidate records from new events
       ▼
   CONSOLIDATION   compares against existing records in the namespace
                   → AddMemory · UpdateMemory · SkipMemory
       ▼
   REFLECTION      (episodic only) generalises across many episodes
       ▼
   long-term records ──► RetrieveMemoryRecords (semantic + metadata filters)

Conversational agents

Semantic (facts) · Summary (session narrative) · User preference (evolving profile). These read only USER / ASSISTANT turns.

Acting agents

Episodic reads TOOL results and reconstructs what the agent did and whether it worked — then reflects across episodes. Without tool payloads, quality collapses.

Memory
Memory · 3 of 3

Namespaces are four things at once

Where records are filed

/facts/{actorId}/, /summaries/{actorId}/{sessionId}/

What retrieval searches

Exact namespace, or prefix across a subtree

What IAM conditions on

bedrock-agentcore:namespace as a policy condition

The consolidation boundary

Records only merge within a namespace.

Two traps

Always end with /. /users/1 is a prefix of /users/10 — in multi-tenant that's a cross-tenant read, not a typo.

Don't over-nest. Every level narrows the candidate set; five deep and semantic search has nothing left to search.

The retrieval recipe

1. Recent turns from events — instantly consistent.
2. Preferences: top_k=5, score ≥ 0.7 — few and confident.
3. Facts: top_k=10, score ≥ 0.3 — broader recall.
Tune per namespace; one global threshold either floods the prompt or drops what the user told you.

Memory
Gateway · 1 of 3

M × N → M + N

Not a proxy. A proxy forwards bytes; Gateway translates protocols, exchanges credentials, indexes tools for discovery and enforces policy. Those four jobs are why it can't be an ALB.

MCP targets

Aggregation. Many backends as one virtual MCP server — Lambda, OpenAPI, Smithy, MCP servers, SaaS connectors.

HTTP targets

Passthrough. Front a Runtime agent or any HTTP service, untranslated, while keeping auth, policy and observability.

Inference targets

Routing. LLM traffic by model ID across Bedrock, OpenAI, Anthropic. Their SDKs work unmodified.

They behave nothing alike

Only MCP targets get aggregation, Target___tool naming, semantic search and per-tool Cedar actions. Choosing HTTP passthrough because it configured faster quietly forfeits all four. Decide by the governance you need, not by what imports fastest.

Gateway · 2 of 3

Tool names are an API contract

${target_name}___${tool_name}
                ▲
                └ three underscores

# every Lambda target needs this
DELIM = "___"

def lambda_handler(event, context):
    raw = context.client_context.custom[
        "bedrockAgentCoreToolName"]
    tool = raw[raw.index(DELIM)+len(DELIM):]

    if tool == "get_order":
        return get_order(event["order_id"])
The #1 "why doesn't my tool fire"

Your router compares "orders___get_order" == "get_order", never matches, and every call returns unknown tool. Strip the prefix first, before any business logic.

The prefix leaks everywhere

Into agent prompts, Lambda routing, Cedar policy actions and rate-limit entries. There is no alias mechanism — renaming a target breaks all four at once.

OpenAPI targets

operationId becomes the tool name and description is what the model reads to choose. Swagger 2.0, oneOf/anyOf/allOf unsupported — budget remediation time.

Gateway
Gateway · 3 of 3

Discovery, not dispatch

Gateway makes it trivial to expose a thousand tools. That's a trap — every tool in tools/list costs context and adds a wrong turn the model can take. Hence the built-in x_amz_bedrock_agentcore_search.

Quota says so

Search is capped at 25 per minute — roughly 0.4 TPS — against 200 TPS for ordinary tool calls.

Price says so

5× a normal invocation: $0.025 vs $0.005 per 1,000, plus indexing per tool per month.

Accuracy says so

Tool overload degrades selection long before it hits any limit. Fewer, better-described tools win.

Enable it at creation — you cannot add it later

searchType lives in protocolConfiguration.mcpConfiguration and is creation-time only. Retrofitting means a new gateway and repointing every client. If the catalogue might ever grow, turn it on day one.

The pattern

Search once per task to narrow the toolset, cache the subset for the session, then call tools directly.

Two independent gates

IAM decides which providers a role may ask for. The workload access token decides whose credentials come back. Agent A can't get user B's Google token even holding valid IAM permission.

Before you ship

GetWorkloadAccessTokenForUserId takes an unverified string. Grant ...ForJWT and explicitly Deny the UserId variant — the managed BedrockAgentCoreFullAccess policy includes it.

Identity · 2 of 2

Three flows — and a design problem

FlowWhat happensHuman in the loop?
M2M (2LO)Agent uses its own client credentialsNo — prefer it whenever per-user scoping isn't required
USER_FEDERATION (3LO)User consents; token scoped to that user and cached in the vaultYes — browser round trip, 10-minute URL expiry
ON_BEHALF_OFExchange the inbound JWT for a downstream token (RFC 8693 / 7523)No consent flow at all
The bit nobody budgets for

3LO puts a human in the middle of an autonomous process. You must build and host an HTTPS callback that validates the live session and calls CompleteResourceTokenAuth — even when the agent runs on Runtime.

Three ways out

Warm consent at onboarding · treat "needs consent" as a first-class resumable agent state · or skip it entirely with OBO where your IdP supports token exchange. That last question is worth asking very early.

Observability · 1 of 2

Is it up? What did it do? Was it right?

1 · Metrics — is it up?

Invocations, errors, latency, active sessions, CPU/GB-hours. Free and automatic — and completely blind to correctness.

2 · Traces — what did it do?

The reasoning trajectory: tool calls, arguments, model turns, retries. Session → trace → span.

3 · Evaluations — was it good?

14 built-in LLM-judges over those traces: Goal Success Rate, correctness, tool-selection accuracy, harmfulness.

Layer 2 needs two opt-ins, and neither errors if you skip it

Transaction Search enabled once per account, and ADOT instrumentation (opentelemetry-instrument python main.py). Metrics appear either way — so teams assume it works and discover during their first incident that they have counters without causality.

Why layer 3 exists

Agent failures are semantic, not operational. Latency fine, error rate zero, user got garbage. Evaluations is the only layer that sees that — and it reads the same OTel traces, so instrumentation quality gates it.

Observability
Observability · 2 of 2

Debug top-down, alarm on five things

  SESSION   the whole conversation
   │
   ├── TRACE   one request/response turn
   │    ├── SPAN  "retrieve context"
   │    ├── SPAN  "invoke model"
   │    │    └── SPAN "tool: get_weather"
   │    └── SPAN  "format output"
   │
   └── TRACE   the next turn …

  user complains → find the SESSION
                 → spot the odd TRACE
                 → drill to the SPAN
Alarm on these

ActiveSessionCount at ~70% of quota · Throttles · NoDeterminingPolicies · Identity token-fetch failures · Goal Success Rate trending down.

Two things to decide before go-live

Sampling — 1% is free, and unsampled traffic is gone forever. Redaction — request_payload and response_payload are logged by default, which is exactly how PII reaches CloudWatch.

Policy · 1 of 2

You can't make an LLM refuse

   ┌─────────────────────────────────────────────────────────┐
   │  the agent — non-deterministic, promptable, persuadable  │
   │  "you must never issue a refund over $1,000"             │
   │       ↑ a suggestion the model may or may not honour     │
   └───────────────────────┬─────────────────────────────────┘
                           │ tool call
   ════════════════════════╪═══════ trust boundary ═══════════
                           ▼
   ┌─────────────────────────────────────────────────────────┐
   │  GATEWAY + POLICY ENGINE — deterministic, unreachable    │
   │  permit(...) when { context.input.amount < 1000 };       │
   └─────────────────────────────────────────────────────────┘

Default deny

No matching permit means denied. Silence is never permission.

Forbid wins

Any matching forbid overrides every permit. Guardrails can't be out-voted.

No ordering

Policies are a set, not a sequence. Same request, same answer, always.

Policy
Policy · 2 of 2

Roll it out in LOG_ONLY. Always.

permit(
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::
    "RefundAPI___process_refund",
  resource == AgentCore::Gateway::"arn:…"
)
when {
  context.input has amount &&     ← always
  context.input.amount < 1000        guard
};
ENFORCE is default-deny

An engine with 3 policies on a gateway exposing 40 tools denies 37 of them. Start in LOG_ONLY, watch NoDeterminingPolicies fall to zero, then switch.

The control-plane risk

Enforcement mode lives on the gateway. Anyone with UpdateGateway can flip it to LOG_ONLY — no separate IAM action protects it.

The feature that changes agent design

Partial evaluation prunes always-denied tools out of tools/list. The model never learns they exist — security, accuracy and context-window win at once. Only possible because Cedar is formally analysable.

Policy
Part two · ~8 minutes

Four things that
will bite you

Gotcha 1

Identifiers are one-way doors

Every service has one identifier chosen early that can't be changed later without abandoning data or breaking references.

Session ID

Drives isolation and microVM affinity. New ID per turn = cold start every turn.

actorId

Defines what can ever be recalled together. Changing it orphans everything written.

User-ID namespace

The vault key. Federate a 2nd IdP without a prefix → two humans, one entry.

Target name

Becomes Target___tool — in prompts, Lambda routing and Cedar actions.

Action strings

Embed that target name. Rename → policies stop matching → denied.

Session ID again

No sessions view, no cross-turn debugging, no session-level evaluators.

Do this first

Spend an hour on naming before you ship anything. None of it is recoverable afterwards — and cognito+user123 beats user123 the day you add a second IdP.

Two fixes cover most of it

Batch turns into one event (up to 100 messages) instead of one event per message — cuts throttling and cost. Search once per task, then call tools directly.

Gotcha 2 · quotas
Gotcha 3

Costs are shaped opposite to intuition

Memory: reading, not storing

Retrieval $0.50/1K beats storage $0.75/1K-per month. Two retrievals per turn ≈ 8× the storage bill. Fetch preferences once per session.

Gateway: search, not calls

Tool calls $0.005/1K — noise. Search is 5×. Web Search is 1,400× at $7 per 1,000 queries.

Runtime: idle memory, not CPU

No CPU charge while blocked — but memory accrues through idle too. Leaked sessions are the classic surprise line item.

Observability: free feature, real bill

$0 from AgentCore; you pay CloudWatch ingestion on dozens of payload-bearing spans per turn.

10 M tool calls/month:  Gateway $50 · Policy $250 · Memory retrieval $2,000
                        … and model tokens dominate all of it.
one Web Search per task × 1 M tasks:                          $7,000  ← 20×

Gotcha 4

Two things are never automatic

Neither errors if you skip it

Traces need two opt-ins — Transaction Search enabled once per account, and ADOT instrumentation. Metrics appear regardless, so it looks like it's working right up until you need it.

Policy in ENFORCE is default-deny. Attaching an engine with an incomplete policy set is an outage, not a warning.

Watch the deny stream

In LOG_ONLY, two CloudWatch metrics tell you everything:

NoDeterminingPolicies — legitimate traffic falling to default deny.
LogOnlyDecisionFlips — what would change if you enforced.

Gotcha 4 · silent defaults
The pattern behind the gotchas

Small and scoped beats big and shared

Four services arrive at the same architecture from completely different directions:

  • Gateway — tool overload degrades model accuracy long before it hits any quota.
  • Policy — the 400 KB Cedar schema grows with tool count; AWS's own remedy is splitting engines per gateway.
  • Identity — scope-down policies are only as fine-grained as your workload identities.
  • Memory — over-nested namespaces destroy retrieval precision.
The synthesis

Prefer several purpose-scoped gateways, engines and identities over one large shared everything. A support agent shouldn't see the deployment tools — and its policy engine shouldn't have to carry their schema.

A support agent, wired up

RequirementServiceThe specific decision

The composition that carries the most weight

Identity → Memory. Memory files records under a user identity, and Identity is the only component that verifies it. Wiring actorId from an unverified string is the most common way a multi-tenant agent leaks one customer's memory to another.

Worked example
What it looks like

Four lines and a deploy

# main.py
from bedrock_agentcore.runtime import (
    BedrockAgentCoreApp)
from strands import Agent

app = BedrockAgentCoreApp()
agent = Agent()

@app.entrypoint
def invoke(payload):
    return {"result":
        agent(payload["prompt"]).message}

if __name__ == "__main__":
    app.run()
# the CLI does the infrastructure
npm install -g @aws/agentcore

agentcore create --name MyAgent
agentcore dev              # localhost:8080
agentcore deploy           # IAM, ECR, runtime

agentcore add memory  --strategies SEMANTIC
agentcore add gateway --name MyGateway
agentcore add policy-engine --name Guard \
  --attach-mode LOG_ONLY

agentcore logs --follow
agentcore traces list
Tooling note

The Python bedrock-agentcore-starter-toolkit is legacy. Use the npm-distributed @aws/agentcore CLI — both claim the agentcore command, so uninstall the old one first. The runtime SDK bedrock-agentcore is unaffected.

Before you go to production

The checklist

Naming

Session IDs, actorId, user-ID namespacing, target names, provider names — decided and frozen.

Runtime

ARM64 · numeric USER · idle timeout tuned · StopRuntimeSession on conversation end · async tasks completed in finally.

Memory & Gateway

Namespaces end with / · turns batched · Lambda strips ___ · backends accept gateway-only traffic.

Identity & Policy

...ForUserId denied · callback URLs registered · LOG_ONLY first · UpdateGateway restricted and alarmed.

Observability

Transaction Search on and spans confirmed arriving · sampling chosen · retention set · redaction decided.

If you only do three things

1. Get session IDs and actorId right — unrecoverable later. 2. Confirm spans arrive before you need them. 3. Put anything irreversible behind Policy, in LOG_ONLY first.

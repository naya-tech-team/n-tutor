AWS AgentCore — Tutorial & Capability Guide

Full Guide 7 capabilities runnable code Terraform included ~60 min

Amazon Bedrock AgentCore is not a framework for building agents. It is the platform an agent you have already built needs in order to become a service: somewhere to run with per-session isolation, a way to reach tools it does not own, memory that survives a restart, an answer to "who is allowed to ask", and a trace when it misbehaves at 2am. Your agent code barely changes. Everything around it does.

This guide teaches it the only way that sticks: by taking one working system — the HR recruiting pipeline used across this whole course — and moving it, capability by capability, from three terminals on a laptop to five deployed runtimes behind one front door.

⬇️ Get the runnable code

Everything on this page ships with the course in agent-core/: five runtimes, a Gateway over a Lambda over S3, Memory, Cognito, OpenTelemetry, a React chat UI, eight Terraform modules and 85 tests. It still runs end to end on your laptop with no AWS account — AGENTCORE, MODEL_PROVIDER and DATA_SOURCE decide which world each file is in. Read agent-core/architecture.md for the design document and agent-core/README.md for how to run it.

One domain across the whole course

Every track here uses the same small world: employees have skills rated 1–5, requisitions require skills at a minimum level, and some of those are mandatory. A candidate below a mandatory bar is blocked — no score saves them. You have already met it in Python, over HTTP in FastAPI, as tools in FastMCP, across processes in A2A, and agent-side in the Strands course. Here it gets deployed.

The one line to carry through the whole page

Locally, a port told you which agent you were talking to. On AgentCore an ARN does — and a session id, which here is the requisition id, is the only thread tying memory, three A2A hops and one distributed trace together. Almost every confusing failure below is a session id or an address that stopped being the thing you thought it was.

🧠 The distinction worth holding on to

A framework decides how your agent thinks. A platform decides what happens when other people can call it. Strands, LangGraph and CrewAI are the first. AgentCore is the second — which is why this page has almost no prompt engineering in it and a great deal about ports, roles and session ids.

Twelve employees with skills rated 1–5. Six open requisitions, each naming required skills with a minimum level, a weight, and a mandatory flag. One function decides who fits:

Three people show up on every screen below, and they are the reason the design is shaped the way it is. Scored against J2001 — Senior Data Engineer, Bengaluru:

shortlist("J2001")
E1002 Priya Raman     100% strong    blockers=[]
E1003 Rahul Menon      61% blocked   blockers=['Apache Spark']
E1005 Vikram Iyer      50% blocked   blockers=['Python', 'SQL']

Rahul is second by score and cannot be hired. The ranking is by score; the decision is the verdict. Hold on to that, because distribution introduces a failure mode a laptop does not have: every hop between agents is a chance to paraphrase, and paraphrase drops the blocker. "Blocked on Apache Spark" becomes "some gaps", and a warm note goes to someone who cannot do the job.

Why this example and not a chatbot

A weather bot cannot teach you AgentCore, because nothing about it is wrong in a way that matters. This system has a fact — blocked — that must survive five processes, three model calls, a summarisation memory strategy and a JSON round-trip without being softened. Every capability below is judged on whether it protects that fact.

4. Capability 1 — Runtime

What it is

A serverless container host built for agents: per-session isolation (each session gets its own microVM, so one conversation's memory and file system cannot leak into another), long turns — hours, not the 15 minutes a Lambda gives you — and framework indifference. You hand it a zip or an image; it hands you an ARN and an endpoint.

The protocol contract — get this wrong and nothing tells you

Runtime does not care what framework you used. It cares that your process listens on the right port at the right path:

ProtocolPortMount pathDiscoveryUse it for
HTTP8080/invocationsnoneyour own front door
MCP8000/mcptools/lista tool server
A2A9000/agent card at /.well-known/agent-card.jsonan agent other agents delegate to
AGUI8080/invocations (SSE)nonea UI-facing event stream
The failure that wastes an afternoon

Bind 8080 in an A2A container and the deploy succeeds. The container starts, fails its health check, and the error you eventually see is a timeout. Nothing anywhere says "wrong port". This table is the first thing to check when a deploy works but never answers.

An HTTP runtime: the supervisor

The orchestrator changing from a script into a service is the structural move of the whole migration. A supervisor that anything can call needs a bounded turn count, an identity to check and a trace id — none of which a script in terminal 3 ever needed.

app/runtimes/hiring_supervisor/main.py
from bedrock_agentcore.runtime import BedrockAgentCoreApp

app = BedrockAgentCoreApp()

@app.entrypoint
async def invoke(payload, context):          # async def + yield => SSE
    """One question per call, answered as a stream."""
    payload = payload or {}
    job_id = payload.get("job_id") or DEFAULT_JOB
    # AgentCore hands us the session id it was invoked with.
    session_id = getattr(context, "session_id", None) or job_id

    async for event in stream_pipeline(
        job_id, session_id=session_id, prompt=payload.get("prompt") or ""
    ):
        yield event

app.run(port=8080)

bedrock_agentcore inspects the entrypoint. See an async generator and it returns StreamingResponse(media_type="text/event-stream"); see a plain def returning a dict and it returns JSON. Both work — but a full run here is three remote delegations and a minute or two, so the JSON version is a browser showing nothing at all until the very end.

An A2A runtime: the three specialists

serve_a2a is the SDK helper that wraps an agent as a Bedrock-compatible A2A server: it handles the health endpoint, serves the agent card, reads AGENTCORE_RUNTIME_URL, propagates the Bedrock headers and binds 9000. Compare the two halves of the one file that knows which world it is in:

app/_shared/a2a_serve.py
from bedrock_agentcore.runtime import serve_a2a
from strands.multiagent.a2a.executor import StrandsA2AExecutor

# Runtime injects the public URL. Putting it on the card matters: a client
# resolves the card, then sends to the `url` it finds there — so a card
# advertising 0.0.0.0 sends the second request into a black hole.
url = os.environ.get("AGENTCORE_RUNTIME_URL", "http://0.0.0.0:9000/")

executor = StrandsA2AExecutor(
    agent_factory=agent_factory,
    enable_a2a_compliant_streaming=True,
)
serve_a2a(executor, build_card(name=name, description=description,
                               skills=skills, url=url))

Two things carry over from the local version, and one does not:

  • The declared AgentSkill is unchanged. candidate_screening, candidate_outreach_note, outreach_compliance_review — it is what a calling agent reads off the card to decide you are the right service to ask.
  • The tool budget carries over, and matters more. See below.
  • agent_factory becomes belt-and-braces. Locally it exists so two callers never share message history. Runtime already isolates by session id, so keep it if you want one file to run both ways — which is exactly why this project keeps it.
A served agent has no call site — so cap it with a hook

On a direct call you bound the loop with agent(prompt, limits={"turns": 8}). Inside A2AServer or serve_a2a the server invokes the agent for you, so there is nowhere to pass limits. The Strands agent loop recurses once per cycle, so an agent that keeps calling tools walks off the stack. A hook attaches to the agent object itself and travels with it:

app/_shared/tool_budget.py
class ToolBudget(HookProvider):
    def register_hooks(self, registry, **_):
        registry.add_callback(BeforeInvocationEvent, self._reset)
        registry.add_callback(BeforeToolCallEvent, self._enforce)

    def _enforce(self, event: BeforeToolCallEvent) -> None:
        # Reserve BEFORE the tool runs. Tools in one turn execute concurrently,
        # so a counter incremented afterwards reads zero at every check.
        self._used += 1
        if self._used > self.max_calls:
            # cancel_tool hands this string to the model as the tool result,
            # so it is a prompt: say what to do now, not just that it failed.
            event.cancel_tool = (
                f"Tool budget of {self.max_calls} calls is used up. Do not call "
                "any more tools. Answer now, using only what you already have."
            )

A remote agent needs this more than a local one, not less. When a service loops, the caller sees a request that never returns — and now the evidence is in CloudWatch instead of a terminal you can see.

An MCP runtime: the scoring engine

The FastMCP server from the FastMCP Quick Start becomes a runtime by changing three arguments, none of them cosmetic:

app/runtimes/hr_skills_mcp/main.py
mcp.run(
    transport="streamable-http",
    host="0.0.0.0",        # a container that binds loopback is unreachable
    port=8000,
    path="/mcp",
    stateless_http=True,   # Runtime load-balances across instances
    show_banner=False,
)

stateless_http=True is the one that bites. Runtime injects an Mcp-Session-Id header on any request that lacks one and load-balances across instances — so a stateful server gets handed a second request by an instance that never heard of that session. Set it False only if you genuinely need elicitation, sampling or progress notifications.

Watch where those arguments go

Every AWS example writes them on the constructor — FastMCP(host="0.0.0.0", stateless_http=True) — because it uses the FastMCP bundled inside the mcp SDK. This project uses the standalone fastmcp package, which moved both to run() at 3.0. On fastmcp 3.x the constructor form raises TypeError: FastMCP() no longer accepts 'host' before the server ever binds.

🔥 runtimeSessionId has a minimum length of 33 characters

The obvious value to send is the requisition id — and J2001 comes back as a ValidationException, on GetAgentCard as well as InvokeAgentRuntime. Do not reach for uuid4(): the session id is what stitches five runtimes into one trace, so a random suffix per hop gives you five traces that share nothing. Pad it deterministically:

app/clients/a2a_call.py
SESSION_RE = re.compile(r"^[a-zA-Z0-9][a-zA-Z0-9_-]{32,255}$")

def safe_session_id(candidate: str) -> str:
    """A session id AgentCore will accept, derived from the one you meant."""
    candidate = (candidate or "").strip()
    if SESSION_RE.match(candidate):
        return candidate
    base = re.sub(r"[^a-zA-Z0-9_-]", "-", candidate) or "session"
    if not base[0].isalnum():
        base = f"s{base}"
    return f"{base}-{'0' * 33}"[:64]      # J2001 -> J2001-00...0, still legible

Sessions are isolated but not free: a new session id per request means a new microVM and a cold conversation, while reusing one forever means it never expires. Key it to a business object — a requisition, a chat thread — and you get the right lifetime without thinking about it.

Start with the zip; move to ECR when you cannot. Two things about zips that only fail in AWS:

  • Wheels are built for the container's CPU, not yours. Build with --python-platform aarch64-manylinux2014 --only-binary=:all:. Without the second flag, a package with no arm64 wheel silently compiles from source for the wrong architecture.
  • A runtime has 30 seconds to become healthy, and dependencies spend it. strands-agents[a2a] drags in a PostgreSQL driver and gRPC; aws-opentelemetry-distro installs ~45 instrumentations that the auto-instrumentor walks before your server binds. Prune the first, disable the second. The failure is HTTP 424, which reads like a client error.

5. Capability 2 — Gateway

What it is

A managed MCP server that fronts things which are not MCP servers. Point it at a Lambda function, an OpenAPI spec, a Smithy model or an API Gateway stage, and each one starts answering tools/list and tools/call. It is a protocol adapter, not a router — and that sentence is the entire design rule.

hr-gateway has exactly one target, and it exports four tools:

tools/list
hrdata___find_by_skill        hrdata___list_bench
hrdata___get_requisition      hrdata___record_shortlist

Why the MCP server does not go behind it

This is the decision people get wrong, because "put everything behind the gateway" sounds tidy. hr_skills_mcp is already an MCP server on a URL. Routing it through the Gateway anyway buys one merged tools/list — at the price of a permanent extra hop on the hottest path in the system, since scoring runs once per candidate per requisition.

The rule

Put a thing behind the Gateway when it cannot speak MCP on its own. Everything else is a hop you are paying for and a schema you now maintain twice. Reverse the decision the moment a caller needs those tools without an execution role that can invoke the runtime — a partner team, a desktop client. That is a one-resource change with no code in it, which is exactly why it is safe to defer.

app/clients/tools.py — two clients, one tool list
skills  = _mcp_client(runtime_url(settings.skills_mcp_arn))   # direct
gateway = _mcp_client(settings.gateway_url)                   # translated

# Both blocks are load-bearing. Leaving either one is silent.
with skills, gateway:
    yield skills.list_tools_sync() + gateway.list_tools_sync()
🔥 A dead MCP connection does not raise — it hallucinates

An MCPClient used outside its with block is a dead connection, and nothing errors. The agent still has the tool names in its history, so it quietly starts making plausible answers up. A dead scoring connection looks exactly like a model that has decided to guess. Making the tools unobtainable outside the block — a context manager that yields them — is the only version of this that cannot be got wrong.

The three-underscore prefix

Gateway namespaces every tool as {target}___{tool} — three underscores — so two targets can both export a get_requisition without colliding. The prefix arrives at your Lambda, and you strip it yourself:

app/lambda_fn/handler.py
DELIMITER = "___"      # three, not two: splitting on "__" gets you "_find_by_skill"

def lambda_handler(event, context):
    original = context.client_context.custom["bedrockAgentCoreToolName"]
    tool = original[original.index(DELIMITER) + len(DELIMITER):]

    if tool == "find_by_skill":
        return find_by_skill(event.get("skill", ""), event.get("min_level", 3))
    if tool == "record_shortlist":
        return record_shortlist(event.get("job_id", ""), event.get("employee_id", ""))
    return {"error": f"unknown tool {tool!r}"}

event is a flat map of your input schema's properties — {"skill": "pyspark", "min_level": 4} — not an API Gateway envelope. The client context also carries bedrockAgentCoreGatewayId, bedrockAgentCoreTargetId and bedrockAgentCoreMcpMessageId, all worth logging.

And keep the rule that made the tools usable in the first place: a returned {"error": ...} beats a raised exception, because the return value is the next thing the model reads. Say what to do next, not just that it failed:

app/runtimes/hr_skills_mcp/main.py
return {
    "error": (
        f"unknown employee {employee_id!r} or job {job_id!r}. Call "
        "hrdata___find_by_skill or hrdata___list_bench and use an id it returned."
    )
}

Semantic tool search — decide once, at creation

search_type = "SEMANTIC" adds a search tool, letting an agent ask for "something that looks up an open role" instead of reading every tool description. Four tools do not need it. Set it anyway, because it can only be enabled when the gateway is created — there is no update path, and turning it on later means recreating the gateway and every target under it.

6. Capability 3 — Identity

What it is

Two directions, and they are genuinely different problems. Inbound: who is allowed to invoke this runtime or gateway — an OAuth/OIDC JWT (Cognito, Okta, Entra) or plain IAM. Outbound: what the agent may reach once it is running — its execution role, plus workload identity for acting on behalf of a specific user.

flowchart TB
    H(["a human
recruiter in a browser"]) -->|"Cognito ID token
CUSTOM_JWT"| SUP["hiring_supervisor"]
    SUP -->|"SigV4 · execution role"| SPEC["the three A2A specialists"]
    SPEC -->|"SigV4 · execution role"| MCPR["hr_skills_mcp"]
    SPEC -->|"SigV4 · AWS_IAM"| GWY["hr-gateway"]
    GWY -->|"gateway_iam_role"| LAM["hr-data-fn"]
    LAM -->|"read + write"| S3B[("S3")]
    MCPR -->|"read only"| S3B
Humans authenticate with Cognito; machines authenticate with IAM. The last two edges are the interesting ones — two computes read the same bucket for two different reasons, and exactly one of them can write.

A scoring engine that can edit the employee record is a scoring engine nobody will trust. Splitting Lambda-writes from runtime-reads makes that enforceable rather than merely intended — the IAM policy is the guarantee, not the code review.

🔥 You cannot forward the caller's bearer token to the next runtime

AgentCore consumes the Authorization header at its edge and never passes it to your container, so context.request_headers has no token to reuse. A workload access token is documented as usable only against first-party AgentCore identity services — not for invoking another runtime — and nothing in a container can obtain a Cognito token without shipping a password.

That is why only the supervisor keeps CUSTOM_JWT and the four inner runtimes take SigV4. It is a rule, not a preference: humans authenticate with Cognito, machines with IAM.

SigV4 has a second, quieter advantage: the screener opens its two MCP connections at container start-up, before any request exists — so a bearer token could never have been there to use. Signing each request with the execution role means a connection opened once at boot keeps working, and botocore refreshes credentials without anyone asking.

app/clients/a2a_call.py
class SigV4(httpx.Auth):
    """Sign every request with this container's execution role."""

    # SigV4 signs a hash of the body. Without this, httpx hands the hook a
    # request whose content has not been read yet — the signature would cover
    # an empty body and every call would be a 403.
    requires_request_body = True
TrapWhat happens
Invoking a CUSTOM_JWT runtime with the AWS SDKThe SDK only signs SigV4. You get "Authorization method mismatch" — call it over plain HTTPS with a bearer token instead.
Setting both allowed_audience and allowed_clientsThey check different claims: aud on an ID token, client_id on an access token. Set one. An ID token has no client_id to match.
Changing authorizer_type on a gatewayIt is immutable — the change replaces the gateway and every target under it.

7. Capability 4 — Memory

What it is

Two things wear the name, and they behave differently. Short-term is the event log: every turn becomes a CreateEvent, and ListEvents replays a session — this is what makes a conversation survive a restart. Long-term is asynchronous extraction: after events land, AgentCore consolidates them in the background into memory records, retrieved by semantic search with RetrieveMemoryRecords.

  • sessionId = uuid4() gives you a system that forgets J2001 between Tuesday and Thursday.
  • actorId = "agent" gives you one shared preference profile for the entire recruiting team.

The with block is load-bearing whenever batch_size > 1 — buffered messages that are never flushed are simply lost, and the buffer is not flushed on garbage collection. Same failure shape as leaving an MCPClient context early: everything looks fine until the history has a hole in it.

🔥 A summarisation strategy will paraphrase a blocker into a gap

"Blocked on Apache Spark" becomes "some gaps", and next Tuesday that sentence is what the supervisor reads. Read memory for context; read the current match() for verdicts. Never the other way round. This is the fifth failure mode distribution adds that the laptop version simply did not have.

resource "aws_cloudwatch_log_resource_policy" "xray_spans" {
  policy_name     = "TransactionSearchXRayAccess"
  policy_document = data.aws_iam_policy_document.xray_spans[0].json

# Half two — the switch, which 403s unless half one has landed and propagated.
resource "aws_xray_trace_segment_destination" "cwl" {
  depends_on  = [time_sleep.policy_propagation]

This is the only resource in the stack whose blast radius is the account rather than the stack. It bills — spans are ingested as CloudWatch Logs — and a terraform destroy sets the account back to X-Ray-only, silently stopping traces for anything else relying on it. Hence the opt-out flag.

2 · Instrument each container. Add aws-opentelemetry-distro>=0.18.0 and start the process through the auto-instrumentor:

3 · Keep the session id on every hop. Set X-Amzn-Bedrock-AgentCore-Runtime-Session-Id on the inbound call and the distro propagates it downstream. Because the supervisor's A2A calls carry the same header, one requisition produces one trace across five runtimes.

9. Capabilities 6 & 7 — Code Interpreter and Browser

Two managed, sandboxed tools your agent can call. This project uses neither, and it is worth being explicit about why — the reasoning is the lesson:

Code Interpreter

A sandboxed session where an agent can run code it wrote — pandas over a CSV, a chart, a calculation too fiddly to trust to token prediction. In this domain the obvious candidate is "plot the skill gap across all six requisitions": genuinely open-ended, no fixed function to call.

What it must never be given is match(). That is 40 lines of weighted arithmetic with partial credit below the bar, and a score you cannot reproduce by hand is a score nobody will defend in a hiring review. Deterministic domain logic goes in a tool. Code Interpreter is for the questions you did not anticipate.

Browser

A managed, isolated browser session for systems that only ever had a web UI. Half of HR tooling is like this — a benefits portal or an applicant tracking system with no API you are allowed to use.

Reach for it last. A browser session is the slowest, most brittle and most expensive way to read a fact, and it is the one integration that breaks because someone else shipped a redesign. If an API exists, put it behind the Gateway as an OpenAPI target and you get typed tools instead.

The decision, in one table
The thing you needWhere it belongs
Arithmetic your business must defenda plain function in a tool server (hr_skills_mcp)
An existing Lambda, API or OpenAPI servicea Gateway target
Open-ended analysis over data you just fetchedCode Interpreter
A system with a UI and no APIBrowser — and a note in the risk register

For the final note to be correct, four things must hold across five runtimes — and they are the same four as on the laptop:

1

match() computes the blocker

Arithmetic, in hr_skills_mcp. Never a model call.

2

The screener uses the verdict word exactly

blocked is never softened into "consider with caution".

3

The supervisor passes the text through verbatim

Not summarised. The delegation tool's docstring says so in capitals.

4

And it has no HR access at all, so it cannot look up a substitute fact.

Break any one and you send a warm note to someone who cannot do the job. Note that the last line of defence is not an agent at all — record_shortlist in the Lambda refuses to persist a blocked verdict. The blocker survives to the last possible moment, because everything upstream can paraphrase and the write cannot.

The reviewer gotcha worth reading twice

The compliance reviewer's first version asked the model to call verify_match_claim before judging. It did not — and then rejected a note for claims "not verified by verify_match_claim", asserting a check it had never run, against facts that were all true.

A reviewer that rubber-stamps rejections is as broken as one that rubber-stamps approvals. The fix was to stop asking: a hook extracts the ids, runs match(), and appends the record to the request before the model sees it. Same rule as everywhere else here — arithmetic should not be optional.

11. Putting a chat box on it

Everything above is reachable from a terminal. Getting it in front of a browser is shaped by two constraints that between them rule out every simpler design:

  • A browser cannot call InvokeAgentRuntime. It is a SigV4-signed AWS API call, and AWS service endpoints send no CORS headers — so the tempting design, where a Cognito identity pool hands the page real credentials and the JS SDK calls the runtime directly, dies at the preflight rather than at the permission check. Something server-side must make the call.
  • That something cannot be Python. Lambda response streaming works on Node.js managed runtimes and custom runtimes only. A full run is three delegations and a minute or two, so buffering it into one JSON reply means a browser showing nothing until the end.

Chunk boundaries are not frame boundaries

EventSource cannot send an Authorization header, so the client is fetch plus a manual reader — which puts SSE framing in your hands. A single read() can deliver half a frame or three and a half. Parsing each chunk as one message passes every manual test against localhost and drops events in production. Test the parser with splits mid-JSON, between the two terminating newlines, and one byte at a time.

🔥 A fixed S3 key means your code never ships

A runtime references its code as bucket + prefix. Rebuild the zip under the same key and the bytes change while the runtime's arguments do not — no diff, no update, no new version, and the container keeps running what it started with. terraform apply even reports the S3 object updating, so it looks like a successful deploy. Put the content hash in the key. The tell is an agent_runtime_version that never moves:

terminal
terraform state show 'module.runtimes.aws_bedrockagentcore_agent_runtime.supervisor' \
  | grep agent_runtime_version
Do not declare a DEFAULT endpoint

CreateAgentRuntime makes one as part of the same call, so an endpoint resource named DEFAULT does not adopt it — it tries to create a second, and every apply fails with ConflictException: An endpoint with the specified name already exists. Waiting does not help; the endpoint really does exist. Declare one only for a named alias like prod that you want to repoint across versions.

Memory strategies, and a naming trap that costs an afternoon of searching:

terraform/04_memory/main.tf
resource "aws_bedrockagentcore_memory_strategy" "facts" {
  name                = "candidate_facts"    # no hyphens allowed in the name
  memory_id           = aws_bedrockagentcore_memory.hiring_desk.id
  type                = "SEMANTIC"           # boto3 calls this semanticMemoryStrategy
  namespace_templates = ["/requisitions/{sessionId}/facts"]
}

Terraform's type values are not the API's field names. Terraform wants SEMANTIC / SUMMARIZATION / USER_PREFERENCE / EPISODIC / CUSTOM; boto3 wants semanticMemoryStrategy / summaryMemoryStrategy / userPreferenceMemoryStrategy nested under memoryStrategies. You will meet both, often in the same afternoon — and note that "summary" and SUMMARIZATION are two words for one thing.

16. Check yourself

Your A2A agent deploys successfully but every delegation to it times out. What do you check first?
The protocol determines the port, and nothing tells you when you get it wrong: the container starts, fails its health check, and the caller sees a timeout. A2A is 9000 at /, MCP 8000 at /mcp, HTTP 8080 at /invocations. Check this before anything else.
You have a Lambda and an existing MCP server. Which goes behind the Gateway?
The Gateway is a protocol adapter, not a router. Put a thing behind it when it cannot speak MCP on its own. Routing the MCP server through anyway costs a permanent extra hop on the hottest call path plus a second copy of its schema in HCL — in exchange for merging two tools/list responses that the client merges for free. Reverse it only when a caller needs those tools without an execution role that can invoke the runtime.
Why is sessionId the requisition id rather than a fresh UUID per request?
A UUID works for all three mechanisms and is useless to the recruiter asking "what happened on J2001 last week". session_id is a business key, not plumbing. It also decides microVM lifetime: a new id per request means a cold conversation every time, one id forever means it never expires. (Do remember the 33-character minimum — pad it deterministically, do not replace it.)
Your agent answers normally, logs look fine, and the GenAI Observability dashboard is empty. Most likely cause?
Logs working proves nothing about traces: they are separate deliveries, and spans go to X-Ray rather than CloudWatch Logs. Both failure modes are non-fatal — the agent answers and every span export is a 403 visible only in the container's own log. Check Transaction Search first (it is two operations, not one), then xray:PutTraceSegments on the runtime role.
A SUMMARIZATION memory strategy records "Rahul had some gaps for J2001". Next week the supervisor reads it. What is the bug?
Rahul is missing Apache Spark, which J2001 marks mandatory — he is blocked and cannot be shortlisted however high the score. Every hop is a chance to paraphrase, and paraphrase drops the blocker. Read memory for context; re-derive verdicts from the arithmetic. This is why the facts travel between agents verbatim, and why the Lambda refuses to persist a blocked shortlist.

Terraform Use Case Catalogue

Use Cases code-first 27 scenarios ~105 min

Twenty-seven self-contained Terraform scenarios, ordered as a learning path. Each one opens with the problem it solves, then shows the code that solves it, then explains the parts that matter.

Scenarios 1–21 take you from a single resource to a fully modularised two-tier application. Scenarios 22–27 close the gaps those leave — between them the first twenty-one use only eight block types, three meta-arguments and three built-in functions, which is enough to read most Terraform and not enough to write it well.

📘 How to use this page

Every scenario is an independent root module. Work through one at a time: read the use case, read the code, then run terraform init → plan → apply → destroy in that scenario's own directory. Never run Terraform from the parent directory — each scenario has its own provider and its own state.

⚠️ These are teaching examples

Scenarios 1–21 target AWS us-west-2 (Oregon) on t3.micro — the free-tier-eligible type in this region — with the Amazon Linux 2023 AMI ami-0b76d82b547c3c077. They are deliberately minimal — see Caveats before reusing any of this in a real project.

🧭 Terraform 1.15 is the baseline

Scenarios 22–27 declare required_version = ">= 1.15", so a too-old CLI gives you a clear message rather than a baffling parse error. Check yours:

terminal
terraform version                        # expect v1.15.x or newer
brew upgrade hashicorp/tap/terraform     # if it isn't

Which release introduced each thing these scenarios use — all of it available on 1.15:

FeatureIntroduced in
check {} blocks, import {} blocks1.5
.tftest.hcl / terraform test1.6 (1.7 for mock_provider)
removed {} blocks1.7
Cross-variable validation conditions — used in scenario 26, and the oldest release these scenarios genuinely need1.9
S3 backend use_lockfile — native state locking, no DynamoDB table1.10
ephemeral resources and variables — values that never reach state1.10

Note the gap: the strict minimum this code needs is 1.9, but it is pinned at 1.15 as a course baseline. That is a deliberate team choice, not a technical requirement — and it is the kind of decision scenario 22 is about. If you are publishing a module for other people, pin the true minimum instead, or you lock out consumers for no reason.

💰 This tier is cheaper than the basics

Scenarios 1–21 run EC2, RDS and Elastic IPs, all of which bill by the hour — public IPv4 has been charged hourly since February 2024. Everything here uses resources that are free to exist: S3 buckets, SSM Standard parameters, CloudWatch log groups, IAM policies and terraform_data. Log groups always set retention_in_days; buckets always set force_destroy = true.

1. Your First Resource

Use case

You want to create a piece of cloud infrastructure — here a network (VPC) — without opening the AWS console. You need the smallest possible file that Terraform will accept, so you can see the whole init → plan → apply → destroy loop end to end.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_vpc" "myvpc" {
    cidr_block = "10.0.0.0/16"
}

Two blocks is the whole program. The provider block says which cloud to talk to and where. The resource block declares one thing you want to exist.

Resource syntax is always resource "<TYPE>" "<LOCAL_NAME>" { … }. The type (aws_vpc) comes from the provider and decides what arguments are valid. The local name (myvpc) is only how Terraform refers to it — it never appears in AWS.

terminal
terraform init      # download the AWS provider
terraform plan      # preview: 1 to add, 0 to change, 0 to destroy
terraform apply     # create it (type "yes")
terraform destroy   # tear it down

2. EC2 Instance

Use case

You need a virtual server to run something on. This is the same two-block shape as before, proving the pattern generalises: change the resource type and the arguments, and you get a completely different piece of infrastructure.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
}

ami is the machine image (the operating system to boot) and instance_type is the hardware size. There's no key pair and no security group here — this is the bare minimum AWS will accept to start an instance.

Why this AMI and this instance type

The same image has a different ID in every region, so hardcoding one — as these examples do — locks the config to us-west-2. See Caveats for the data-source version that works anywhere.

The type is t3.micro rather than the more familiar t2.micro for two independent reasons: in us-west-2 AWS reports t2.micro as not free-tier eligible while t3.micro is, and Amazon Linux 2023 requires ENA networking, which the older Xen-based t2 family doesn't support. Free-tier eligibility differs by region — verify it before copying this elsewhere.

3. Security Groups & Implicit Dependencies

Use case

Your server needs a firewall rule so traffic can reach it. But a security group has to exist before an instance can be attached to it — so how do you tell Terraform the correct order? The answer: you don't. Reference one resource from another and Terraform derives the order itself.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    security_groups = [aws_security_group.webtraffic.name]   # <-- implicit dependency
}

resource "aws_security_group" "webtraffic" {
    name = "Allow HTTPS"

    ingress {
        from_port = 443
        to_port = 443
        protocol = "TCP"
        cidr_blocks = ["0.0.0.0/0"]
    }

    egress {
        from_port = 443
        to_port = 443
        protocol = "TCP"
        cidr_blocks = ["0.0.0.0/0"]
    }
}

Because the instance reads aws_security_group.webtraffic.name, Terraform builds a dependency graph and creates the security group first, automatically. On destroy it reverses the order.

The order the blocks appear in the file is irrelevant — the instance is written above the security group it depends on and it still works. Terraform resolves ordering from references, never from position.

ingress is inbound traffic, egress is outbound. Each nested block opens a port range from a set of source addresses; 0.0.0.0/0 means "the entire internet".

4. Elastic IP & Outputs

Use case

A default EC2 public IP changes every time the instance restarts. You want a permanent address — and, just as importantly, you want Terraform to tell you what that address is once it's built, instead of hunting for it in the console.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
}

resource "aws_eip" "elasticeip" {
    instance = aws_instance.ec2.id
}

output "EIP" {
    value = aws_eip.elasticeip.public_ip
}

An output block surfaces a value that only exists after the resource is created. Terraform prints it at the end of apply, and you can re-read it from state at any time without applying again.

terminal
terraform apply
terraform output          # show all outputs
terraform output EIP      # show just this one

Outputs have a second, bigger job: they are how a child module returns values to whatever called it. That becomes the backbone of scenarios 14 and 21.

5. IAM User, Policy & Attachment

Use case

You need to grant a person or service a specific set of AWS permissions. That takes three separate things — an identity, a permissions document, and the link between them — and it's a good example of embedding raw JSON inside HCL.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_iam_user" "myUser" {
    name = "terraform-user"
}

resource "aws_iam_policy" "customPolicy" {
    name = "GlacierEFSEC2"

    policy = <<EOF
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "VisualEditor0",
            "Effect": "Allow",
            "Action": [
                "ec2:AuthorizeSecurityGroupIngress",
                "ec2:CreateVpc",
                "ec2:StopInstances",
                "ec2:CreateVolume",
                "glacier:ListVaults",
                "glacier:CompleteMultipartUpload",
                "elasticfilesystem:ClientMount"
            ],
            "Resource": "*"
        }
    ]
}
EOF
}

resource "aws_iam_policy_attachment" "policyBind" {
    name = "attachment"
    users = [aws_iam_user.myUser.name]
    policy_arn = aws_iam_policy.customPolicy.arn
}

The real policy in the course code lists roughly 70 EC2, Glacier and EFS actions; it's trimmed here to keep the shape readable.

The heredoc syntax <<EOF … EOF embeds a multi-line string verbatim — ideal for a JSON policy document you've copied out of the AWS policy generator. The closing EOF must sit at the start of its own line.

The attachment resource is the join: it takes a list of users and a policy ARN. Note it reads .arn from the policy — another implicit dependency, so all three resources are created in the right order.

Prefer the non-exclusive attachment

aws_iam_policy_attachment is exclusive — it detaches the policy from any identity not listed in its arguments, which can silently revoke access elsewhere in the account. For real work use aws_iam_user_policy_attachment.

6. Managed Database (RDS)

Use case

Your application needs a database, and you'd rather not run one yourself. RDS gives you a managed engine; Terraform gives you a repeatable definition of it. This scenario also shows a resource with a meaningful number of required arguments.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_db_instance" "myRDS" {
    db_name = "myDB"
    identifier = "my-first-rds"
    instance_class = "db.t3.micro"
    engine = "mariadb"
    engine_version = "11.4"
    username = "bob"
    password = "password123"
    port = 3306
    allocated_storage = 20
    skip_final_snapshot = true
}

Two names are in play and they mean different things: identifier is what AWS calls the instance, while db_name is the database created inside the engine.

skip_final_snapshot = true lets terraform destroy finish without prompting for a snapshot name. That's convenient in a lab and dangerous in production — leave it false for anything you'd miss.

Never hardcode a password

The password here is inline for demo purposes. Anything you write in a .tf file is also written to the state file in plain text. Use a sensitive variable, AWS Secrets Manager, or manage_master_user_password.

7. Explicit Dependencies

Use case

Your web server must not start until the database server exists — but nothing in the web server's configuration actually references the database, so Terraform has no way to infer the ordering and would happily build both at once. You need to state the dependency by hand.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_instance" "db" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
}

resource "aws_instance" "web" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"

    depends_on = [aws_instance.db]   # <-- explicit: db must exist first
}

depends_on takes a list of resource addresses and forces Terraform to finish those before starting this one. Compare with scenario 3, where the dependency came free from a reference.

Reach for it only when an implicit reference isn't available. It's a blunter instrument: it can't express which attribute you need, so it serialises more of the graph than necessary and slows applies down.

8. Variable Types

Use case

Hardcoded values mean copying the whole file to change one setting. Variables turn a config into something parameterised and reusable. This scenario is a reference sheet: every variable type Terraform supports, in one place.

hcl
variable "vpcname" {          # string
  type    = string
  default = "myvpc"
}

variable "sshport" {          # number
  type    = number
  default = 22
}

variable "enabled" {          # bool — type inferred from the default
  default = true
}

variable "mylist" {           # list — ordered, same type throughout
  type    = list(string)
  default = ["Value1", "Value2"]
}

variable "mymap" {            # map — key/value lookup
  type = map
  default = {
    Key1 = "Value1"
    Key2 = "Value2"
  }
}

variable "mytuple" {          # tuple — fixed length, mixed types
  type    = tuple([string, number, string])
  default = ["cat", 1, "dog"]
}

variable "myobject" {         # object — named attributes, mixed types
  type = object({ name = string, port = list(number) })
  default = {
    name = "terraform-user"
    port = [22, 25, 80]
  }
}

variable "inputname" {        # no default -> Terraform prompts at apply time
  type        = string
  description = "Set the name of the VPC"
}

Variables are consumed with var.<name>:

hcl
resource "aws_vpc" "myvpc" {
  cidr_block = "10.0.0.0/16"

  tags = {
    Name = var.inputname
  }
}

output "vpcid" {
  value = aws_vpc.myvpc.id
}

A variable with no default and no supplied value makes Terraform stop and prompt interactively. That's fine at a keyboard and fatal in CI, so supply it explicitly instead:

terminal
terraform apply -var="inputname=MyVPC"

export TF_VAR_inputname=MyVPC     # any TF_VAR_* env var becomes a variable
terraform apply

9. Count — Replicating Resources

Use case

You need three identical servers. Copy-pasting the resource block three times works but is unmaintainable — every future change has to be made three times. count turns one block into N.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    count = 3
}

The resource is now a list, addressed by index: aws_instance.ec2[0], [1], [2]. Anything referencing it must pick an element or use a splat (scenario 12).

Index shifting

Because count addresses are positional, removing an item from the middle of a count-driven list renumbers everything after it — and Terraform will destroy and recreate resources that you never touched. Scenario 15 shows the fix.

10. Variable Files per Environment

Use case

Test needs 2 servers; production needs 50. You want one configuration — not a copied folder per environment — with the differences pulled out into small values files you can swap at the command line.

hcl
provider "aws" {
    region = "us-west-2"
}

variable "number_of_servers" {
    type = number
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    count = var.number_of_servers
}

The two values files hold nothing but the differences:

test values
number_of_servers = 2
prod values
number_of_servers = 50
terminal
terraform apply -var-file="test.tfvars"    # 2 instances
terraform apply -var-file="prod.tfvars"    # 50 instances

A values file named terraform.tfvars (or anything ending .auto.tfvars) is loaded automatically. Any other name needs -var-file — which is exactly what makes the environment choice explicit and visible in your shell history.

One state, two environments

Applying both files in the same directory doesn't give you two environments — the second apply rewrites the first, because they share one state file. Real separation comes from separate state: workspaces, separate backends, or separate directories.

11. Feature Switch — Conditional Resources

Use case

Some infrastructure should only exist in production — a bastion host, a monitoring box, a read replica. You want a single config where that resource is created in prod and completely absent everywhere else.

hcl
provider "aws" {
    region = "us-west-2"
}

variable "environment" {
    type = string
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    count = var.environment == "prod" ? 1 : 0
}

This is the classic Terraform feature toggle. There is no if statement in HCL — instead you put a ternary on count, where 0 means "don't create this at all".

prod values
number_of_servers = 50
environment="prod"
test values
number_of_servers = 2
environment="test"
terminal
terraform apply -var-file="prod.tfvars"    # 1 instance created
terraform apply -var-file="test.tfvars"    # 0 instances — resource skipped entirely

The resource still uses list addressing even when there's one of it, so referencing it elsewhere means aws_instance.ec2[0].id — which will error in the environments where the count is zero. That's the main friction of this pattern.

12. count.index & Splat Expressions

Use case

You want three database servers, but each should be named differently — and afterwards you need the private IP of every one of them as a single list. Plain count gives you copies; this scenario makes each copy distinct and then collects an attribute across all of them.

The caller passes a list of names into a module:

hcl · root
provider "aws" {
    region = "us-west-2"
}

module "db" {
    source = "./db"
    server_names = ["mariadb","mysql","mssql"]
}

output "private_ips" {
    value = module.db.PrivateIP
}

The module derives its own count from the length of that list:

hcl · db module
variable "server_names" {
    type = list(string)
}

resource "aws_instance" "db" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    count = length(var.server_names)          # 3 instances

    tags = {
        Name = var.server_names[count.index]  # "mariadb", "mysql", "mssql"
    }
}

output "PrivateIP" {
    value = [aws_instance.db.*.private_ip]    # splat: the attribute from every instance
}

Three techniques stack up here:

TechniqueWhat it buys you
length(var.server_names)The count is derived from the data. Add a fourth name and you get a fourth server — no other edit.
count.indexThe 0-based iteration number, used to pick this instance's matching name out of the list.
aws_instance.db.*.private_ipThe splat expression — reads one attribute from every instance and returns them as a list.

Without the splat you'd have to write out aws_instance.db[0].private_ip, [1], [2] — and update it every time the count changed.

13. Dynamic Blocks

Use case

Your security group needs to open eight ports. Writing eight near-identical ingress blocks by hand is tedious and error-prone, and the port list should really be configurable. But count can't help — these are nested blocks inside a resource, not whole resources. That's what dynamic is for.

hcl
provider "aws" {
    region = "us-west-2"
}

variable "ingressrules" {
    type = list(number)
    default = [80,443]
}

variable "egressrules" {
    type = list(number)
    default = [80,443,25,3306,53,8080]
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    security_groups = [aws_security_group.webtraffic.name]
}

resource "aws_security_group" "webtraffic" {
    name = "Allow HTTPS"

    dynamic "ingress" {
        iterator = port
        for_each = var.ingressrules
        content {
            from_port   = port.value
            to_port     = port.value
            protocol    = "TCP"
            cidr_blocks = ["0.0.0.0/0"]
        }
    }

    dynamic "egress" {
        iterator = port
        for_each = var.egressrules
        content {
            from_port   = port.value
            to_port     = port.value
            protocol    = "TCP"
            cidr_blocks = ["0.0.0.0/0"]
        }
    }
}

Four parts to the syntax:

PartMeaning
dynamic "ingress"The name of the nested block you're generating.
for_eachThe collection to iterate over.
iterator = portRenames the iteration variable (it defaults to the block name). The current element is port.value.
content { }The block body produced on each pass.

Twelve lines produce two ingress rules and six egress rules — and adding a port is now a one-number edit to a variable. Compare against the hand-written pair of blocks in scenario 3.

14. Modules

Use case

You've written a good EC2 configuration and now three projects want it. Copying the file into each one means three places to fix every bug. A module packages the configuration behind a small interface — inputs in, outputs out — so callers reuse it instead of duplicating it.

hcl · root
provider "aws" {
    region = "us-west-2"
}

module "ec2module" {
    source  = "./ec2"          # local path; can also be a registry or git URL
    ec2name = "Name From Module"
}

output "module_output" {
    value = module.ec2module.instance_id
}
hcl · ec2 module
variable "ec2name" {
    type = string
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    tags = {
        Name = var.ec2name
    }
}

output "instance_id" {
    value = aws_instance.ec2.id
}

The module contract has exactly three rules:

  1. Inputs — the child declares variable "ec2name"; the caller sets it as an argument inside the module block.
  2. Outputs — the child declares output "instance_id"; the caller reads it as module.ec2module.instance_id. Nothing is visible to the caller unless it's an output.
  3. No provider block in the child — it inherits the provider configured by the root module.
Re-run init after touching a module

Adding, moving, or changing the source of a module block requires terraform init again — Terraform has to fetch and link the source before it can plan. "My module change did nothing" is almost always a missing init.

15. for_each on a Module

Use case

You want the same stack in dev, test, and prod. count = 3 would build three of them — but then deleting the middle environment renumbers the other two and Terraform destroys and rebuilds infrastructure you never touched. You need instances keyed by name, not by position.

hcl · root
provider "aws" {
    region = "us-west-2"
}

module "ec2" {
    source   = "./ec2"
    for_each = toset(["dev", "test", "prod"])
}
hcl · ec2 module
resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
}

toset() converts the list into a set so each element becomes a stable string key rather than a position. The instances are addressed as module.ec2["dev"], module.ec2["test"], module.ec2["prod"].

That's the whole point. Remove "test" from the list and only module.ec2["test"] is destroyed — "dev" and "prod" keep their keys and are left completely alone. Inside the child, the current key is available as each.key, which is how you'd tag each instance with its environment name.

Terraform 0.13+

count and for_each on module blocks were added in Terraform 0.13. Before that, repeating a module meant writing the block out once per environment.

Rule of thumb: for_each for named collections; count only for genuinely identical copies or an on/off toggle.

16. Error Handling

Use case

You will write broken Terraform. This scenario is broken on purpose so you can practise the thing that actually matters: reading the error, finding the line, and fixing it — before you burn an apply against real infrastructure.

hcl · intentionally broken
provider "aws" {
    region = "us-west-2"
}

resource "aws_instance" "ec2" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = var.type     # <-- undeclared variable
}

The config reads var.type, which is never declared anywhere. Run the cheapest check first:

terminal
terraform validate    # catches it without credentials or a network call
terraform plan
output
Error: Reference to undeclared input variable

  on main.tf line 7, in resource "aws_instance" "ec2":
   7:     instance_type = var.type

An input variable with the name "type" has not been declared.

The fix is to add the missing declaration:

hcl · the fix
variable "type" {
    type    = string
    default = "t3.micro"
}

Terraform's error messages improved sharply in 0.12+ — they name the file, the line, the expression, and usually the fix. Make terraform validate a reflex: it's the fastest feedback loop you have, since it needs no AWS credentials and touches nothing.

17. Importing Existing Infrastructure

Use case

Someone built a VPC by clicking around the console last year. You now want Terraform to manage it — without destroying and rebuilding it. Import brings existing infrastructure under management by teaching Terraform's state file that a real resource corresponds to a block in your config.

hcl
provider "aws" {
    region = "us-west-2"
}

resource "aws_vpc" "myvpc" {
    cidr_block = "10.0.0.0/16"
}

resource "aws_vpc" "myvpc2" {
    cidr_block = "192.168.0.0/24"
}
terminal
# 1. Write the resource block first — Terraform will not generate it for you
# 2. Map the real AWS resource ID onto that address
terraform import aws_vpc.myvpc2 vpc-0a1b2c3d4e5f67890

# 3. Confirm your config matches reality — the goal is "No changes"
terraform plan

Two things to internalise:

  • terraform import only writes to state. It does not write HCL — you author the resource block yourself, by hand, before importing.
  • If plan shows changes after an import, your HCL doesn't match the real resource. Keep adjusting the HCL until the plan is clean. Applying a dirty plan here means modifying live infrastructure to match a config you only half-wrote.
Terraform 1.5+ makes this easier

Newer versions add a declarative import { } block plus terraform plan -generate-config-out=…, which scaffolds the HCL for you — a large improvement over hand-writing blocks for dozens of existing resources.

18. Remote State on S3

Use case

By default the state file sits on your laptop. Your colleague's Terraform therefore has no idea what you've built, will try to create it again, and whoever applies last wins. A backend moves state into shared storage so a team can work on the same infrastructure.

hcl · backend
terraform {
    backend "s3" {
        key        = "terraform/tfstate.tfstate"
        bucket     = "demo-remote-backend-2020"
        region     = "us-west-2"
        access_key = "your_access_key"
        secret_key = "your_secret_key"
    }
}
hcl · config
provider "aws" {
    region = "us-west-2"
}

resource "aws_vpc" "test" {
    cidr_block = "10.0.0.0/16"
}
terminal
terraform init    # offers to copy your existing local state up to the bucket

Four things that catch people out:

  • The S3 bucket must already exist. A backend can't create its own storage — it's needed before Terraform has any state to work from.
  • The backend block cannot use variables or interpolation. Values must be literals, or passed at init time with terraform init -backend-config=….
  • Add state locking so two people can't apply at once — use_lockfile = true on current versions, or a DynamoDB table on older ones.
  • Don't commit credentials. Omit access_key/secret_key entirely and let the AWS credential chain resolve them from environment variables, your credentials file, or an instance role.
State files contain secrets

State stores every resource attribute in plain text — including that RDS password from scenario 6. Never commit terraform.tfstate, and treat the bucket holding it as a secret store: private, encrypted, versioned, access-logged.

20. Challenge 2 — A Full Stack in One File

Use case · challenge

Your task: build a two-tier application. A database server and a web server; the web server runs Apache and serves a page; a security group opens ports 80 and 443; the web server has a permanent public IP; and the run finishes by printing the database's private IP and the website's public IP.

This is the first scenario that combines everything so far — security groups, bootstrap scripts, dynamic blocks, Elastic IPs and outputs — in a single configuration.

hcl · solution
provider "aws" {
    region = "us-west-2"
}

resource "aws_instance" "db" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"

    tags = {
        Name = "DB Server"
    }
}

resource "aws_instance" "web" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    security_groups = [aws_security_group.web_traffic.name]
    user_data = file("server-script.sh")     # bootstrap script, runs at first boot
    tags = {
        Name = "Web Server"
    }
}

resource "aws_eip" "web_ip" {
    instance = aws_instance.web.id
}

variable "ingress" {
    type = list(number)
    default = [80,443]
}

variable "egress" {
    type = list(number)
    default = [80,443]
}

resource "aws_security_group" "web_traffic" {
    name = "Allow Web Traffic"

    dynamic "ingress" {
        iterator = port
        for_each = var.ingress
        content {
            from_port   = port.value
            to_port     = port.value
            protocol    = "TCP"
            cidr_blocks = ["0.0.0.0/0"]
        }
    }

    dynamic "egress" {
        iterator = port
        for_each = var.egress
        content {
            from_port   = port.value
            to_port     = port.value
            protocol    = "TCP"
            cidr_blocks = ["0.0.0.0/0"]
        }
    }
}

output "PrivateIP" {
    value = aws_instance.db.private_ip
}

output "PublicIP" {
    value = aws_eip.web_ip.public_ip
}

The bootstrap script installs and starts Apache the first time the instance boots:

bash · bootstrap script
#!/bin/bash
sudo dnf -y update
sudo dnf install -y httpd
sudo systemctl start httpd
sudo systemctl enable httpd
echo "<h1>Hello from Terraform</h1>" | sudo tee /var/www/html/index.html

file(…) reads the script off disk and hands it to user_data, where cloud-init executes it on first boot. Browse to the PublicIP output and the page is there — infrastructure and configuration from one apply.

user_data runs once

Cloud-init runs the script on first boot only. Editing the script won't change a running instance — Terraform will show a plan that replaces the instance instead. That's expected; it's why this pattern suits bootstrapping rather than ongoing configuration management.

21. Challenge 3 — The Same Stack, Modularised

Use case · challenge

Your task: take challenge 2 — which works, but is one long file where everything knows about everything else — and refactor it into modules, without changing what gets built.

This is the capstone. It demonstrates module composition: modules that call other modules and pass values between them, with each piece reusable on its own.

The stack splits into four modules:

ModuleOwnsExposes
rootthe provider; calls db and webPrivateIP, PublicIP
dbthe database instancePrivateIP
webthe web instance; calls sg and eippub_ip
sgthe security groupsg_name
eipthe elastic IPPublicIP (takes instance_id)

The root becomes almost empty — it wires two modules together and re-exports their results:

hcl · root
provider "aws" {
    region = "us-west-2"
}

module "db" {
    source = "./db"
}

module "web" {
    source = "./web"
}

output "PrivateIP" {
    value = module.db.PrivateIP
}

}

The db module is the simplest — one resource, one output:

hcl · db module
resource "aws_instance" "db" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"

        Name = "DB Server"
    }

    value = aws_instance.db.private_ip

The web module is where composition happens — it calls two further modules and feeds its own instance ID into one of them:

hcl · web module
resource "aws_instance" "web" {
    ami = "ami-0b76d82b547c3c077"
    instance_type = "t3.micro"
    security_groups = [module.sg.sg_name]          # consumes the sg module's output
    user_data = file("./web/server-script.sh")     # path relative to the ROOT module

        Name = "Web Server"
    }

}

    source = "../sg"
}

    value = module.eip.PublicIP                    # re-exports a nested module's output
}

The sg module is the dynamic-block security group from scenario 13, now exposing its name so callers can attach to it:

hcl · sg module

}

The eip module is the best example of a genuinely reusable module — it knows nothing about web servers, only that it needs an instance ID:

hcl · eip module
variable "instance_id" {
    type = string
}

resource "aws_eip" "web_ip" {
    instance = var.instance_id
}

output "PublicIP" {
    value = aws_eip.web_ip.public_ip
}

What this scenario teaches

  1. Output chaining. The public IP travels up four levels: aws_eip.web_ip.public_ip → module.eip.PublicIP → module.web.pub_ip → the root's PublicIP. Every layer must explicitly re-export — outputs are not inherited automatically. Miss one link and the value is invisible at the top.
  2. Relative sources. The root reaches down with ./db, while the web module reaches sideways to its siblings with ../eip and ../sg.
  3. file() paths resolve against the root module, not the file containing the call — which is why the web module has to write ./web/server-script.sh even though the script sits right next to it. Using "${path.module}/server-script.sh" is the robust alternative: it resolves relative to the module's own directory and keeps working wherever the module is called from.
  4. Reusability comes from narrow interfaces. The eip module takes an instance_id and returns an IP. Because it makes no assumptions about what it's attached to, it can be dropped into any project unchanged.

22. Version pinning

Use case

"It worked last week." Between then and now a provider released a new major, a module moved a branch, and a colleague ran a different CLI. Pin all three so the config you wrote is the config that runs.

You should already know: basic scenario 14 (modules), basic scenario 18 (backends).

hcl
terraform {
  # The CLI itself, pinned to the course baseline so everyone gets identical
  # behaviour and a clear message instead of a baffling parse error.
  #
  # Worth noticing, since this scenario is about pinning honestly: the OLDEST
  # release that can actually run these scenarios is 1.9 — that is when a
  # validation block could first reference another variable (scenario 26).
  # Everything else here works on 1.5. Pinning the baseline rather than the
  # true minimum is a deliberate team choice, not a technical requirement;
  # if you are publishing a MODULE for others, pin the true minimum instead,
  # or you lock out consumers for no reason.
  required_version = ">= 1.15"

  required_providers {
    aws = {
      source = "hashicorp/aws"

      # "~>" is the pessimistic constraint operator. On a two-part version it
      # allows the last part to move: ~> 6.0 means >= 6.0.0 and < 7.0.0.
      # You get bug fixes and new features; you never get a breaking major.
      version = "~> 6.0"
    }

    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}
WrittenMeans
= 6.1.0exactly this, nothing else
>= 6.1.0this or anything newer, including the next major — rarely what you want
~> 6.1>= 6.1.0, < 7.0.0 — minors and patches move, majors don't
~> 6.1.0>= 6.1.0, < 6.2.0 — only patches move

The provider block is where cross-cutting configuration lives:

hcl
provider "aws" {
  region = var.region

  # Applied to every taggable resource this provider creates. Set them once
  # here and you never write them on an individual resource again.
  default_tags {
    tags = {
      Project   = "terraform-course"
      Scenario  = "22-versions-pinning"
      ManagedBy = "terraform"
    }
  }

  # Tags that something *else* writes onto our resources — EKS, Config rules,
  # cost tooling. Without this, every plan would show a diff trying to strip
  # them back off.
  ignore_tags {
    key_prefixes = ["kubernetes.io/", "aws:"]
  }
}

The bucket in this scenario deliberately has no tags block. Every tag on it arrives from default_tags — the effective_tags output reads tags_all (resource tags merged with provider defaults) rather than tags, which would be empty.

The lock file

terraform init writes .terraform.lock.hcl recording the exact version and checksums it chose. Commit it — that is what makes a colleague's init resolve identically to yours.

terminal
terraform init                                   # writes the lock file
terraform providers                              # what this config requires
terraform init -upgrade                          # re-resolve within constraints, rewrite the lock
terraform providers lock -platform=linux_amd64 \
                        -platform=darwin_arm64   # add checksums for CI's platform too

That last command matters more than it looks: a lock file created on a Mac has no checksums for Linux, so CI fails on a checksum mismatch. Record every platform your team builds on.

Pinning modules

Same constraint syntax, different argument per source type:

hcl
# Registry module — `version` is a separate argument:
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"
}

# Git module — there is no `version` argument; pin with a ref in the URL.
# Always pin to a TAG, never a branch. `?ref=main` is not a pin.
module "vpc" {
  source = "git::https://github.com/acme/tf-modules.git//vpc?ref=v1.2.0"
}

Local modules cannot be versioned at all — they are whatever is on disk, which is exactly why they belong to one repo rather than to a team.

23. Data sources and locals

Use case

Your config has an account ID typed into it, a region repeated eleven times, and an AMI ID that expires. Ask AWS for those at plan time instead, and compose the derived names in one place.

You should already know: basic scenario 8 (variables), scenario 22 (pinning).

A resource block says make this exist and keep it that way. A data block says go and find out, I am not managing it. Data sources are re-read on every plan, so they always reflect reality.

hcl
# Who am I? Returns the account ID of whatever credentials are in use — the
# reliable way to build globally-unique names without hardcoding an account.
data "aws_caller_identity" "current" {}

# Where am I? Note: in AWS provider 6.x the attribute is `.region`.
# The older `.name` still resolves but is deprecated.
data "aws_region" "current" {}

# Which availability zones can I actually use *in this account*? This differs
# per account, which is why hardcoding "us-west-2a" eventually breaks.
data "aws_availability_zones" "available" {
  state = "available"
}

# The current Amazon Linux 2023 AMI, straight from the parameter AWS maintains.
# This is the fix for the hardcoded AMI in the basic scenarios: that ID is
# region-locked and goes stale, this one never does.
data "aws_ssm_parameter" "al2023" {
  name = "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64"
}

A local is not an input and not an output — it is a named expression, so a rule that appears in fifteen places is written down once:

hcl
locals {
  account_id = data.aws_caller_identity.current.account_id
  region     = data.aws_region.current.region

  # "${...}" is string interpolation — expressions evaluated inside a string.
  name_prefix = "${var.app}-${var.env}"

  # Globally unique without hardcoding anything.
  bucket_name = "tf-course-23-${local.name_prefix}-${local.account_id}"

  # Locals can reference other locals, so long as there is no cycle.
  az_names = data.aws_availability_zones.available.names
  az_count = length(local.az_names)
}

path.module is the directory of this module, not the directory you were standing in when you ran Terraform. Always prefer it over a bare relative path — a bare path is exactly what breaks when a module is called from somewhere else, which basic scenario 21 runs straight into:

hcl
resource "aws_ssm_parameter" "app_config" {
  name  = "/tf-course/${local.name_prefix}/config"
  type  = "String"
  value = file("${path.module}/config/app-config.json")
}
A provider-6.x trap

Every aws_ssm_parameter value is marked sensitive, so a root output reading .value fails with "Output refers to sensitive values". For a parameter that genuinely isn't a secret — a public AMI pointer — read .insecure_value instead. Otherwise mark the output sensitive = true.

Explore the values interactively:

terminal
terraform console
> data.aws_caller_identity.current.account_id
> local.name_prefix
> length(data.aws_availability_zones.available.names)

24. for_each on resources

Use case

Three teams each need a log group and a parameter. Later a fourth arrives and a second leaves. You want adding a team to be a one-line change that touches nothing else.

You should already know: basic scenario 9 (count), basic scenario 15 (for_each on a module), scenario 23 (locals).

This is the biggest single gap in the basic catalogue: count is taught thoroughly and for_each on a resource never appears, so each.key and each.value are never seen.

Over a set — each.key and each.value are the same string:

hcl
resource "aws_ssm_parameter" "team_marker" {
  for_each = toset(var.team_names)

  name  = "/tf-course/24/teams/${each.key}/marker"
  type  = "String"
  value = "team ${each.value} is managed by terraform"
}

for_each accepts a set or a map, never a list — hence toset().

Over a map of objects — the form you actually want. each.key is the map key, each.value is the whole object, so every instance is configured differently from one block:

hcl
resource "aws_cloudwatch_log_group" "team" {
  for_each = var.teams

  name              = "/tf-course/24/${each.key}"
  retention_in_days = each.value.retention_days

  tags = {
    Team  = each.key
    Owner = each.value.owner
    Tier  = each.value.tier
  }
}

Chaining — a for_each resource is a map, so it can be fed straight back into another for_each. The keys line up automatically:

hcl
resource "aws_ssm_parameter" "team_log_group_arn" {
  for_each = aws_cloudwatch_log_group.team

  name  = "/tf-course/24/teams/${each.key}/log-group-arn"
  type  = "String"
  value = each.value.arn
}

Why this matters — run the experiment

count addresses by position; for_each addresses by name:

state addresses
aws_ssm_parameter.count_based[0]     aws_cloudwatch_log_group.team["orders"]
aws_ssm_parameter.count_based[1]     aws_cloudwatch_log_group.team["billing"]
aws_ssm_parameter.count_based[2]     aws_cloudwatch_log_group.team["search"]

Apply, remove "billing" from the middle of both inputs, and plan again:

  • count — index [1] is now "search" and [2] is gone, so Terraform destroys and recreates the search parameter that you never touched. One removal, two unrelated changes.
  • for_each — only ["billing"] is destroyed. orders and search keep their keys and are not mentioned in the plan.
The rule

Use count for identical copies or an on/off toggle. Use for_each for anything with an identity.

25. Expressions, functions and templatefile

Use case

One map of services should produce resource names, a tag set, an IAM policy document and a rendered config file — without writing any of them out four times.

You should already know: scenario 23 (locals), scenario 24 (for_each).

for expressions reshape a collection into a different collection. Not to be confused with the for_each meta-argument: for_each makes many resources, a for expression makes one value.

hcl
# LIST form — just the names.
service_names = [for name, _ in var.services : name]

# LIST form with a filter — only the gold tier.
gold_services = [for name, cfg in var.services : name if cfg.tier == "gold"]

# MAP form — rebuild the map with a computed value.
service_ports = { for name, cfg in var.services : name => cfg.port }

# MAP form with both a transform and a filter. `upper()` on the key shows
# that you can rewrite keys, not just values.
busy_services = {
  for name, cfg in var.services : upper(name) => cfg.replicas
  if cfg.replicas > 1
}

Square brackets produce a list; curly braces with => produce a map.

The functions worth knowing

FunctionWhat it's for
coalesce(a, b)First non-null wins — "use what the caller gave me, otherwise derive it"
try(expr, fallback)First argument that evaluates without erroring
can(expr)true/false instead of the value — for conditions, especially validation
lookup(map, key, default)Map access with a fallback, so a missing key isn't fatal
merge(a, b)Combine maps, later wins — the standard tagging idiom
format("%s-%03d", ...)printf for HCL
join / splitstring ↔ list
keys / valuespull the two halves of a map apart
cidrsubnet(base, bits, n)carve a subnet without binary arithmetic in your head
jsonencodebuild JSON from HCL instead of a raw string

All of them are exercised in the scenario and echoed back by its function_results output, so you can check your intuition against what Terraform actually returned.

jsonencode versus a heredoc

Compare with the raw JSON blob in basic scenario 5. This version cannot have a trailing-comma syntax error, and it interpolates real values:

hcl
policy = jsonencode({
  Version = "2012-10-17"
  Statement = [
    {
      Sid    = "ReadBucket"
      Effect = "Allow"
      Action = [
        "s3:GetObject",
        "s3:ListBucket",
      ]
      Resource = [
        aws_s3_bucket.app.arn,
        "${aws_s3_bucket.app.arn}/*",
      ]
    },
  ]
})

templatefile versus file

file() reads a file verbatim (basic scenario 20). templatefile() reads it and evaluates ${...} interpolations and %{ for } loops inside it:

hcl
locals {
  rendered_config = templatefile("${path.module}/templates/app.conf.tftpl", {
    env      = var.env
    bucket   = aws_s3_bucket.app.bucket
    services = var.services
  })
}

The template itself — the tildes in %{~ for ... ~} strip surrounding whitespace:

tftpl template
# Generated by Terraform — do not edit by hand.
# Environment: ${env}
# Storage:     ${bucket}

%{~ for name, cfg in services ~}
[${name}]
port     = ${cfg.port}
replicas = ${cfg.replicas}
tier     = ${cfg.tier}

%{ endfor ~}
# ${length(services)} service(s) configured.

Splat. [*] pulls one attribute out of every element of a list. A map has no splat, so values() converts first — values(var.services)[*].port. The older .*. form from basic scenario 12 still parses, but [*] is what to write today.

26. Validation, preconditions, postconditions and checks

Use case

A typo in a variable should fail immediately with a message that says what to fix — not twenty minutes into an apply, as an opaque error from the AWS API, halfway through creating things.

You should already know: basic scenario 8 (variables), scenario 25 (can/regex).

Terraform has five guards. The whole point of this scenario is which one fires when.

GuardFires atCan seeBlocks?
variable → validationplan, as variables resolveother variables (1.9+)yes
lifecycle → preconditionplan, before createdata sources, locals, other resourcesyes
lifecycle → postconditionapply, after createselfyes
output → preconditionapply, when the output evaluatesanythingyes
check → assertplan and applyits own scoped data sourceno — warns only

Variable validation is the cheapest. can() turns an expression that might error into a plain boolean, which is what a condition needs — regex() alone would blow up on a non-match instead of returning false:

hcl
validation {
  condition     = can(regex("^[a-z0-9][a-z0-9-]{1,40}[a-z0-9]$", var.bucket_prefix))
  error_message = <<-EOT
    bucket_prefix must be 3-42 characters of lowercase letters, digits and
    hyphens, starting and ending with a letter or digit. S3 rejects
    uppercase and underscores.
  EOT
}

A variable can carry several validation blocks. Terraform 1.9+ lets one reference other variables — before 1.9 this rule was impossible here and had to live in a precondition:

hcl
validation {
  condition     = var.env != "prod" || var.retention_days >= 30
  error_message = "Production keeps logs for at least 30 days. Raise retention_days or change env."
}

A precondition covers what a variable validation cannot see — here the length depends on the account ID, which only a data source knows:

hcl
lifecycle {
  precondition {
    condition     = length(local.bucket_name) <= 63
    error_message = "Composed bucket name is ${length(local.bucket_name)} characters; S3 allows 63. Shorten bucket_prefix."
  }
}

A postcondition asserts that reality matched your assumption, using self:

hcl
lifecycle {
  postcondition {
    condition     = self.versioning_configuration[0].status == "Enabled"
    error_message = "Versioning did not come back Enabled after apply."
  }
}

A check block is the odd one out: a failure is a warning, not an error, and it never blocks an apply. That makes it the right tool for continuous assertions about health — things you want to know about but not halt a deploy over. Uniquely, it can declare its own scoped data source, which degrades to a warning if it fails rather than killing the plan the way a top-level data source would:

hcl
check "al2023_ami_resolves" {
  data "aws_ssm_parameter" "al2023" {
    name = "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64"
  }

  assert {
    condition     = data.aws_ssm_parameter.al2023.value != ""
    error_message = "Could not resolve the current Amazon Linux 2023 AMI for ${var.region}."
  }
}

Two traps, both verified against the CLI

1. terraform validate does not check your values

It ignores -var-file and does not read terraform.tfvars. It evaluates validation rules only against variable defaults, so a file full of invalid values still reports success.

terminal
terraform validate -var-file=bad.tfvars   # "Success!"  — a lie
terraform plan     -var-file=bad.tfvars   # 2 errors
2. Coupled rules hide each other

The scenario's bad.tfvars has three wrong values but produces two errors. retention_days has a rule referencing var.env; var.env is itself invalid, so that rule cannot be evaluated and Terraform suppresses all reporting for retention_days — including the simple contains() rule that has nothing to do with env. Fix env, re-run, and the third error appears.

terminal
terraform plan -var env=production -var retention_days=2   # 1 error (env)
terraform plan -var env=dev        -var retention_days=2   # 1 error (retention)

Validation surfaces in waves when your rules are coupled. That is the hidden cost of cross-variable validation, and worth knowing before you reach for it.

27. The lifecycle block

Use case

One resource must never be deleted. Another is having its tags rewritten by a scanner, and every plan wants to undo it. A third needs replacing whenever an unrelated version string moves.

You should already know: basic scenario 7 (depends_on), basic scenario 14 (modules), scenario 26 (which also lives in lifecycle).

create_before_destroy — Terraform's default on replacement is destroy-then-create, which leaves a gap where the thing does not exist. For anything other resources point at, that gap is an outage. The catch: whatever makes the resource unique must hold two values at once, which is why the name here carries the version:

hcl
resource "aws_ssm_parameter" "rotating" {
  name  = "/tf-course/27/rotating/${var.config_version}"
  type  = "String"
  value = "created for ${var.config_version}"

  lifecycle {
    create_before_destroy = true
  }
}

prevent_destroy — a plan that would delete this errors out instead. It must be a literal; it cannot read a variable, precisely so nobody can switch it off from a tfvars file in a pipeline:

hcl
lifecycle {
  prevent_destroy = true
}
⚠️ This blocks terraform destroy for scenario 27

That friction is the entire feature. To tear the scenario down: set prevent_destroy = false, run terraform apply, then terraform destroy.

ignore_changes — stop fighting another system. Something outside Terraform writes tags here; without this, every plan tries to strip them and every apply starts a slow tug of war:

hcl
lifecycle {
  ignore_changes = [
    tags["CostCentre"],  # one specific tag key
    tags["LastScanned"], # another
  ]
}

Use ignore_changes = all only when adopting a resource you genuinely do not manage.

replace_triggered_by — replace me when something else changes. terraform_data is the modern, provider-free replacement for null_resource: it stores whatever you give it and does nothing else, which makes it a perfect tripwire.

hcl
resource "terraform_data" "config_version" {
  input = var.config_version
}

resource "aws_ssm_parameter" "app_config" {
  name  = "/tf-course/27/app-config"
  type  = "String"
  value = var.app_setting

  lifecycle {
    # Change var.app_setting  -> ordinary in-place update.
    # Change var.config_version -> full replacement, triggered from outside.
    replace_triggered_by = [terraform_data.config_version]
  }
}

Try both and watch the plan differ:

terminal
terraform apply -var app_setting=debug      # ~ update in place
terraform apply -var config_version=v2      # -/+ replacement

Contrast with terraform apply -replace=ADDR, the imperative one-off equivalent — that belongs to the state tier, still to come.

Finally, depends_on works on a module block, meaning "finish everything inside that module before starting anything in this one":

hcl
module "marker" {
  source = "./modules/marker"

  name    = "downstream"
  message = "created after the protected log group existed"

  depends_on = [aws_cloudwatch_log_group.protected]
}

Caveats — before you reuse any of this

These scenarios are teaching examples, deliberately stripped down so one idea stands out at a time. Each shortcut below is fine in a lab and a genuine problem in production:

Shortcut takenWhat to do instead
Hardcoded credentials — the RDS password and the S3 backend keys are inlineSensitive variables, AWS Secrets Manager, or the ambient AWS credential chain
Wide-open security groups — 0.0.0.0/0 throughoutRestrict to known CIDR ranges, or reference another security group
Region-locked, perishable AMI — the ID only exists in us-west-2, and Amazon replaces the image every few weeksLook it up dynamically with an aws_ssm_parameter or aws_ami data source — see below
Free-tier eligibility assumed — it varies by region and changes over timeRe-check with describe-instance-types before relying on it in another region
No provider version pinningAdd a required_providers block and commit the lock file
security_groups set by name (EC2-Classic style)Use vpc_security_group_ids with the group ID on modern VPC accounts
Everything in one state fileSeparate state per environment — workspaces, separate backends, or separate directories

Fixing the AMI properly

The hardcoded AMI is the shortcut most likely to bite you first, because it rots on its own — Amazon publishes a new Amazon Linux 2023 image every few weeks and eventually retires the old one. Ask AWS for the current image at plan time instead — a fully worked version of this is scenario 23:

hcl
data "aws_ssm_parameter" "al2023" {
  name = "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64"
}

resource "aws_instance" "ec2" {
  ami           = data.aws_ssm_parameter.al2023.value
  instance_type = "t3.micro"
}

AWS maintains that parameter, so the config now works in any region and never goes stale. The trade-off: the AMI can change under you between applies, which Terraform will show as a plan that replaces the instance — pin a specific ID when that matters.

Troubleshooting

SymptomCause and fix
BucketAlreadyExistsS3 names are globally unique across every AWS account. Every bucket here is suffixed with the account ID or a random_pet for exactly this reason — if you still collide, change bucket_prefix.
Output refers to sensitive valuesAn aws_ssm_parameter value is sensitive in provider 6.x. Use .insecure_value for genuinely non-secret parameters, or mark the output sensitive = true.
terraform destroy refuses in scenario 27That's prevent_destroy working. See the note in scenario 27.
AWS CLI fails with CERTIFICATE_VERIFY_FAILED but Terraform worksExpected behind a TLS-intercepting corporate proxy. Terraform uses Go's TLS and reads the macOS system keychain; the Python-based AWS CLI does not. Fix below.
terminal
security find-certificate -a -p /Library/Keychains/System.keychain > /tmp/corp.pem
cat /etc/ssl/cert.pem >> /tmp/corp.pem
export AWS_CA_BUNDLE=/tmp/corp.pem

FastAPI Quick Start

Quick Start code-first ~15 min

FastAPI turns ordinary Python functions into a web API — a program other apps (and browsers) can call over the internet. You write a function, add one line above it, and FastAPI handles the web plumbing, validates the data, and even generates interactive docs. New to Python? Skim the Python Quick Start first.

⬇️ Get the runnable code

A fuller, ready-to-run project for this quick start ships with the course: a Task API with routers, Pydantic v2 models, middleware, DI, and pytest tests. It lives in quickstart/code/fastapi/ — open its README for exact run steps and expected output.

1. Install & run

terminal
pip install "fastapi[standard]" uvicorn

# save the code below as main.py, then run the dev server:
uvicorn main:app --reload      # main = file, app = the FastAPI object
# now open http://127.0.0.1:8000  and  http://127.0.0.1:8000/docs

--reload restarts the server automatically when you edit the file. uvicorn is the program that actually runs your app.

2. Hello, API

main.py
from fastapi import FastAPI

app = FastAPI()

@app.get("/")          # handle GET requests to "/"
def home():
    return {"message": "Hello, API!"}

Visit / and you get back JSON: {"message": "Hello, API!"}. That @app.get("/") is a decorator — it wires your function to a web address. Returning a Python dict automatically becomes JSON.

🌐 The 4 verbs you'll use

@app.get reads data · @app.post creates · @app.put updates · @app.delete removes. Same pattern for each.

3. Path & query parameters

main.py
# Path parameter: part of the URL.  /items/42
@app.get("/items/{item_id}")
def get_item(item_id: int):        # type hint -> FastAPI converts & validates
    return {"item_id": item_id}

# Query parameters: after the ?.  /search?q=cats&limit=5
@app.get("/search")
def search(q: str, limit: int = 10):   # limit has a default
    return {"query": q, "limit": limit}

The type hints (item_id: int) aren't decoration — FastAPI uses them to convert and validate input. Send /items/abc and it returns a clean 422 error automatically, no code needed.

4. Request bodies with Pydantic

For POST/PUT, the data arrives in the request body as JSON. Describe its shape with a Pydantic BaseModel and FastAPI validates it for you:

main.py
from enum import Enum
from pydantic import BaseModel, Field

class Priority(str, Enum):
    high = "high"
    medium = "medium"
    low = "low"

class TaskCreate(BaseModel):
    title: str = Field(min_length=1, max_length=120)
    priority: Priority = Priority.medium      # optional, defaults to medium

@app.post("/tasks")
def create_task(data: TaskCreate):   # FastAPI parses & validates the JSON body
    return {"received": data.title, "priority": data.priority}

Post {"title": "Write docs", "priority": "high"} and it just works. Post an empty title and you get an automatic, descriptive validation error. This is the models.py from quickstart/code/fastapi/, and this validation is the reason FastAPI is loved.

5. Response model & status codes

main.py
class Task(TaskCreate):          # adds server-set fields to TaskCreate
    id: int
    done: bool = False

@app.post("/tasks", response_model=Task, status_code=201)
def create_task(data: TaskCreate):
    return store.create(data)    # response_model shapes what goes back out

response_model=Task guarantees the output shape (and hides fields you don't include). status_code=201 means "created." Task inherits from TaskCreate, so it reuses the same validation.

6. Async endpoints

main.py
@app.get("/slow")
async def slow():                 # use async when you await I/O
    data = await fetch_from_db()   # e.g. a database or another API
    return data

Use async def when your function awaits something (a database, another API). It lets one server handle many requests while waiting. Plain def is fine when there's nothing to await.

8. Returning errors

main.py
from fastapi import HTTPException, status

@app.get("/tasks/{task_id}", response_model=Task)
def get_task(task_id: int):
    task = store.get(task_id)
    if task is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, detail="task not found")
    return task

raise HTTPException(...) sends a proper HTTP error (like 404) with a JSON message, instead of crashing.

9. Dependencies (shared logic)

main.py
from fastapi import Depends

class TaskStore:                     # a stand-in for a database
    def list(self) -> list[Task]: ...

_store = TaskStore()
def get_store() -> TaskStore:        # the dependency provider
    return _store

@app.get("/tasks", response_model=list[Task])
def list_tasks(store: TaskStore = Depends(get_store)):   # injected
    return store.list()

Depends runs shared setup (a store, a DB connection, auth) before your endpoint and passes the result in — write it once, use it everywhere. This is the store.py pattern from the code project; tests can inject their own store.

10. Routers — split a growing app into files

One main.py with every route gets unwieldy fast. An APIRouter is a mini-app: you group related routes in their own file, then plug it into the main app. Same decorators, just @router instead of @app.

routers/users.py
from fastapi import APIRouter, Depends, status

router = APIRouter(prefix="/tasks", tags=["tasks"])

@router.get("", response_model=list[Task])       # GET /tasks
async def list_tasks(store: TaskStore = Depends(get_store)):
    return store.list()

@router.post("", response_model=Task, status_code=status.HTTP_201_CREATED)
async def create_task(data: TaskCreate, store: TaskStore = Depends(get_store)):
    return store.create(data)
main.py
from fastapi import FastAPI
from .routers import tasks

app = FastAPI(title="Task API")

app.include_router(tasks.router)     # plug the router in

The prefix="/tasks" is added to every route in that file, so you don't repeat it. tags=["tasks"] groups these endpoints under a "tasks" heading in the /docs page — instantly tidier. This mirrors app/routers/tasks.py in the code project.

🧩 Handy extras on a router

Apply things to a whole group at once: APIRouter(prefix="/admin", dependencies=[Depends(verify_admin)]) protects every admin route with one line. That pairs the dependencies idea with routers.

11. Middleware (runs on every request)

Middleware is code that wraps every request: it runs just before the request reaches your endpoint, and again just after the response is built. Think of a security desk everyone passes on the way in and out — perfect for logging, timing, adding headers, or auth checks you want applied everywhere.

main.py
import time
from fastapi import FastAPI, Request

app = FastAPI(title="Task API")

@app.middleware("http")
async def add_timing_header(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)   # run the actual endpoint
    elapsed_ms = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time-ms"] = f"{elapsed_ms:.2f}"
    return response

The one rule: call await call_next(request) to pass control to your endpoint (or the next middleware), then do something with the response before returning it. Code before that line runs on the way in; code after runs on the way out.

The one you'll almost always need: CORS

By default a browser blocks a web page from calling your API if it's on a different address. CORS middleware lets you allow specific front-ends. FastAPI ships with a ready-made one:

main.py
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],          # tighten to real origins in production
    allow_methods=["*"],
    allow_headers=["*"],
)

Two ways to add middleware: the @app.middleware("http") decorator for your own logic, or app.add_middleware(SomeMiddleware, ...) for prebuilt ones like CORS, GZip, or trusted-hosts.

🔁 Middleware vs. dependencies

Use middleware for cross-cutting concerns on all requests (logging, timing, CORS). Use dependencies when only some routes need it (like auth on protected endpoints). Order matters: middleware added later runs "outermost," wrapping the ones added before it.

Terraform Quick Start

Quick Start code-first ~30 min

Terraform lets you describe cloud infrastructure — servers, databases, networks — in text files, then create and change it safely and repeatably. Instead of clicking around a cloud console, you write what you want and Terraform makes reality match. It's how you provision the machines your app (and later, your AI agents) run on.

📘 By the end of this page you'll be able to…

read almost any Terraform file, run the plan → apply loop with confidence, use variables and outputs, loop with for_each, split work into modules, share state with a team, inspect and fix state, and know which commands to reach for when something breaks.

⬇️ Get the runnable code

A fuller, ready-to-run project for this quick start ships with the course: a full project: per-team S3 buckets with for_each, variables, data, and outputs. It lives in quickstart/code/terraform/ — open its README for exact run steps and expected output.

1. What Terraform actually does

Imagine ordering a coffee. The imperative way is to stand at the machine and press every button in the right order yourself. The declarative way is to hand over a note that says "one large oat latte" and let the barista figure out the steps. Terraform is the note. You write down the end state you want, and Terraform works out what to create, change, or delete to get there.

This idea has a name: Infrastructure as Code (IaC). Your cloud setup lives in plain text files you can read, review, and store in version control (like git) — the same way you'd store a program. That gives you three big wins:

Without IaC (clicking)With Terraform (code)
Steps live in someone's memory.Steps live in files anyone can read.
"Works on my account" surprises.Same files → same result, every time.
No record of who changed what.Git history shows every change.
Rebuilding after a disaster is manual.Re-run apply and it's back.

Terraform talks to platforms through providers — plugins for AWS, Azure, Google Cloud, GitHub, Cloudflare, and hundreds more. One tool, one language, many platforms.

2. Install & the whole workflow

terminal
brew install hashicorp/tap/terraform   # macOS; see downloads page for Windows/Linux
terraform -version

terraform init      # download providers (run once, and after adding providers/modules)
terraform plan      # preview changes — READ THIS before applying
terraform apply     # make the changes (type "yes")
terraform destroy   # tear everything down
terraform fmt       # auto-format  ·  terraform validate  # syntax check

Terraform is declarative: you describe the end state, it figures out the diff. Re-running apply with no changes does nothing. The plan step is your safety net — it shows every create, change, and destroy before anything happens.

3. The core commands, explained

You'll spend 90% of your time in just four commands. Here's what each one really does under the hood:

CommandWhat actually happens
initReads your config, downloads the providers/modules it names, and creates the .terraform/ folder + lock file. Run it in a new project and any time you add a provider or module.
planCompares your files ↔ real infra ↔ recorded state, then prints the diff. Changes nothing. This is a dry run.
applyShows the same plan, waits for you to type yes, then makes the changes and updates state.
destroyDeletes everything in this config's state. Great for tearing down a test environment.

Reading a plan is a core skill. The symbols tell you exactly what's about to happen:

SymbolMeaning
+create a new resource
~update in place (safe, no downtime)
-destroy a resource
-/+destroy then recreate — the one to watch for
💾 Save a plan, apply exactly that

For production, capture the plan and apply the reviewed artifact so nothing can change in between: terraform plan -out=tfplan then terraform apply tfplan.

4. Core building blocks

Every .tf file is made of a few block types. Know these eight and you can read almost any config:

BlockWhat it's for
terraform {}Settings — required version, providers, backend.
provider {}Configure a platform plugin (AWS region, credentials).
resource {}Create & manage a piece of infra. The main one.
data {}Read existing infra you didn't create (read-only).
variable {}An input you pass in.
output {}A value published after apply.
locals {}Named computed values, reused across the config.
module {}Call a reusable bundle of resources.

Mental model: variable + data flow in → locals compute → resource/module build → output comes out. Here's the shape of each:

syntax at a glance
terraform {
  required_version = ">= 1.9"
  required_providers { aws = { source = "hashicorp/aws", version = "~> 5.0" } }
}

provider "aws" { region = "us-east-1" }

resource "aws_s3_bucket" "docs" { bucket = "acme-docs" }   # ref: aws_s3_bucket.docs.id
data "aws_vpc" "main" { default = true }                    # ref: data.aws_vpc.main.id
variable "env" { type = string, default = "dev" }           # ref: var.env
locals { name = "acme-${var.env}" }                         # ref: local.name
output "bucket" { value = aws_s3_bucket.docs.bucket }
module "network" { source = "./modules/network" }           # ref: module.network.vpc_id
📁 How files are organized

Terraform loads every .tf file in the current folder and treats them as one config — file names are just for humans. A common layout is main.tf (resources), variables.tf (inputs), outputs.tf (outputs), and terraform.tfvars (values). Order doesn't matter; Terraform figures out dependencies from references.

5. HCL syntax essentials

Terraform's language is HCL (HashiCorp Configuration Language). It's designed to be easy to read. Here are the pieces you'll meet constantly:

hcl-basics.tf
# 1. Arguments — name = value
name    = "orders"
count   = 3
enabled = true

# 2. Blocks — a keyword, optional labels, and a { body }
resource "aws_instance" "web" { }
#  ^type    ^resource-kind  ^your-name

# 3. Interpolation — drop a value into a string with ${ }
bucket = "acme-${var.env}-docs"        # -> "acme-prod-docs"

# 4. Comments
# single line      // also single line      /* block */

# 5. Multi-line strings (heredoc)
user_data = <<-EOT
  #!/bin/bash
  echo "hello from ${var.env}"
EOT

Refer to things with simple dotted paths — this is how values flow between blocks:

ReferenceReads…
var.envan input variable
local.namea computed local value
aws_s3_bucket.docs.arnan attribute of a resource you made
data.aws_vpc.main.idan attribute of a data source
module.network.vpc_idan output of a module
each.key / each.valuethe current item inside a for_each

6. Variable types

Three families. Always set a type — it catches bad input at plan time, not mid-apply.

variables.tf
# primitives
string   number   bool

# collections (many of the SAME type)
list(string)   set(string)   map(number)

# structural (mixed types)
object({ name = string, size = string })
tuple([string, number, bool])

variable "agent" {
  type = object({
    name     = string
    size     = string
    replicas = optional(number, 1)   # optional w/ default
  })
  sensitive = false                  # true = hide from logs/output
  validation {
    condition     = contains(["small", "large"], var.agent.size)
    error_message = "size must be small or large."
  }
}

7. Passing values in (tfvars & precedence)

A variable block declares an input; you still have to supply a value. There are several ways, and Terraform has a strict order when the same variable is set more than once.

terminal & files
# A. a values file (most common)
# terraform.tfvars
env      = "prod"
replicas = 3

# B. on the command line
terraform apply -var="env=prod" -var="replicas=3"

# C. a named file
terraform apply -var-file="prod.tfvars"

# D. an environment variable (prefix TF_VAR_)
export TF_VAR_env=prod

When a variable is set in more than one place, later beats earlier in this order (last wins):

  1. Default in the variable block
  2. TF_VAR_* environment variables
  3. terraform.tfvars (and *.auto.tfvars)
  4. -var-file and -var on the command line
⚠️ Don't commit secret tfvars

Files with passwords or keys should never enter git. Add *.tfvars to .gitignore (keep an example.tfvars with fake values), or better, pull secrets from a secrets manager at plan time.

8. Your first resource

main.tf
resource "aws_s3_bucket" "docs" {
  bucket = "acme-agent-docs-unique-name"
  tags   = { Project = "ai-agent-platform" }
}

resource "TYPE" "LOCAL_NAME". Reference its attributes elsewhere as aws_s3_bucket.docs.id — that reference also creates the dependency order automatically, so you never write "create A then B."

9. Variables, locals, outputs

main.tf
variable "env" { type = string, default = "dev" }

locals {
  name = "acme-${var.env}"          # computed once, reused
}

resource "aws_s3_bucket" "docs" {
  bucket = "${local.name}-docs"
}

output "bucket" {
  value = aws_s3_bucket.docs.bucket # printed after apply; readable by other configs
}

Pass values with -var="env=prod" or a *.tfvars file. variable = input, local = computed value, output = published value. Read outputs any time with terraform output or terraform output bucket.

10. Expressions & built-in functions

HCL can compute values, not just store them. You'll use these all the time for names, tags, and conditional wiring.

expressions.tf
# conditional  (condition ? if_true : if_false)
instance_type = var.env == "prod" ? "m5.large" : "t3.micro"

# for expression — transform a list/map
upper_names = [for n in var.names : upper(n)]          # ["ORDERS", "BILLING"]
by_id       = { for u in var.users : u.id => u.name }  # build a map

# splat — pull one attribute from every item
all_arns = aws_s3_bucket.docs[*].arn

Terraform ships with a big standard library. The ones you'll reach for first:

FunctionDoes
merge(a, b)combine maps (great for shared + per-resource tags)
lookup(map, key, default)safe map read with a fallback
coalesce(a, b, …)first non-empty value
join / splitlist ↔ string
toset / tolist / tomapconvert between collection types
file("x.txt") / templatefile()read a file / fill a template
jsonencode / jsondecodebuild or read JSON (IAM policies, etc.)
length / keys / valuesinspect collections
🧪 Try expressions live

Run terraform console to open a REPL and test any expression: type upper("hi") or merge({a=1},{b=2}) and see the result instantly. No apply needed.

11. Make many — for_each (not copy-paste)

main.tf
resource "aws_s3_bucket" "docs" {
  for_each = toset(["orders", "support", "billing"])
  bucket   = "acme-${each.key}-docs"
}
# addressed as aws_s3_bucket.docs["orders"]

# count = N identical copies, or an on/off toggle:
resource "aws_db_instance" "replica" {
  count = var.env == "prod" ? 1 : 0
  # ...
}
⚠️ Prefer for_each over count for named things

count is index-based — removing a middle item shifts every later index and recreates unrelated resources. for_each keys by name, so removing one touches only that one.

12. Conditionals & dynamic blocks

Sometimes you need to generate nested blocks (like a list of firewall rules) from a variable. A dynamic block is a for_each loop that produces inner blocks instead of whole resources.

main.tf
variable "ingress_ports" { default = [80, 443] }

resource "aws_security_group" "web" {
  name = "web"

  dynamic "ingress" {              # generate one "ingress { }" per port
    for_each = var.ingress_ports
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}

Reach for dynamic only when the number of nested blocks truly varies — writing them out by hand is clearer when the list is fixed and short.

13. Meta-arguments: depends_on & lifecycle

Terraform usually orders work automatically from references. These special arguments let you override that behavior when you need to.

main.tf
resource "aws_instance" "app" {
  # ...

  # force ordering when there's no direct reference
  depends_on = [aws_iam_role_policy.app]

  lifecycle {
    create_before_destroy = true    # make the new one before killing the old (no downtime)
    prevent_destroy       = true    # refuse to delete this (guard a prod database)
    ignore_changes        = [tags]  # don't fight edits made outside Terraform
  }
}
SettingUse it when…
create_before_destroyreplacing a resource must not cause an outage.
prevent_destroyaccidental deletion would be catastrophic (databases, state buckets).
ignore_changessomething else (autoscaling, a console operator) legitimately manages a field.
depends_ona hidden dependency exists that Terraform can't infer.

14. Modules — reuse a group of resources

main.tf
module "orders_agent" {
  source  = "./modules/agent-service"   # local dir, git URL, or registry
  version = "1.4.0"                      # required for registry/git sources
  name    = "orders"
  env     = var.env
}

output "orders_db" {
  value = module.orders_agent.db_endpoint   # reach modules only via their outputs
}

A module is a reusable bundle with a small interface: input variables go in, outputs come out, and everything inside is hidden. Run terraform init after adding one. Expose only what varies; bake secure defaults for the rest.

Source typeExample
local foldersource = "./modules/network"
git reposource = "git::https://github.com/acme/tf-network.git?ref=v2"
public registrysource = "terraform-aws-modules/vpc/aws"

15. Data sources — read what you didn't create

main.tf
data "aws_vpc" "main" {
  tags = { Name = "agent-platform-${var.env}" }
}

resource "aws_db_subnet_group" "this" {
  subnet_ids = data.aws_vpc.main.subnet_ids   # no hardcoded IDs
}

resource creates & owns; data only reads. Refreshed every plan, so it always reflects current reality. Perfect for looking up things another team owns — a shared network, the latest AMI, your account ID.

16. Remote state & locking

backend.tf
terraform {
  backend "s3" {
    bucket       = "acme-terraform-state"
    key          = "agent-platform/prod/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true   # locking = no corrupted concurrent applies
  }
}

Terraform's state file is its memory of what it created — a JSON map from your config to real cloud IDs. Never commit terraform.tfstate (it holds secrets, and git has no locking). A remote backend lets a whole team share one authoritative, encrypted, locked state. Locking means only one apply can run at a time, so two people can't corrupt it.

🗂️ Split state by environment

Keep dev, staging, and prod in separate state files (different key paths). A mistake in dev then can never touch prod, and plans stay small and fast.

17. Managing state (the rescue commands)

Occasionally you need to look at or fix Terraform's memory directly — after a rename, or to adopt a resource that already exists. These are safe when you understand them.

terminal
terraform state list                 # every resource Terraform tracks
terraform state show aws_s3_bucket.docs   # full details of one

# renamed a resource in code? move it in state so it isn't destroyed+recreated:
terraform state mv aws_s3_bucket.old aws_s3_bucket.new

# stop tracking something WITHOUT deleting the real infra:
terraform state rm aws_s3_bucket.docs

# adopt an EXISTING cloud resource into Terraform:
terraform import aws_s3_bucket.docs acme-existing-bucket

Modern Terraform can also record renames in code with a moved block, so teammates get the change automatically instead of running a manual command:

moved.tf
moved {
  from = aws_s3_bucket.old
  to   = aws_s3_bucket.new
}

18. Workspaces

A workspace gives one config multiple independent state files — a lightweight way to run the same code for several environments without copying it.

terminal
terraform workspace new staging
terraform workspace select staging
terraform workspace list        # * marks the active one

# use the workspace name inside config:
# name = "acme-${terraform.workspace}"
⚠️ Workspaces aren't always the right tool

They share the same backend and code, so they're best for small variations (a personal sandbox, ephemeral test envs). For prod-grade separation, many teams prefer separate folders + separate backends so environments can differ and can't be confused on the command line.

19. Provisioners (and why to avoid them)

A provisioner runs a script on a machine after it's created. It exists as an escape hatch — but it breaks Terraform's declarative model (it isn't tracked in state, and it only runs at create time), so treat it as a last resort.

main.tf
resource "aws_instance" "app" {
  # ...
  provisioner "local-exec" {
    command = "echo ${self.public_ip} >> hosts.txt"   # runs on YOUR machine
  }
}

Prefer these instead: pass a startup script via user_data, bake images with Packer, or configure servers with a dedicated tool (Ansible). Reach for a provisioner only when there's truly no other way.

20. A complete example, end to end

Everything so far, assembled into one small but real project — a private bucket per team, tagged consistently, with outputs you can hand to the next tool. This is the runnable project in quickstart/code/terraform/ (there it's split across versions.tf, variables.tf, main.tf, and outputs.tf — shown combined here).

main.tf
terraform {
  required_version = ">= 1.9"
  required_providers { aws = { source = "hashicorp/aws", version = "~> 5.0" } }
}

provider "aws" { region = var.region }

variable "region" { type = string, default = "us-east-1" }
variable "env"    { type = string, default = "dev" }
variable "teams"  { type = list(string), default = ["orders", "billing"] }

# Read-only lookup of the current AWS account (a data source).
data "aws_caller_identity" "current" {}

locals {
  common_tags = { Project = "ai-agent-platform", Env = var.env }
  suffix      = "${var.env}-${data.aws_caller_identity.current.account_id}"
}

resource "aws_s3_bucket" "team" {
  for_each = toset(var.teams)
  bucket   = "acme-${each.key}-docs-${local.suffix}"
  tags     = merge(local.common_tags, { Team = each.key })
}

resource "aws_s3_bucket_public_access_block" "team" {
  for_each                = aws_s3_bucket.team
  bucket                  = each.value.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

output "bucket_names" {
  value = [for b in aws_s3_bucket.team : b.bucket]
}

output "bucket_arns" {
  value = { for team, b in aws_s3_bucket.team : team => b.arn }
}
terminal — run it
terraform init
terraform plan      # review: 4 to add (2 buckets + 2 access blocks)
terraform apply     # type yes

# expected output (account-id suffix will be your own):
# bucket_names = [
#   "acme-orders-docs-dev-123456789012",
#   "acme-billing-docs-dev-123456789012",
# ]

Add a team to the teams list and re-apply: Terraform creates only the new bucket, leaving the others untouched — because for_each keys by name. That's the whole promise of Terraform in one change.

21. Debugging & troubleshooting

terminal
terraform fmt         # fix indentation/spacing
terraform validate    # check syntax & types (no cloud calls)
terraform console      # REPL to test expressions
terraform refresh      # re-sync state with real infra (or: plan -refresh-only)

# verbose logs when something is really stuck:
export TF_LOG=DEBUG          # TRACE, DEBUG, INFO, WARN, ERROR
export TF_LOG_PATH=tf.log    # send logs to a file
terraform apply

Workflow when a plan surprises you: run validate and fmt first, read the plan slowly for any -/+, then use console to inspect the exact expression that's off. Turn on TF_LOG only as a last resort — it's very noisy.

22. Everyday gotchas

You see…It means / do this
-/+ in a planResource will be destroyed & recreated. Check before applying (especially databases).
Plan wants to undo your changeDrift — someone edited it by hand. Change the config, not the console.
BucketAlreadyExistsS3 names are globally unique. Add a suffix.
Auth erroraws configure or set AWS_PROFILE.
Module changes ignoredRe-run terraform init.
State lockedAnother apply is running. Only force-unlock if you're sure it's not.
"Provider produced inconsistent result"Usually a provider bug or a hand-edit; refresh then re-plan.

24. Rules that keep you safe

  1. Always read the plan. An unexpected - (destroy) is a stop sign.
  2. Never commit state or secrets. Use a remote backend; gitignore *.tfvars.
  3. for_each for named collections; count only for identical copies / toggles.
  4. Pin provider versions; commit .terraform.lock.hcl.
  5. Change infra in code, never by hand in the console.
  6. Guard the irreplaceable with prevent_destroy.
  7. Keep dev/staging/prod state separate.

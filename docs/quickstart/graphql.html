GraphQL Quick Start

Quick Start code-first ~20 min

GraphQL replaces a wall of URLs with one endpoint and a typed schema. The client sends a query naming exactly the fields it wants; the server returns exactly those, in the same shape. You still write ordinary Python functions — Strawberry turns them into a schema, and FastAPI keeps serving the HTTP. New to APIs? Read the FastAPI Quick Start first: this page is the same HR API, converted.

⬇️ Get the runnable code

Every snippet below is lifted from a working project that ships with the course — the HR Skills GraphQL API, the REST project from the FastAPI page converted field for field. It lives in fast-api-graphql/:

terminal
cd fast-api-graphql
uv run uvicorn app.main:app --reload
# then open http://127.0.0.1:8000/graphql   ← GraphiQL, the in-browser explorer
uv run pytest -q                            # 31 passing tests
The domain, in one line

Employees have skills rated 1–5; requisitions require skills at a minimum level; some of those are mandatory. A candidate below a mandatory bar is blocked — no score saves them. In REST that was eight URLs. Here it is one endpoint and this schema:

Ask for…You get
employees(availableOnly: true)the directory, optionally just the bench
requisition(jobId:) { candidates(limit:) }a role and everyone scored against it, one round trip
employee(employeeId:) { match(jobId:) }the same scoring engine, asked the other way round
shortlistCandidate(jobId:, employeeId:)a mutation that can answer ShortlistEntry, NotFound or CandidateBlocked

1. Install & run

terminal
pip install "strawberry-graphql[fastapi]" fastapi uvicorn

# save the code below as main.py, then run the dev server:
uvicorn main:app --reload
# now open http://127.0.0.1:8000/graphql

Strawberry is the schema library; FastAPI still runs the process. There is no /docs page here — the schema itself is the documentation, and GraphiQL (served at that same URL in a browser) reads it live.

2. Hello, schema

A GraphQL server has one required type: Query, the root of everything readable. Each method decorated with @strawberry.field becomes a field a client may ask for.

main.py
import strawberry
from fastapi import FastAPI
from strawberry.fastapi import GraphQLRouter

@strawberry.type
class Query:
    @strawberry.field
    def health(self) -> str:          # the return type IS the schema
        return "ok"

schema = strawberry.Schema(query=Query)

app = FastAPI()
app.include_router(GraphQLRouter(schema), prefix="/graphql")
the request, and the answer
POST /graphql   {"query": "{ health }"}
200             {"data": {"health": "ok"}}

Note what the type hint bought you: -> str published health: String! in the schema, and the ! is a promise — this field is never null. Forget the hint and Strawberry refuses to build the schema at all, at import time, rather than shipping an untyped field.

3. Types: the contract clients program against

Objects are classes. Field names get camelCased on the way out (employee_id → employeeId), so Python stays Pythonic and the schema stays idiomatic GraphQL.

app/graph/types.py
from datetime import datetime
import strawberry
from app import models

# Reuse the domain enums rather than redeclaring them — one list of verdicts.
Availability = strawberry.enum(models.Availability, description="Bench or on a project.")
Verdict = strawberry.enum(models.Verdict, description="The scoring engine's answer.")

@strawberry.type(description="One rated skill. Level is 1 aware · 3 independent · 5 expert.")
class SkillRating:
    skill: str
    level: int

@strawberry.type(description="Someone in the directory.")
class Employee:
    employee_id: strawberry.ID
    name: str
    location: str
    availability: Availability
    experience_years: float
    skills: list[SkillRating]
    created_at: datetime

    # Private: available to this type's resolvers, absent from the published schema.
    model: strawberry.Private[models.Employee]

    @classmethod
    def from_model(cls, employee: models.Employee) -> "Employee":
        return cls(employee_id=strawberry.ID(employee.employee_id), name=employee.name,
                   location=employee.location, availability=employee.availability,
                   experience_years=employee.experience_years,
                   skills=[SkillRating.from_model(s) for s in employee.skills],
                   created_at=employee.created_at, model=employee)

That from_model is a deliberate seam. models.py is what the store keeps; this file is what clients may ask for. They mirror each other today, but renaming a Pydantic field is a refactor — renaming a GraphQL field breaks every client in production. Keeping them separate lets one change without the other.

📄 The schema is a file you can read
terminal
uv run strawberry export-schema app.graph.schema:schema > schema.graphql

Commit that file and a CI job can diff it on every PR: adding a field is safe, removing one is a breaking change, and now the review sees which is which.

4. Queries with arguments

A resolver's parameters become the field's arguments — typed, with defaults, exactly like Python. info is the exception: Strawberry recognises it by type and hands you per-request state instead of exposing it in the schema.

app/graph/schema.py
@strawberry.type
class Query:
    @strawberry.field(description="The directory, optionally just the people on the bench.")
    def employees(self, info: Info, available_only: bool = False) -> list[Employee]:
        people = info.context.store.list_employees(available_only=available_only)
        return [Employee.from_model(p) for p in people]

    @strawberry.field(description="One person by id. Null if there is no such person.")
    def employee(self, info: Info, employee_id: strawberry.ID) -> Employee | None:
        # Null, not an error: "no such row" is an ordinary answer to a lookup, and
        # a nullable field lets the rest of a multi-field query still succeed.
        person = info.context.store.get_employee(employee_id)
        return Employee.from_model(person) if person else None
real response
{ employee(employeeId: "E9999") { name } health }

{"data": {"employee": null, "health": "ok"}}     ← no "errors" key at all

REST answered that with a 404. Here the missing person is null and the sibling field still resolved — which matters, because one GraphQL request routinely carries several independent questions.

5. Nested resolvers — the actual payoff

This is the part with no REST equivalent. A field can be a function that takes arguments, anywhere in the graph — so "the role, ranked candidates, their gaps and their records" is one request instead of four.

app/graph/types.py
@strawberry.type(description="An open role and the skills it needs.")
class Requisition:
    job_id: strawberry.ID
    title: str
    required_skills: list[SkillRequirement]
    model: strawberry.Private[models.Requisition]

    @strawberry.field(description="Everyone on the bench, scored and ranked, best first.")
    def candidates(self, info: Info, limit: int = 3) -> list[MatchResult]:
        if not 1 <= limit <= MAX_CANDIDATES:
            raise GraphQLError(f"limit must be between 1 and {MAX_CANDIDATES}, got {limit}")
        return [MatchResult.from_model(m)
                for m in info.context.store.rank(self.model, limit=limit)]

@strawberry.type(description="Someone in the directory.")
class Employee:
    ...
    @strawberry.field(description="Score this person against one open role.")
    def match(self, info: Info, job_id: strawberry.ID) -> MatchResult | None:
        requisition = info.context.store.get_requisition(job_id)
        if requisition is None:
            return None
        return MatchResult.from_model(info.context.store.score(self.model, requisition))

The scoring engine lives in store.py and has not changed a line — the same arithmetic that GET /requisitions/J2001/candidates called. What changed is who decides when it runs: the client, by naming the field.

terminal
curl -sG http://127.0.0.1:8000/graphql --data-urlencode 'query=
{ requisition(jobId: "J2001") {
    title
    candidates(limit: 3) {
      name score verdict blockers

    }
} }'
real response (trimmed)
{"data": {"requisition": {"title": "Senior Data Engineer", "candidates": [
  {"name": "Priya Raman", "score": 100, "verdict": "strong", "blockers": [],

🔎 Reads can go over GET

curl -sG --data-urlencode 'query=…' keeps a multi-line query readable. It has to: a raw newline is illegal inside a JSON string, so a POST body must keep the query on one line (or send it from a file). Mutations are POST-only by design.

6. Inputs & mutations

Anything that changes state goes on the Mutation type. Arguments that are objects need @strawberry.input — GraphQL keeps input and output types separate on purpose, so a client can never send back a server-set field like createdAt.

app/graph/types.py
@strawberry.input(description="One rated skill on a new employee.")
class SkillRatingInput:
    skill: str
    level: int

@strawberry.input(description="A new person for the directory.")
class EmployeeInput:
    name: str
    location: str
    experience_years: float
    availability: Availability = models.Availability.bench
    skills: list[SkillRatingInput] = strawberry.field(default_factory=list)
app/graph/schema.py
@strawberry.type
class Mutation:
    @strawberry.mutation(description="Add someone to the directory. Skill levels must be 1–5.")
    def add_employee(self, info: Info, employee: EmployeeInput) -> AddEmployeeResult:
        try:
            data = models.EmployeeCreate(**strawberry.asdict(employee))
        except PydanticValidationError as exc:
            return ValidationFailed(
                message=f"{exc.error_count()} field(s) rejected",
                invalid_fields=[
                    InvalidField(field=".".join(str(p) for p in err["loc"]), message=err["msg"])
                    for err in exc.errors()
                ],
            )
        return Employee.from_model(info.context.store.create_employee(data))

strawberry.asdict() turns the input into a plain dict, so the Pydantic model that guarded the REST edge is reused unchanged — one definition of the rules, two protocols.

7. Errors: two channels, and they mean different things

The first surprise for anyone arriving from REST: a GraphQL server answers 200 almost no matter what. The status line stops carrying meaning; the body carries it instead. There are two places it can appear, and conflating them is the most common way to make a GraphQL API unpleasant to consume.

ChannelMeansExample
errors, with data: nullthe request was never valid — a bug in the clientasking for a field that does not exist
errors, with partial dataone resolver failed; the rest still resolvedlimit: 0 on candidates
inside data, as a typea domain outcome — the server working correctlycandidate blocked, requisition not found
a client bug — nothing ran
{ employees { salary } }

{"data": null,
 "errors": [{"message": "Cannot query field 'salary' on type 'Employee'."}]}

The query was validated against the schema before any resolver ran. That check is free, it is exhaustive, and it is why a typed schema is worth the ceremony.

8. Unions: the schema's 404 and 409

So where do "not found" and "blocked" go? Into the schema, as types. A mutation whose return type is a union forces the client to name each outcome it wants to read — it cannot forget the unhappy path, because the query will not compile without it.

app/graph/types.py
@strawberry.type(description="No such employee or requisition.")
class NotFound:
    message: str
    kind: str
    id: strawberry.ID

@strawberry.type(description="The candidate misses a mandatory skill — the REST 409.")
class CandidateBlocked:
    message: str
    blockers: list[str]
    score: int

ShortlistResult = Annotated[
    ShortlistEntry | NotFound | CandidateBlocked,
    strawberry.union("ShortlistResult",
                     description="Every way shortlisting can end, spelled out in the schema."),
]
app/graph/schema.py
    @strawberry.mutation(description="Shortlist a candidate — refused if they are blocked.")
    def shortlist_candidate(
        self, info: Info, job_id: strawberry.ID, employee_id: strawberry.ID
    ) -> ShortlistResult:
        store = info.context.store
        requisition = store.get_requisition(job_id)
        if requisition is None:
            return NotFound(message="requisition not found", kind="requisition", id=job_id)

        employee = store.get_employee(employee_id)
        if employee is None:
            return NotFound(message="employee not found", kind="employee", id=employee_id)

        match = store.score(employee, requisition)
        if match.blockers:
            return CandidateBlocked(
                message=f"{match.name} is missing mandatory {', '.join(match.blockers)}",
                blockers=match.blockers, score=match.score,
            )
        return ShortlistEntry.from_model(store.add_to_shortlist(job_id, match))

The client selects on the union with inline fragments — ... on TypeName — and __typename tells it which arm it got:

the query
mutation S($job: ID!, $emp: ID!) {
  shortlistCandidate(jobId: $job, employeeId: $emp) {
    __typename
    ... on ShortlistEntry  { name score verdict }
    ... on CandidateBlocked { message blockers }
    ... on NotFound        { message kind }
  }
}
real responses
{"emp": "E1002"} → {"__typename": "ShortlistEntry", "name": "Priya Raman",
                    "score": 100, "verdict": "strong"}

{"emp": "E1005"} → {"__typename": "CandidateBlocked",
                    "message": "Vikram Iyer is missing mandatory Python, SQL",
                    "blockers": ["Python", "SQL"]}

{"job": "J9999"} → {"__typename": "NotFound", "message": "requisition not found",
                    "kind": "requisition"}

All three are 200, and none of them has an errors key. That is the point: a blocked candidate is not a failure, it is an answer. The REST version said the same thing with 409 — this version says it in a way a code generator can turn into an exhaustive switch.

When to use which

Use a nullable field for "this lookup found nothing" (employee(employeeId:)). Use a union when the caller must do something different per outcome, or when you owe them detail — CandidateBlocked carries the blocking skills, which a bare null never could.

9. What the type system will not do for you

level: Int! promises a whole number. It says nothing about 1–5. GraphQL has no ge/le, no regex, no cross-field rules — so every constraint REST got free from Field(ge=1, le=5) and Query(3, ge=1, le=20) is now yours to enforce.

two rejections, two channels
skills: [{skill: "SQL", level: "expert"}]      ← wrong TYPE
  {"data": null, "errors": [{"message": "Int cannot represent non-integer value..."}]}
  GraphQL caught it. No Python ran.

skills: [{skill: "SQL", level: 9}]             ← right type, wrong VALUE
  {"data": {"addEmployee": {"__typename": "ValidationFailed",
    "message": "1 field(s) rejected",
    "invalidFields": [{"field": "skills.0.level",
                       "message": "Input should be less than or equal to 5"}]}}}
  Pydantic caught it, inside the resolver, and reported it as data.

The same split applies to arguments. limit is an Int!, so bounding it is a line of resolver code — and because an out-of-range limit is a client bug rather than a domain outcome, it belongs in the errors channel:

real response
{"data": {"requisition": null},
 "errors": [{"message": "limit must be between 1 and 20, got 0",
             "path": ["requisition", "candidates"]}]}

Note the path. GraphQL errors point at the exact field that failed — with a deep query, that is the difference between a five-minute fix and an afternoon.

10. Context: dependency injection with one route

REST gets its dependencies per route with Depends(). GraphQL has one route, so they arrive a level down — in the context, a per-request object every resolver sees as info.context.

app/graph/context.py
from fastapi import Depends
from strawberry.dataloader import DataLoader
from strawberry.fastapi import BaseContext

from app.store import HRStore, get_store

class Context(BaseContext):
    """One instance per HTTP request, not per resolver call."""

    def __init__(self, store: HRStore) -> None:
        super().__init__()
        self.store = store
        self.employees = DataLoader(load_fn=self._load_employees)

    async def _load_employees(self, employee_ids: list[str]) -> list[Employee | None]:
        return self.store.get_employees(employee_ids)

async def get_context(store: HRStore = Depends(get_store)) -> Context:
    return Context(store=store)
app/main.py
graphql_router = GraphQLRouter(
    schema,
    context_getter=get_context,   # an ordinary FastAPI dependency
    graphql_ide="graphiql",       # the in-browser explorer at GET /graphql
)
app.include_router(graphql_router, prefix="/graphql")

Because get_context is a normal dependency, everything FastAPI does still works — including app.dependency_overrides[get_store], which is how each test below gets its own store. Authentication belongs here too: read the header off self.request, put the user on the context, and every resolver has it.

11. N+1, and the DataLoader that fixes it

Nested fields are GraphQL's best feature and its sharpest edge. Ask for a shortlist of 30 people and let each entry resolve its own employee record, and a naive server makes 30 database calls — the N+1 problem. It is invisible in the response and obvious in the query log.

app/graph/types.py
    @strawberry.field(description="The full record behind this entry, batched by a DataLoader.")
    async def employee(self, info: Info) -> Employee | None:
        person = await info.context.employees.load(self.employee_id)
        return Employee.from_model(person) if person else None

A DataLoader collects every .load() made in the same tick, calls your batch function once with all the keys, and hands each caller its own result. Two rules make it correct:

  • Build it per request — it caches, and a cache that outlives its request serves one client another client's stale data.
  • Return results positionally — one slot per key, None for a miss. Drop the misses and every key after the first gap gets the wrong answer.
tests/test_graphql.py
def test_dataloader_batches_employee_lookups(client, store):
    """Two shortlist entries, each asking for its employee: one trip to the store."""
    ...
    assert len(entries) == 2
    assert store.batch_calls == 1            # N+1 would make this 2

That assertion is worth copying into your own project. Batching is the kind of thing that works on the day you write it and quietly regresses six months later; only a test notices.

12. GraphiQL & introspection

Open http://127.0.0.1:8000/graphql in a browser and you get GraphiQL: an editor with autocomplete, inline docs and a schema browser. Nobody wrote it — it asks the server to describe itself (introspection), which is the same mechanism client code generators use to produce typed SDKs.

ToolWhat you get
GET /graphql in a browserGraphiQL — write queries with autocomplete, read every description.
strawberry export-schemathe SDL as a file: commit it, diff it in CI, catch breaking changes.
Introspection querywhat codegen tools read to build typed clients.
🔒 Turn both off in production

Introspection publishes your entire API surface, and the IDE invites people to explore it. Public deployments usually disable both, plus add query depth and complexity limits — with nested fields, one small query can ask for a very large amount of work.

13. Testing

No new machinery: it is still FastAPI's TestClient posting JSON. What changes is the assertion — you check the body, because the status is 200 either way.

tests/test_graphql.py
@pytest.fixture
def client(store):
    app.dependency_overrides[get_store] = lambda: store   # the SAME store per test
    yield TestClient(app)
    app.dependency_overrides.clear()

def gql(client, query, **variables):
    """POST one operation and return the parsed body — errors included, not raised."""
    response = client.post("/graphql", json={"query": query, "variables": variables})
    assert response.status_code == 200, response.text
    return response.json()

def test_blocked_candidate_is_a_union_member_not_an_error(client):
    body = gql(client, SHORTLIST, jobId="J2001", employeeId="E1005")
    assert "errors" not in body
    result = body["data"]["shortlistCandidate"]
    assert result["__typename"] == "CandidateBlocked"
    assert set(result["blockers"]) == {"Python", "SQL"}
🐰 Click through it instead

The project also ships a Bruno collection at fast-api-graphql/bruno/ — 24 requests grouped Meta · Queries · Mutations · Errors · Schema, each with its own tests and a docs tab. It is the fastest way to see the difference between the two error channels: run Mutations › Shortlist a blocked candidate and watch a refusal arrive as 200 with no errors key.

terminal

npx @usebruno/cli run --env Local -r     # server must already be running

Two habits worth keeping: assert "errors" not in body on the happy path (a typo'd field name otherwise passes as a silent None), and write one test against the SDL itself — assert "union ShortlistResult = ShortlistEntry | NotFound | CandidateBlocked" in schema.as_str() — so a change to the contract has to be deliberate.

14. REST → GraphQL, line by line

Both versions of this API sit side by side in the course: fast-api/ and fast-api-graphql/. models.py and store.py are the same file in both — the scoring engine never learns which protocol is asking. Everything else maps like this:

RESTGraphQL
8 URLs, each with a fixed response shapeone POST /graphql; the client picks fields
GET /requisitions/{id}/candidatesRequisition.candidates(limit:) — a field
response_model=Employee@strawberry.type class Employee
404 Not Foundnull, or a NotFound union member
409 ConflictCandidateBlocked union member
422 from Pydantic, automaticallyValidationFailed — you call Pydantic yourself
Query(3, ge=1, le=20)a bounds check inside the resolver
Depends(get_store) on each routecontext_getter, once
over-fetching; several round trips per screenone round trip, exact fields — but N+1 is now yours to manage
HTTP caching, per-URL rate limits, CDNall much harder: every request is POST /graphql
/docs generated from type hintsGraphiQL + SDL generated from type hints
Which should you pick?

GraphQL pays off with many different clients over one graph of related data — a mobile app that wants three fields and a dashboard that wants thirty, without a new endpoint for each. REST stays the better answer for simple, cacheable, file-and-CDN-shaped APIs, for webhooks, and anywhere HTTP semantics are the interface. Nothing stops you running both: they are two doors onto the same store.py.

16. Everyday gotchas

TrapRemember
Checking the status codeIt is 200. Read data and errors instead.
Everything thrown into errorsClient bugs → errors. Domain outcomes → types in data.
Trusting Int! to mean 1–5It means "an integer". Ranges are yours (Pydantic, or a check).
A union that returns {}You forgot the inline fragments: ... on ShortlistEntry { … }.
N+1 in a nested fieldBatch with a DataLoader, per request, and test the call count.
One shared DataLoaderBuild it in the context. A cross-request cache leaks data between users.
A package named graphql/It shadows the graphql-core library on sys.path. This project uses graph/.
Reusing an output type as inputGraphQL forbids it — declare a matching @strawberry.input.
Unbounded query depthNested fields let a client ask for enormous work. Add depth/complexity limits.
Middleware timing per endpointIt only ever sees POST /graphql. Per-field timing needs a schema extension.

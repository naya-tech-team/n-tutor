FastMCP Quick Start

Quick Start code-first ~15 min

MCP (Model Context Protocol) is a standard way to give an AI assistant real tools and data — so it can look things up and take actions instead of only chatting. FastMCP is the Python library for building an MCP server: you write normal functions, add a decorator, and the AI can call them. If FastAPI exposes functions to the web, FastMCP exposes them to an AI. New to decorators? See Decorators.

⬇️ Get the runnable code

A fuller, ready-to-run project for this quick start ships with the course: the HR skills server, exposing the same domain the rest of the course uses. It lives in mcp-server/app/main.py:

terminal
cd mcp-server
uv run app/main.py            # HTTP on http://127.0.0.1:8000/mcp/
fastmcp dev app/main.py       # …or poke at it in the browser inspector
Why this server exists

The HR team owns employee data. They publish tools once, over a protocol — and Strands, Claude Desktop, an IDE, or your own script all consume the same four tools without importing a line of their code. mcp-server/app/main.py opens with the point: "This file has no idea Strands exists." That is the whole idea of MCP.

1. Install

terminal
pip install fastmcp

python -c "import fastmcp; print(fastmcp.__version__)"

FastMCP also ships inside the official MCP SDK (from mcp.server.fastmcp import FastMCP) — the API below is the same either way.

2. Your first MCP server

server.py
from fastmcp import FastMCP

from _shared import get_job

mcp = FastMCP("hr-skills")           # give your server a name

@mcp.tool(description="Get one open job requisition and the skills it requires.")
def get_requisition(job_id: str) -> dict:
    """Args: job_id, e.g. "J2001"."""
    job = get_job(job_id)
    return job or {"error": f"no requisition {job_id}"}

if __name__ == "__main__":
    mcp.run(transport="http", show_banner=False, port=8000)   # serves /mcp/

That's a complete MCP server. The @mcp.tool decorator turns get_requisition into something an AI can call. Run it with uv run app/main.py (or fastmcp run app/main.py). This is the real server in mcp-server/app/main.py — the next sections add its other three tools.

3. Tools — actions the AI can take

A tool is just a Python function the AI may call. Two things matter enormously:

server.py
@mcp.tool(description="Find employees who have a skill at or above a given level.")
def find_by_skill(skill: str, min_level: int = 3, available_only: bool = True) -> list[dict]:
    """Args: skill (name or alias, e.g. "pyspark"), min_level 1-5, available_only."""
    return [
        {"employee_id": e["employee_id"], "name": e["name"],
         "location": e["location"], "availability": e["availability"]}
        for e in employees_with_skill(skill, min_level=min_level, available_only=available_only)
    ]

@mcp.tool(description="Score one employee against one job and explain the gaps.")
def score_match(employee_id: str, job_id: str) -> dict:
    """Args: employee_id e.g. "E1002", job_id e.g. "J2001"."""
    employee, job = get_employee(employee_id), get_job(job_id)
    if employee is None or job is None:
        return {"error": f"unknown employee {employee_id!r} or job {job_id!r}"}
    return match(employee, job)

@mcp.tool(description="Rank the best available candidates for a job.")
def shortlist(job_id: str, limit: int = 3) -> list[dict]:
    """Args: job_id, limit (how many candidates to return)."""
    return rank_candidates(job_id, available_only=True, limit=limit)
  • Type hints (min_level: int, -> list[dict]) tell the AI exactly what to send and what comes back — and FastMCP validates it.
  • The docstring and description= are not just documentation — they are how the AI decides when to use the tool. Write them for the model: say plainly what it does and when to reach for it.
  • Defaults become optional arguments, so min_level: int = 3 means the model may call find_by_skill(skill="pyspark") and still get something sensible.
Return an error, don't raise one

score_match returns {"error": …} for an unknown id rather than raising. The model reads that string and can correct itself; an unhandled exception is just a failed call. Better still, say what to do next — "unknown employee E1148; call find_by_skill and use an id it returned" — or a weak model will try E1149, then E1150, until something stops it.

Notice what these four tools have in common: the scoring is arithmetic inside match(), never something the model works out. The AI decides who to score and explains the result; the number itself is reproducible by hand, which is what makes it defensible in a hiring review.

4. Resources — read-only data the AI can fetch

Where a tool does something, a resource just exposes data for the AI to read (like a file or a config). Each has a URI:

server.py
@mcp.resource(
    "hr://employees",
    name="employee-directory",
    description="Every employee: id, designation, location, availability, years of experience.",
    mime_type="text/plain",
)
def employee_directory() -> str:
    return "\n".join(
        f"{e['employee_id']}  {e['name']:<22} {e['designation']:<32} "
        f"{e['location']:<12} {e['availability']:<10} {e['experience_years']}y"
        for e in EMPLOYEES
    )

# A *template* resource: one URI shape, many documents.
@mcp.resource(
    "hr://employees/{employee_id}",
    description="One employee's full profile including rated skills. e.g. hr://employees/E1002",
    mime_type="application/json",
)
def employee_profile(employee_id: str) -> dict:
    """Returning a dict is fine — FastMCP serialises it to JSON for the wire."""
    employee = get_employee(employee_id)
    return employee or {"error": f"no employee {employee_id!r}"}

Rule of thumb: use a tool for actions and anything with side effects; use a resource for "just give me this data."

The reason resources are underrated

You read a resource by URI — the model is not involved, so it costs no tokens and cannot be hallucinated.

client side
profile = await client.read_resource("hr://employees/E1002")   # no model call at all

A template resource ({employee_id} in the URI) gives you one declaration and a whole family of documents. Reach for a resource whenever the answer does not depend on the question — a skill catalogue never changes per query, so making the model "call a tool" for it is pure waste.

5. Prompts — reusable message templates

server.py
@mcp.prompt(description="Screen one candidate against one requisition, using the server's own score.")
def screen_candidate(employee_id: str, job_id: str) -> str:
    """Args: employee_id e.g. "E1010", job_id e.g. "J2003"."""
    employee, job = get_employee(employee_id), get_job(job_id)
    if employee is None or job is None:
        return f"Reply exactly: 'No such employee {employee_id!r} or requisition {job_id!r}.'"

    result = match(employee, job)
    return (
        f"Write a screening note for {result['name']} ({employee_id}) against "
        f"{result['title']} ({job_id}).\n\n"
        f"The matching engine has already decided this — do not recompute it:\n"
        f"{json.dumps(result, indent=2)}\n\n"
        "Cover, in this order and in three sentences total:\n"
        "1. the score and verdict, in plain language;\n"
        "2. the strongest matched skill and the most damaging gap;\n"
        "3. a recommendation — interview, develop, or decline."
    )

A prompt is a saved, parameterised message the client can pull up on demand. Look at what this one is really doing: the score is computed on the server and embedded in the question. The model is not asked to judge the candidate — it is asked to explain a decision that has already been made, and told not to recompute it.

Prompts are how the data owner keeps authorship

HR knows what a good screening note contains; your app does not. Shipping that as a prompt means the wording lives with the team that owns the definition — and improves for every client at once, without anyone shipping a new release.

A prompt can also return a conversation rather than one string, which lets the server pre-seed the assistant's turn to steer the format:

server.py
from fastmcp.prompts import Message

@mcp.prompt(description="Brief a hiring manager on the current shortlist for a requisition.")
def shortlist_brief(job_id: str, limit: str = "3") -> list[Message]:
    ranked = rank_candidates(job_id, available_only=True, limit=int(limit))
    table = "\n".join(summarize_match(r) for r in ranked)
    return [
        Message(f"Brief me on the shortlist for {job_id}:\n{table}"),
        Message("Here is the shortlist, strongest first:", role="assistant"),
    ]

6. Running it: stdio vs. HTTP

python
mcp.run()                                   # default: stdio (local, for desktop apps)
mcp.run(transport="http", host="127.0.0.1", port=8000)  # remote / networked
TransportUse when…
stdioThe AI app runs the server locally (e.g. Claude Desktop launches it). Default.
httpThe server runs somewhere on a network and clients connect to a URL.

7. Test it fast

terminal + python
# Interactive inspector in the browser — click your tools to try them:
fastmcp dev app/main.py
client.py
import asyncio
from fastmcp import Client

client = Client("http://127.0.0.1:8000/mcp/")   # the running HTTP server
# Client("app/main.py") instead launches the file as a stdio subprocess

async def main():
    async with client:
        tools = await client.list_tools()
        print("tools    :", [t.name for t in tools])

        result = await client.call_tool("score_match",
                                        {"employee_id": "E1002", "job_id": "J2001"})
        print("E1002/J2001:", result.data["score"], result.data["verdict"])

        result = await client.call_tool("shortlist", {"job_id": "J2001", "limit": 3})
        print("shortlist :", [(m["name"], m["score"]) for m in result.data])

asyncio.run(main())
output — a real run
tools    : ['find_by_skill', 'get_requisition', 'score_match', 'shortlist']
E1002/J2001: 100 strong
shortlist : [('Priya Raman', 100), ('Rahul Menon', 61), ('Vikram Iyer', 50)]

The Client is how your code (or an agent) talks to any MCP server — connect, list what it offers, then call a tool. Calling tools directly like this, with no model in the loop, is also the easiest way to test an MCP server: deterministic, fast, and no sampling to argue with.

The async with block is load-bearing

Leave it and the connection closes — over stdio the server subprocess dies with it; over HTTP the session goes. Either way those tool names become unusable. In an agent this is nasty to debug, because the model still has the tool names in its history and will happily start improvising answers instead of calling anything.

8. Use it in Claude Desktop

terminal
fastmcp install claude-desktop app/main.py

This registers your server so Claude Desktop can launch it and use your tools in a normal conversation — ask it "who on the bench could fill J2001?" and it will call shortlist itself. (Under the hood it adds an entry to the app's MCP config — you can also do that by hand.)

Nothing about the server changes to support this. The same four tools are consumed by Claude Desktop here, by a Strands agent in lesson 02 of the Strands course, and by the plain Client above. That is the payoff: write the tools once, and every AI client can use them.

9. Context — talk back to the AI & the client

Most tools just take inputs and return a value. But sometimes a tool needs to communicate while it runs — log what it's doing, report progress on a long job, read other data, or even ask the AI for help. That's what Context is for. Add a ctx: Context parameter to any tool (or resource, or prompt) and FastMCP injects it automatically — the caller never passes it.

server.py
from fastmcp import FastMCP, Context

mcp = FastMCP("hr-skills")

@mcp.tool
async def screen_bench(job_id: str, employee_ids: list[str], ctx: Context) -> str:
    """Write a one-line screening note for each candidate, reporting progress."""
    await ctx.info(f"Screening {len(employee_ids)} candidates for {job_id}")  # log to the client

    notes = []
    for i, employee_id in enumerate(employee_ids):
        profile = await ctx.read_resource(f"hr://employees/{employee_id}")   # another resource
        reply = await ctx.sample(                                            # ask the AI
            f"One line on this candidate's fit for {job_id}:\n\n{profile}"
        )
        notes.append(reply.text)
        await ctx.report_progress(progress=i + 1, total=len(employee_ids))   # move the bar

    await ctx.info("Done")
    return "\n".join(notes)

You never pass ctx yourself — FastMCP spots the Context type hint and fills it in. (The parameter can be named anything; the type is what matters.)

What the Context can do

CallWhat it does
ctx.debug / info / warning / error(msg)Send a log message to the client (four severity levels).
ctx.report_progress(progress, total)Update a progress indicator during a long task.
ctx.read_resource(uri)Read another resource this server exposes, from inside a tool.
ctx.sample(prompt)Ask the client's LLM to generate text — your server borrows the model. Returns a message with .text.
ctx.elicit(message, schema)Pause and ask the user for extra input mid-tool.
ctx.request_id · ctx.client_idIdentify the current request and the connected client (handy for logs).
ctx.fastmcpReach the server instance itself (settings, other components).
🧠 The clever one: ctx.sample()

Normally the AI calls your tool. With sample(), your tool calls the AI back — it asks the client's model to do a sub-task (summarise, classify, draft text) without you needing your own API key. The model comes "for free" from whoever is using your server.

⚠️ Two things to remember

1. Context only exists during a request — you can't grab it at import time or in a background thread. 2. Its methods are async, so use async def and await them (a plain def tool can still accept ctx for the sync-safe bits, but async is the norm here).

11. Everyday gotchas

TrapRemember
Vague docstringThe AI reads it to pick tools — say what it does and when to use it.
Missing type hintsNo hints = the AI can't tell what arguments to send.
Tool vs. resource mix-upAction → tool; "just give me data" → resource.
print() in a stdio serverstdio uses stdout to talk to the client — log via ctx, don't print.
Untrusted tool outputTreat what a tool returns as data, not instructions to the model.
Leaving the async withThe subprocess dies with it and the agent quietly starts improvising.
Raising instead of returningReturn {"error": "…and here is what to do next"} — the model reads it and recovers.
Letting the model do the mathsCompute the score in the tool. A number nobody can reproduce is a number nobody will defend.

A2A Quick Start

Quick Start code-first runs locally ~25 min

A2A (Agent2Agent) is an open protocol — started by Google, now under the Linux Foundation — that lets independently built AI agents discover each other and delegate work, even across different teams, frameworks, or companies. If MCP gives one agent tools, A2A lets one agent hand a task to another agent. New to MCP? See the FastMCP Quick Start — the two are complementary.

⬇️ Get the runnable code

A ready-to-run project ships with the course in a2a-strands/: three agents on three ports — an orchestrator that discovers two specialists and delegates real hiring work to them, built with Strands Agents and running entirely on a local model via Ollama. No API keys, nothing leaves your machine. Sections 1–7 below are the raw protocol; section 8 is that project.

One domain across the whole course

Every track here uses the same small world: employees have skills rated 1–5, requisitions require skills, and some of those are mandatory. A candidate below a mandatory bar is blocked — they cannot be shortlisted however high the score. In this track you will watch that one fact travel across three processes without ever being re-derived. See it in Python, over HTTP in FastAPI, exposed to an AI in FastMCP, and agent-side in the Strands course.

2. The big picture

Two roles, connected over plain HTTP:

flowchart LR
    C["Client agent
needs work done"]
    S["Remote agent
does the work"]
    C -->|"1 · GET /.well-known/agent-card.json"| S
    C -->|"2 · send message → task created"| S
    S -->|"3 · task updates, then the result"| C
A client reads the remote agent's public "business card" from a fixed URL, then sends it a task and receives the result.
  • Agent Card — a JSON document at a well-known URL describing what an agent is and can do.
  • Task — a unit of work with a lifecycle (submitted → working → completed/failed).
  • Message / parts — the content exchanged (text, data, files).

These are roles, not fixed identities. A real agent is usually both at once — a server to whoever called it, and a client to the specialists it calls.

🧠 The one distinction to hold on to

A tool is a function. An agent is a colleague. You call a function and get a value back. You delegate to a colleague — who has their own judgement, may come back with a question, and may take a while. That difference is why A2A has a task lifecycle and MCP does not.

3. The Agent Card (discovery)

The card advertises the agent. It's served at /.well-known/agent-card.json so any client can find it:

server.py
from a2a.types import AgentCard, AgentSkill, AgentCapabilities

HOST, PORT = "127.0.0.1", 9001

skill = AgentSkill(
    id="candidate_screening",
    name="Candidate screening and ranking",
    description=(
        "Score internal employees against an open requisition and rank the best "
        "available candidates. Returns match percentages, verdicts, skill gaps and "
        "blocking mandatory skills. Use for any question about who fits a role."
    ),
    tags=["recruiting", "screening", "matching", "hr"],
    examples=["Who are the top candidates for J2001?", "Score E1002 against J2001."],
)

card = AgentCard(
    name="Talent Screening Agent",
    description="Scores and ranks internal candidates against open requisitions.",
    version="1.0.0",
    url=f"http://{HOST}:{PORT}/",
    default_input_modes=["text"],
    default_output_modes=["text"],
    capabilities=AgentCapabilities(streaming=True),
    skills=[skill],
)

The skills are the key part — clear names and descriptions are how another agent decides to delegate to yours (just like a good tool docstring in MCP). Note the examples: a remote model matches its need against those strings, so they earn their place.

The card is a contract, not documentation

Everything a caller knows about you comes from this JSON at a fixed URL. If the description says "ranks candidates" and the agent actually rewrites job adverts, no amount of correct code will save the delegation — the calling model chose you by reading prose.

4. Build the agent (its logic)

Your agent's behaviour lives in an AgentExecutor with two methods: execute (do the work) and cancel (stop it):

server.py
from a2a.server.agent_execution import AgentExecutor, RequestContext
from a2a.server.events import EventQueue
from a2a.utils import new_agent_text_message

class ScreeningExecutor(AgentExecutor):
    async def execute(self, context: RequestContext, event_queue: EventQueue):
        user_text = context.get_user_input()             # what the caller sent
        job_id = user_text.strip().split()[-1]           # the agent's "brain",
        reply = rank_candidates_as_text(job_id)          # here: a plain lookup
        await event_queue.enqueue_event(                 # send a result back
            new_agent_text_message(reply)
        )

    async def cancel(self, context: RequestContext, event_queue: EventQueue):
        raise NotImplementedError                        # nothing long-running to stop

You read the incoming message from context, do your work (call an LLM, a tool, another service…), and push results onto the event_queue. That's the whole contract — and note the "brain" here is deliberately not a model at all, just a lookup, to keep the protocol in focus. Section 8 swaps it for a real agent and the rest stays identical.

5. Run the server

server.py
from a2a.server.apps import A2AStarletteApplication
from a2a.server.request_handlers import DefaultRequestHandler
from a2a.server.tasks import InMemoryTaskStore
import uvicorn

handler = DefaultRequestHandler(
    agent_executor=ScreeningExecutor(),
    task_store=InMemoryTaskStore(),      # remembers tasks in memory
)
app = A2AStarletteApplication(agent_card=card, http_handler=handler)

if __name__ == "__main__":
    uvicorn.run(app.build(), host=HOST, port=PORT)

Run python server.py. Your agent is now live at http://127.0.0.1:9001, card and all.

6. Call it from another agent (the client)

client.py
import asyncio
from uuid import uuid4
import httpx
from a2a.client import A2ACardResolver, ClientFactory, ClientConfig
from a2a.types import Message, Part, Role, TextPart

BASE_URL = "http://127.0.0.1:9001"

async def main():
    async with httpx.AsyncClient(timeout=120) as http:
        # 1. discover the agent by reading its card
        card = await A2ACardResolver(http, BASE_URL).get_agent_card()

        # 2. build a client bound to that agent
        client = ClientFactory(ClientConfig(httpx_client=http)).create(card)

        # 3. send a message and collect the reply
        message = Message(
            role=Role.user,
            message_id=uuid4().hex,
            parts=[Part(root=TextPart(text="Who are the top 2 candidates for J2001?"))],
        )
        last_task = None
        async for event in client.send_message(message):
            if isinstance(event, tuple):        # (Task, update) — a streaming server
                last_task = event[0]            # the Task is cumulative: keep the newest

        print("".join(
            part.root.text
            for artifact in (last_task.artifacts or [])
            for part in artifact.parts
            if getattr(part.root, "text", None)
        ))

asyncio.run(main())
The trap that returns an empty string

The obvious first guess is for part in event.parts — and against a compliant streaming server it silently yields nothing, because the events are (Task, TaskArtifactUpdateEvent) tuples and a tuple has no .parts. No error, no warning, just an empty reply and an afternoon spent blaming the server. (This page's own project shipped that bug first.)

What actually arrives:

the event stream, unpacked
(Task, TaskArtifactUpdateEvent)   ← the answer, growing one token per event
(Task, TaskArtifactUpdateEvent)
(Task, TaskArtifactUpdateEvent)   ← …dozens of these…
(Task, TaskStatusUpdateEvent)     ← working → completed

The Task is cumulative — every event carries the whole task so far — so keep the last one and read task.artifacts[*].parts[*].text at the end. Do not try to stitch the deltas yourself.

Discover → connect → send. In a real system, an orchestrator agent does exactly this to hand sub-tasks to specialist agents. This is the client in a2a-strands/app/a2a_call.py, which also falls back to plain Message events for servers that do not stream.

7. The task lifecycle

A2A tasks aren't just request/response — they can take time and report progress. Every task moves through states:

sequenceDiagram
    participant C as Client agent
    participant R as Remote agent
    C->>R: send message
    R-->>C: task created · submitted
    R-->>C: status update · working
    R-->>C: status update · working
    Note over R: (may run for minutes)
    R-->>C: artifact · the result
    R-->>C: status update · completed (final)
One send, many events back. This is why the client loops with async for instead of awaiting a single response.
StateMeaning
submittedReceived, not started yet.
workingIn progress.
input-requiredPaused — needs more info from the caller.
completedDone; an artifact (the result) is available.
failed / canceledErrored out, or stopped on request.
rejectedThe agent declined to even attempt it (e.g. not authorised).

To continue an input-required task, the client sends another message reusing the same task ID — that's how multi-turn delegation works.

8. Real agents: Strands on a local llama

Everything above is the protocol by hand. The agent's "brain" in §4 was a single .upper() call — deliberately, to keep the protocol in focus. Now put a real agent inside that envelope.

Strands Agents does two things for you here: it is the brain (a model, a system prompt, tools, a reasoning loop), and it ships an A2AServer that publishes that brain over A2A — no AgentExecutor, no card built by hand. And because the model is a swappable object, all of this runs on llama3.2 on your own laptop.

The system you'll build

Three agents in three terminals. One asks; two answer.

flowchart LR
    U(["You"])
    O["Hiring Orchestrator
no data of its own"]
    S["Talent Screening Agent :9001
owns the HR data
+ the scoring engine"]
    W["Recruiting Outreach Agent :9002
no tools at all"]
    U --> O
    O -->|"1 · A2A · who fits J2001?"| S
    S -->|"2 · Priya 100% strong · Rahul 61% blocked"| O
    O -->|"3 · A2A · draft a note from these facts"| W
    W -->|"4 · a note to Priya, citing real skills"| O
    O -->|"5 · the note"| U
Three separate processes. Nobody scripted that order — the orchestrator's model worked out from its tool descriptions that you cannot write to a candidate before you have screened one.

The two specialists are deliberately opposite: one owns a database and a scoring engine; the other has no tools whatsoever and can only write from facts it is handed. From the outside they are indistinguishable — same card format, same protocol, same task lifecycle. That is what a protocol buys you.

Why this is the A2A example and not a Graph

Screening and outreach are owned by different teams. The scoring engine is HR's — copy it into your pipeline and you have forked the definition of "a good match", which drifts the day they change a weighting. The house style for candidate notes is Recruiting's. A Graph or Swarm would be simpler if you owned both; the moment you don't, the boundary is a network boundary.

a) Point an agent at the local llama

shared.py
from strands.models.ollama import OllamaModel

def make_model(temperature: float = 0.2) -> OllamaModel:
    return OllamaModel(
        host=settings.ollama_host,       # where Ollama listens
        model_id=settings.ollama_model,
        temperature=temperature,         # low — we want reliable tool picking
    )

That is the only local-model-specific code in the whole project. Swap it for BedrockModel or AnthropicModel and nothing else changes — the agents, the tools, and every line of A2A plumbing are model-agnostic.

b) Publish a Strands agent over A2A

app/screening_agent.py
from a2a.types import AgentSkill
from strands import Agent, tool
from strands.multiagent.a2a import A2AServer

@tool
def rank_for_requisition(job_id: str, limit: int = 3) -> str:
    """Rank the best available candidates for an open requisition.

    Use this for any question about who could fill a role, who is the
    best fit, or who should be shortlisted.
    """
    print(f"  [screening] rank_for_requisition({job_id!r})", flush=True)
    ...   # calls match() — arithmetic, never a model

def build_screener(context_id: str) -> Agent:
    return Agent(
        name="Talent Screening Agent",              # ← goes on the Agent Card
        description="Scores and ranks internal candidates against open requisitions.",
        model=make_model(),
        tools=[rank_for_requisition, score_one],
        hooks=[ToolBudget(max_calls=3)],            # ← see the caps section below
        system_prompt="You are the talent screening desk. Call "
                      "rank_for_requisition ONCE, then copy its line for each "
                      "candidate straight into your answer — id, name, score, "
                      "verdict, strengths AND blockers. Use the tool's verdict "
                      "word exactly. Then stop.",
    )

SCREENING_SKILL = AgentSkill(
    id="candidate_screening",
    name="Candidate screening and ranking",
    description="Score internal employees against an open requisition and rank "
                "the best available candidates. Returns match percentages, "
                "verdicts, skill gaps and blocking mandatory skills.",
    tags=["recruiting", "screening", "matching", "hr"],
    examples=["Who are the top candidates for J2001?"],
)

A2AServer(
    agent_factory=build_screener,
    host="127.0.0.1", port=9001,
    skills=[SCREENING_SKILL],
    enable_a2a_compliant_streaming=True,
).serve()

Compare that with §4–§5: the executor, the request handler, the task store and the hand-written AgentCard are all gone. A2AServer derives the card from the agent's name and description, mounts the endpoints, and runs the task lifecycle.

⚠️ Use agent_factory, not agent=

A2AServer calls your factory once per A2A context — one caller's ongoing conversation — so two callers never share message history. Passing a single agent= instance is deprecated for exactly that reason: it isn't multi-tenant safe, and every caller would write into the same conversation.

Your agent is now live. Prove it without writing any client at all:

terminal
curl http://127.0.0.1:9001/.well-known/agent-card.json
# -> "name": "Talent Screening Agent", "skills": [{"id": "candidate_screening", ...}]

c) Cap it — a service that loops is worse than a script that loops

The Strands agent loop recurses once per cycle, so an agent that keeps calling its own tools walks off Python's stack rather than spinning. On a direct call you bound that at the call site:

orchestrator.py
result = await orchestrator.invoke_async(question, limits={"turns": 8})

Inside an A2AServer there is no call site — the server invokes the agent for you. A hook is the way in, because it attaches to the agent object and travels with it:

app/tool_budget.py
class ToolBudget(HookProvider):
    """Allow at most `max_calls` tool calls per invocation, then answer from what you have."""

    def register_hooks(self, registry: HookRegistry, **_) -> None:
        registry.add_callback(BeforeInvocationEvent, self._reset)
        registry.add_callback(BeforeToolCallEvent, self._enforce)

    def _enforce(self, event: BeforeToolCallEvent) -> None:
        # Reserve BEFORE the tool runs: tools in one turn execute concurrently, so a
        # counter incremented afterwards reads zero at every check and enforces nothing.
        self._used += 1
        if self._used > self.max_calls:
            event.cancel_tool = (
                f"Tool budget of {self.max_calls} calls is used up. Do not call any "
                "more tools. Answer now, using only what the earlier results told you."
            )
This is not hypothetical

While this project was being written the screening agent looped on its own tool — rank_for_requisition('J2001'), six times and climbing. From the orchestrator's side that is indistinguishable from a slow network: a request that never returns, with all the evidence in someone else's terminal. Cap both ends.

d) Delegate to it — a remote agent as a tool

The other direction. Wrap the A2A call from §6 in a function, put @tool on it, and a remote agent becomes something your model can choose to use:

app/orchestrator.py
from strands import Agent, tool
from a2a_call import call_agent      # exactly the code from §6, made reusable

@tool
async def ask_screening_agent(job_id: str) -> str:
    """Get the ranked candidates for a requisition from the remote Screening Agent.

    Use this FIRST for any hiring question — you must know who the candidates
    are, and their scores, before you can ask for an outreach note.
    """
    return await call_agent(SCREENING_URL,
                            f"Who are the top 2 available candidates for {job_id}?")

@tool
async def ask_outreach_agent(screening_facts: str = "") -> str:
    """Ask the remote Outreach Agent to draft a note to a candidate.

    Pass the WHOLE reply from ask_screening_agent as one string — names, ids,
    scores and blockers together. This agent has no HR access and cannot look
    any of that up itself.
    """
    if not screening_facts.strip():          # ← see the callout below
        return ('ask_outreach_agent needs the screening text. Call it again as '
                'ask_outreach_agent(screening_facts="<the entire reply you got '
                'from ask_screening_agent, copied verbatim>") — one string, not '
                'separate fields, and do not retype the numbers.')
    return await call_agent(OUTREACH_URL,
                            f"Draft an outreach note using only these facts:\n{screening_facts}")

orchestrator = Agent(
    model=make_model(),
    tools=[ask_screening_agent, ask_outreach_agent],
    system_prompt="You run a hiring pipeline by delegating to two remote "
                  "specialists. Every fact in your answer must have come back "
                  "from a tool — you have no HR data of your own.",
)
await orchestrator.invoke_async(question, limits={"turns": 8})

Read those two docstrings again — "use this FIRST… before you can ask for an outreach note". That sentence is the entire routing logic. Nothing in the code sequences the calls; the model reads the descriptions and chains them. Same lesson as an MCP tool docstring and an AgentSkill description, for the third time: the prose is the interface.

⚠️ Why screening_facts is optional

A small model reaches for the shape it is thinking in. Ask llama3.2 to draft a note and it calls ask_outreach_agent(candidate_name="Priya Raman", score="100", blockers="") — five invented parameters instead of the one. If screening_facts were required, that is a bare pydantic validation error carrying no way forward, and the model reshuffles the same wrong guess until something stops it.

Making it optional and returning instructions turns a dead end into a recovery: in a real run llama3.2 gets it wrong, reads the message, and calls it correctly on the very next turn. A tool result is the next thing the model reads — write your failures as prompts.

🪆 What just nested

When ask_screening_agent fires, the orchestrator's model calls a tool, which makes an HTTP request, which starts a task on another agent, whose model calls its tool, which runs match(). A tool call inside an agent inside another agent's tool call — three processes deep, and each layer only knows about the one below it.

🔁 The batteries-included shortcut

strands-agents-tools ships A2AClientToolProvider, which generates delegation tools from a list of URLs: Agent(tools=A2AClientToolProvider(known_agent_urls=[...]).tools) — one line instead of twenty. Hand-writing them, as above, shows what an A2A call is, and gives the model typed parameters instead of a generic "send text to a URL" tool. Prefer the provider once you're on a larger model. It lives in strands_tools.a2a_client.

What it takes for that note to be correct

Look at the output again. Rahul scores 61% and is blocked — J2001 marks Apache Spark mandatory and he is a level short. The note goes to Priya, and cites Python L4, Apache Spark L5 — numbers that came out of match() three processes away. Four separate things had to hold:

  1. match() computes the blocker — arithmetic, not a model call.
  2. The screening agent is told to use the verdict word exactly: blocked must not get softened to "consider with caution".
  3. The orchestrator passes the screening text through verbatim instead of summarising it.
  4. The outreach agent is told never to write to a candidate with blockers.

Break any one and the pipeline sends a friendly note to someone who cannot do the job. Every one of those four was a bug in an earlier draft of this project — including a note that praised a candidate's "expertise in data analysis", a phrase that appears nowhere in the HR data. Grounding is not a property you get by using good models; it is a property you maintain at every hop.

The failure mode to watch for

Each hop is a chance to paraphrase, and paraphrase is where facts die. The screening agent that reports "a score of 61%" without the word blocked has technically told the truth and practically caused the wrong outreach. When you design an A2A boundary, ask what the next agent needs — not what reads nicely.

⚠️ Small models need blunter prompts

llama3.2 is a 3B model. Left to itself it will answer a hiring question from its own invented knowledge rather than delegating, so the real orchestrator's prompt says it outright: "Every fact in your final answer must have come back from a tool — you have no HR data of your own." It also needs the screening_facts recovery message above, and a turn cap to stop it re-delegating out of indecision. qwen2.5:7b runs the same pipeline cleanly in two tool calls. That verbosity is a property of the model size, not of A2A — but design for it, because the small model is the one that shows you where your interfaces are weak.

9. A2A vs. MCP — which do I use?

SituationUse
One agent needs a tool or data sourceMCP
One agent delegates a task to another agentA2A
Agents built by different teams must cooperateA2A
A single, fixed function call in your own codeNeither — just call it

They pair up: an agent often uses MCP to reach its own tools and A2A to delegate to other agents.

flowchart TB
    O["Orchestrator agent"]
    S["Specialist agent
(another team, another framework)"]
    T1[("HR database")]
    T2[("Payroll API")]
    O -->|"A2A · delegate a task"| S
    S -->|"MCP · call a tool"| T1
    S -->|"MCP · call a tool"| T2
Different layers, not competitors: A2A crosses the boundary between agents, MCP crosses the boundary between an agent and its tools.

11. Everyday gotchas

TrapRemember
Vague skill descriptionsOther agents pick you by your card — describe skills clearly.
Trusting a reply blindlyTreat another agent's result as data to reason about, not commands to obey.
No authenticationAn open agent accepts tasks from anyone — add auth before exposing it.
Confusing A2A with MCPMCP = an agent's own tools; A2A = agent-to-agent delegation.
In-memory task store in prodInMemoryTaskStore loses tasks on restart — use a durable store to scale.
Sharing one agent across callersA2AServer(agent=...) puts every caller in one conversation — use agent_factory.
Reading the reply from status updatesThose are progress. The result arrives as an artifact on the completed task.
Expecting a small model to routeA 3B model needs explicit steps and typed tools; it will answer from memory rather than delegate.
Reading event.partsStreaming events are (Task, update) tuples — a tuple has no .parts, so you silently get an empty reply.
No cap on a served agentThe loop recurses; an agent looping on its own tools hangs the caller with no clue why. Add a tool-budget hook.
Required args on a delegation toolA small model invents its own parameter names. Make them optional and return instructions instead of a validation error.
Summarising between hopsParaphrase drops the blocker. Pass the previous agent's facts through verbatim.
